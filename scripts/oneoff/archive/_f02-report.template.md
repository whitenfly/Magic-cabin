## 2. 为什么必须做这一步

实施前的实测：`monolith.js` 中有 **286 处 `Math.random()`**（185 行），发生在**场景生成期** ——
树木位置、石头朝向、花丛角度、蘑菇分布、星空排布、云块组合、雨雪初始位置，
甚至连**画布纹理的噪点**都用了它。

后果非常具体：

```
第一次加载：树在 (3.2, -7.1)，石头转 1.83 rad，星空这样排布
第二次加载：树在 (-5.7, 2.4)，石头转 0.41 rad，星空换了一种排布
```

于是当你想验证「把天气系统从 `updateWeatherSystem()` 拆出去有没有改坏画面」时：

```
重构前截图 ≠ 重构后截图
```

**但差异可能 100% 来自随机布局，与改动无关 —— 你无法判断。**
这是 `05-风险-验收-度量.md` 里的 **R1（概率 高 / 影响 致命）**：视觉回归是这次重构唯一的安全网，
而它在此之前根本无法建立。

## 3. 实施设计

### 3.1 三类分离，而不是一刀切

**最容易做错的地方是把 286 处一律换成 `rng()`** —— 那会让爆炸碎屑、镜子涟漪、撒糖每次都完全相同，**破坏原有的自然感**。
正确做法是按**生命周期**分三类：

| 类 | 含义 | 举例 | 种子策略 |
|---|---|---|---|
| **A** | **构建期**（场景生成） | 树木 / 石头 / 花 / 蘑菇 / 星空 / 云的位置与缩放 | **永久确定**，每次加载一致 |
| **C** | **初始化**（一次性算出、之后一直影响动画） | 粒子相位、气泡半径、烟雾漂移、书架每本书的微偏移 | **永久确定** |
| **B** | **运行期瞬态**（用户触发或循环重置） | 爆炸碎屑、镜子涟漪、撒糖、魔方打乱、翻牌、天气轮换、流星、闪电、震屏 | **默认真随机**（保自然感）；**测试模式**下切换为确定 |

**判断口诀**：

> 问「**这一处随机会不会影响"我在第 120 帧截到的图"？**」
> 会 → 种子化；不会 → 保持真随机，但提供测试模式开关。

### 3.2 七个随机源

| 随机源 | 类别 | 覆盖内容 | 调用数 |
|---|---|---|---|
| `outdoorRng` | A | 室外景物：森林 / 草地 / 石头 / 蘑菇 / 花 / 树桩 / 萤火虫 | 34 |
| `floor1Rng` | A+C | 一楼：书堆 / 坩埚 / 魔法阵 / 水晶球 / 纸堆 / 塔罗 / 毛线球 / 烟雾 / 气泡 | 26 |
| `floor2Rng` | A+C | 二楼：金币柱 / 雪景球雪花 / 星空粒子 | 14 |
| `skyRng` | A | 星空 / 云 / 雨滴 / 雪花 / 雪球粒子的初始位置与方向 | 55 |
| `textureRng` | A | Canvas 程序化纹理噪点（计划板黑板 / 毛茸茸大地毯） | 16 |
| `slimeRng` | C | 史莱姆体表气泡 | 4 |
| `runtimeRng` | B | 全部运行期瞬态效果（爆炸 / 涟漪 / 撒糖 / 天气 / 震屏 / 浮字重生…） | 137 |
| | | **合计** | **286** |

**全局种子**：`SCENE_SEED = 20260214`（`src/cabin/app/rng.js`）。
改动它会得到「整体不同但风格一致」的另一个小屋 —— 可用于生成多套布局做 A/B 比对。

### 3.3 为什么按区域 fork，而不是共用一个全局序列

若所有模块共用一个序列，那么**「在森林里多加一棵树」会让后续所有模块的随机值整体错位** ——
星空、云、雨雪全变，回归基线立刻失效，你无法判断是改动生效还是随机位移。

按区域 fork 后，**改森林不影响星空**，局部改动只影响局部比对。

### 3.4 确定性模式开关（B 类的测试通道）

```
?deterministic=1                        在 URL 上加这个参数
window.__CABIN_DETERMINISTIC = true     或设置全局标志（需在 boot 前）
```

开启后 `boot.js` 会调用 `setDeterministicRuntime(true)`，把 B 类随机也切为确定 ——
这样**爆炸、涟漪、撒糖、天气轮换**也逐帧可复现。
正常浏览时不开这个开关，效果保持自然随机。

## 6. 排查记录：过程中发现并修复的两个真实 bug

> 这两条有独立价值：它们都是**静态校验通过、但运行时才暴露**的问题。

### 6.1 ASI（自动分号插入）陷阱 —— 3D 完全无法渲染

**现象**：注入完成后，静态校验 23/23 全过、`tsc` 零错误，但浏览器里 3D **完全不渲染**
（截图只有 28 KB，是空白页 + UI；正常应为约 172 KB）。

**错误**：`TypeError: runtime(...) is not a function`

**根因**：注入的赋值语句没有分号，而下一行以 `(` 开头（顶层 IIFE）：

```js
const runtimeRng = runtime        // ← 缺分号
(function () { ... })()           // ← 被解析为 runtime(...) 的调用，而非独立 IIFE
```

JS 的 ASI 规则**不会**在此插入分号，于是解析为
`const runtimeRng = runtime(function(){...})()` ——
把 IIFE 当作 `runtime` 的参数调用，返回数字后再调用 → `runtime(...) is not a function`。

**定位方法**：

1. 先做 V8 错误消息格式实验，确定 `X(...)` 形态对应「调用返回值」（`f()()`）；
2. 排除 `runtimeRng()()` 的可能后，把 IIFE 临时包装为具名函数 `__cabinMain()` —— 错误消失
   （因为 `function` 关键字会触发 ASI），据此锁定为分号问题。

**修复**：`const runtimeRng = runtime;`

### 6.2 `Object.assign` 吞掉 getter —— 确定性验证出现假阳性

**现象**：确定性验证报告「三轮摘要完全相同」，但摘要值恒为 `811c9dc5`（FNV 初始值）。

**根因**：`Object.assign(target, { get digest() {...} })` 会**读取** getter 的值并复制为**数据属性** ——
所以 `digest` 永远停在初始值，`calls` 永远是 0。**"一致"其实是"都没变"**。

**修复**：改用 `Object.defineProperty` 定义 getter。

**教训**：一个恒定的指标看起来"稳定"，实则毫无信息量。设计验证指标时必须先证明**它会变化** ——
修复后 `scripts/oneoff/_rng-digest-test.mjs` 会断言「取值后 digest 必须改变」。

> 另有一次假阳性：验证脚本一度在**服务未启动**时截图，拿到的是 Chromium 错误页，
> 两次"相同"其实是同一个错误页。为此 `verify-determinism.mjs` 现在会先做**健康检查**
> （HTTP 可达 + `src/main.js` 存在 + `canvas` 已创建），不合格直接退出。

## 7. 使用方式

### 7.1 日常开发（默认：场景固定，特效自然随机）

```bash
pnpm serve            # 场景布局每次一致；爆炸/涟漪/撒糖保持自然随机
```

### 7.2 视觉回归（全部确定）

```bash
pnpm serve
node scripts/verify-determinism.mjs 3     # 三轮比对场景摘要
# 或手工：打开 http://127.0.0.1:5173/index.html?deterministic=1
```

### 7.3 在代码里使用

```js
import { scene, runtime, setDeterministicRuntime, sceneDigest, SCENE_SEED } from '@/cabin/app/rng.js'

scene.outdoor()                              // [0,1)，场景用（永久确定）
scene.outdoor.range(0, 10)                   // [0,10)
scene.outdoor.int(5)                         // [0,5) 整数
scene.outdoor.pick(arr)                      // 随机取一个
scene.outdoor.bool(0.3)                      // 以 0.3 概率 true
const r = scene.outdoor.fork('my-module')    // 派生独立序列（推荐新模块使用）

runtime()                                    // [0,1)，运行期用（默认真随机）
setDeterministicRuntime(true)                // 切为确定（测试）
sceneDigest()                                // 场景随机序列摘要（回归断言用）
```

## 8. 与 F0.3 的边界

F0.2 消除的是**随机性**，F0.3（可步进时钟）消除的是**时间不确定性**。二者合起来才能做到像素级复现。

当前状态：

| 项 | 状态 |
|---|---|
| 场景布局（树 / 石 / 花 / 星空 / 云 / 纹理） | ✅ 完全确定 |
| 运行期特效（爆炸 / 涟漪 / 撒糖 / 天气轮换） | ✅ 确定性模式下确定 |
| **时间驱动动画**（火焰摆动、水面、时钟、连续粒子） | ⬜ **属 F0.3**：`animate(t)` 的 `t` 来自 `performance.now()`，截图时刻的相位仍有微小差异 |

因此 `verify-determinism.mjs` 以**随机序列摘要**为主判据、截图哈希为辅证，
并明确标注剩余差异的来源 —— 不把 F0.3 的未完成误报为 F0.2 的缺陷。
