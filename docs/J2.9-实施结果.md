## 2. 为什么必须做（不变量 `N9`）

搬迁前同一个坐标写两遍：

```js
put(box(1.15, 0.06, 0.8), MTX, 0.75, MTZ);                        // 几何：餐桌在这儿
{ x: FX, z: FZ, r: 2.0, label: '点燃 / 熄灭壁炉', act: toggleFire } // 交互：壁炉判定在这儿
```

两边一旦不同步，就会出现**"看得见点不着"或"点得着看不见"**。
`J2.6` 的统一交互契约要求每个物件声明自己的 `anchor`，那时"坐标只能有一份"就从建议变成必需 ——
`J2.9` 是 `J2.6` 的前置。

## 3. 实现方式：脚本改 + 自检

15 处定义点散落在 8600 行里，手工逐处删除既慢又容易漏。
用 `scripts/oneoff/_j29-rewrite.mjs`：

1. 建筑外壳的 7 行连续定义 → **一次解构**（含 41 个名字，按分组换行）；
2. 14 处散落定义 → 按**精确行内容**删除（找不到就抛错，不静默跳过）；
3. 加 `import { createLayout } from '../world/layout.js'`；
4. **自检**：列出仍以「`NAME =`」形态出现的位置供人工核对。

> ★ 自检第一次跑**失败**了，值：判据把**派生常量**误判成残留 ——
> `const OX = MTX - 0.38`（派生自 `MTX`）、`const TEEPEE_TOP_Y = HEARTH + 0.62`。
> 收紧为"只判声明形态"（`const NAME =` 或 `const A = 1, NAME =`）后通过。
> 这也说明脚本化的价值：**它在写盘之前就拦住了**，而不是等到运行时才发现少了一个常量。

`layout.js` 以**语义分组 + 依赖顺序**组织（`FX = CHX + 0.15`、`TBL_TOP = FY + 0.80`），
而不是照抄 monolith 的散乱行序 —— `J3` 写 `defineProp` 时会直接照着它取坐标。

## 5. 新增测试：7 项坐标自洽性

`tests/unit/layout.test.mjs` **不测"某个坐标等于某个数"**（那是把实现抄一遍，改数值时两边一起改，等于没测），
而测 `J3` 写 `defineProp` 时会踩的坑：

| 测试 | 守什么 |
|---|---|
| `FX = CHX + 0.15`、`FZ = CHZ` | 派生关系没在搬迁中被打断 |
| `FY = FLOOR_TOP`、`TBL_TOP = FY + 0.80` | 二楼的锚点链完整 |
| 门窗洞 `y0 < y1`、`hw > 0` | **`logWall` 会按这个区间切原木**，非法区间会切出负高度 |
| 门窗不越过墙顶 | 剖切模式下的虚线位置正确 |
| 一楼陈设锚点低于楼面 | 没有被"放到二楼去" |
| 二楼锚点在小屋范围内 | 半边长约 4–6 米 |
| 壁炉与坩埚距离 > 1 米 | **交互半径不重叠**（`J2.6` 的近距判定按 `r` 竞争最近目标） |

## 8. 遗留与交接

| 项 | 留给谁 | 说明 |
|---|---|---|
| 其余 ~140 个坐标常量 | `J3` | 本批只收了「建筑外壳 + 交互判定引用的锚点」；每件物件自己的内部尺寸（如茶壶的 `PROF`、星象仪的 `OX/OZ`）在它被搬成 `defineProp` 时一起进 `layout.js` 或留在 prop 内 |
| 相机常量 `FIX_LOOK` / `fixYaw` / `fixPitch` / `fixDist` | `J2.7` | 属 `CameraRig` 的职责（`FIX_LOOK = V(0, 2.2, 0)` 是固定视角的注视点） |
| `D_HALF` / `WX` / `GABLE_TOP` / `RAIL_R` 等墙体细部 | `J3` | `GABLE_TOP` 依赖屋顶段的局部计算 `ridgeY`，要连算法一起搬（属 `world/house/shell.js`） |

## 9. 一句话总结

**41 个坐标从 15 处散落定义收敛成一份真源，画面未变一个像素** ——
它本身不产生任何可见效果，但它是 `J2.6`（每个物件要声明 `anchor`）与 `J3`（67 件物件搬迁）
共同的地基：从这一步起，"看得见"与"点得着"用的是同一份数字。
