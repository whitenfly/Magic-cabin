## 0. 一句话结论

`tests/e2e/perf.mjs` 生成基线报告时，文内链接前缀**写死**成了 `../../docs/实施结果/`。
那个前缀**本身没错** —— 对脚本自己所在目录（`tests/e2e/`）它是正确的；
错的是它被用在了**生成物**（`docs/*.md`）身上：从 `docs/` 出发会解析到
`FrontProj/docs/实施结果/`，**不存在**。

现在前缀改由 `linkPrefix()` **按生成物自己的位置**算出（`docs/` 下 → `./实施结果/`），
报告渲染抽成纯函数模块 `tests/e2e/perf-report.mjs`，并补了 **10 条单元判据** ——
其中 4 条在复现旧形态时**确实变红**（A/B 实证，见 §3），报错精确指向那个不存在的位置。

**产品代码零改动**：截图 3/3 机位 sha256 逐字节相同、冒烟 32/32、渲染统计全 **+0.0%**。

## 1. 事故解剖（为什么会坏，以及为什么没人发现）

### 1.1 现场

一次 `node tests/e2e/perf.mjs --gpu --rounds=5 --update` 之后，`docs/baseline.gpu.md` 的 diff 里有三样东西：

| # | 变化 | 性质 |
|---|---|---|
| 1 | 时间戳 + 参考项数值（首屏 504→532 ms、FPS 78.05→75.88） | 噪声范围内的正常刷新 |
| 2 | 页面 URL：`/index.html?deterministic=1&stats=1` → `/?deterministic=1&stats=1&bare=1` | **口径变化**（旧基线采于 `J1.5` Astro 落地之前） |
| 3 | 文末三个链接：`./实施结果/X.md` → `../../docs/实施结果/X.md` | ★ **把正确链接覆盖成死链** |

三样里只有第 3 样是**缺陷**，而它恰恰是最不容易被注意到的那样 ——
数字变了会有人看，链接变了不会。

### 1.2 根因：一次性批量改引用脚本把「生成模板」当成了「引用方」

`840c1db`（*实施结果文档集中到 `docs/实施结果/`*）用一次性脚本 `.cache/_fix-refs.mjs` 批量改引用。
那个脚本的规则是**对的**，文件头就写着：

```js
// 关键：**相对路径要按引用方所在目录重算**，不能做全局字符串替换 ——
//   根 README       → ./docs/实施结果/X.md
//   docs/*.md       → ./实施结果/X.md
//   tests/README.md → ../docs/实施结果/X.md
```

它的 `FILES` 清单里包含 `tests/e2e/perf.mjs`，于是按 `tests/e2e/` 算出了 `../../docs/实施结果/`。

**问题在于**：perf.mjs 里那三个链接不是它**自己**要用的引用，
而是**它生成 `docs/*.md` 时的模板文本** —— 引用的最终所在地是 `docs/`，不是 `tests/e2e/`。

⇒ **脚本没错，位置判断错了**：它把「文本住在哪个文件里」当成了「链接住在哪个文件里」。

### 1.3 为什么长期没被发现

`docs/baseline.md` 里至今仍是 `./实施结果/`（正确形态），不是因为它从没坏过，
而是因为**它自 `840c1db` 之后没被重写过** —— 模板里的坏前缀只会在**下一次 `--update`** 时落到文件上。

| profile | 上次重写 | 文件里的链接 |
|---|---|---|
| `swiftshader`（`docs/baseline.md`） | `840c1db` 之前 | 侥幸保留正确形态 |
| `gpu`（`docs/baseline.gpu.md`） | **本次事故** | 被覆盖成死链 |

**⇒ 任何人跑一次 `pnpm baseline:perf`（= `perf.mjs --update`）都会踩到它。**
这不是"某次手滑"，是一颗定时炸弹；只是这次由 GPU 采集先引爆。

### 1.4 与 P8 同类：跑起来是绿的，东西却是错的

这个缺陷**跑采集发现不了** —— 脚本退出码 0、数字全对、采集质量"✓ 稳定"，
只有文档静默变成了死链。它和 `VERSIONING.md` §附录B 的 **P8**（PowerShell 写文件会加 BOM）
属于同一类：**必须靠断言守，不能靠"跑一遍看看"**。

## 2. 改的是什么

### 2.1 三处改动

| 文件 | 改动 |
|---|---|
| `tests/e2e/perf-report.mjs` | ★ **新增**：`linkPrefix()` / `backendVerdict()` / `renderMarkdown()` 三个纯函数（从 `perf.mjs` 抽出）。前缀按**生成物位置**算，不再写死 |
| `tests/e2e/perf.mjs` | 删掉 `renderMarkdown()` / `backendVerdict()` 的定义，改为 import；调用时传入 `mdRel`（生成物的仓库相对路径）等参数；新增 `relPosix()` 工具 |
| `tests/unit/perf-report.test.mjs` | ★ **新增**：10 条判据（见 §3） |
| `tests/e2e/README.md` | 文件表补登 `perf-report.mjs`（`J4.12`） |

### 2.2 关键函数：`linkPrefix(mdRel, targetRel)`

```js
linkPrefix('docs/baseline.md',      'docs/实施结果')   // './实施结果'          ← 本次修复的形态
linkPrefix('docs/baseline.gpu.md',  'tests/e2e/baseline') // '../tests/e2e/baseline'
linkPrefix('tests/e2e/x.md',        'docs/实施结果')   // '../../docs/实施结果'  ← 事故形态：没错，只是用错了位置
```

基准是**第一个参数**（生成物）的目录 —— 这正是把「位置判断」从人脑挪进代码：
换产物位置也不用改模板。

### 2.3 为什么必须**抽出模块**，而不是就地改一行

`perf.mjs` 顶层有副作用（起浏览器 → 采集 → 写盘），**不能被单元测试 import** ——
`import` 它就会立刻跑完整个采集流程。

⇒ 改前那段渲染逻辑**根本没有被判据覆盖的可能**，这才是它能坏掉而无人察觉的结构性原因。
抽成纯函数后，`renderMarkdown()` 可以拿一份**假基线**直接调用并断言，无需浏览器、无需 5 轮采集。

> 这与 `tests/unit/release-tool.test.mjs`（给 `release.mjs` 写测试）是同一条既有的做法：
> **工具的关键逻辑要能被断言，而不是只能被"跑一遍"**。

### 2.4 刻意**没有**动的东西

| 没动 | 为什么 |
|---|---|
| `docs/baseline.md` / `docs/baseline.gpu.md` | 两个文件当前形态**都是正确的**，不需要改；产物应由脚本生成，不手工修 |
| `tests/e2e/baseline/perf*.json` | 判据数据，本任务与它无关 |
| `THRESHOLDS` / `REFERENCE_ONLY` / `WARMUP_MS` | 阈值语义的事实来源仍在 `perf.mjs`（`verify-f06` 有静态判据指向它们），只把**值**传进渲染器 |
| GPU 基线**重建** | ★ 见 §6 —— 实测证明**没有必要** |

## 6. ★ 遗留与交接

### 6.1 GPU 基线：实测证明**不该重建**（本任务是它的下游）

触发本任务的那次 `--update` 已被撤销（`git restore`，工作区回到 `HEAD`）。
撤销之后补跑了一次**只读**的 GPU 实测，用来回答"旧 GPU 基线（口径是 `J1.5` 之前的 `index.html` 形态）还能不能用"：

| 指标 | 旧 GPU 基线 → 现口径实测 | 偏差 | 阈值 | 判定 |
|---|---|---|---|---|
| `calls` / `triangles` / `geometries` / `textures` / `sceneObjects` | 3138 / 86158 / 2843 / 38 / 5365 → **逐项相同** | **+0.0%** | +10% | ✅ |
| `readyMs`（参考项） | 504 → 534 | +6.0% | +30% | ✅ |
| `fps`（参考项） | 78.05 → 66.46 | −14.8% | −25% | ✅ |

**结论：口径差异没有造成任何误报** —— 主判据逐项相同，两个参考项都远在阈值内。
⇒ 重建 GPU 基线**没有必要**，`J4.11` §7 立下的「判据的强度不动」继续成立。
本任务因此**只修生成逻辑，不动任何基线数值**。

### 6.2 还剩一颗同类炸弹（已由本任务判据覆盖一半）

`.cache/` 里仍留着那次集中化重构的几个一次性脚本（`_fix-refs.mjs`、`_fix-inner-links.mjs` 等，
均在 `.gitignore` 内）。它们的规则本身是对的，但**同样的误判仍可能重演**
（"文本住在哪个文件里" ≠ "链接住在哪个文件里"）。

现在有了判据 7–8（现存报告的链接必须可解析）与判据 3–6（**产出的**链接必须可解析），
**再犯会在 `test:unit` 里当场变红**，而不是等到某次 `--update` 之后。

> 建议：今后任何批量改引用的脚本，都把「引用方」定义为**引用的最终所在地**（生成物 / 产物），
> 而不是"这段文本当前躺在哪个文件里"。

### 6.3 未做（明确留给后续）

- **未给 `docs/baseline.md` 的链接单独加"产物存在性"以外的校验**（如锚点有效性）—— 收益与成本不成比例。
- **未把 `THRESHOLDS` 一并抽进 `perf-report.mjs`** —— 它是回归判定的语义来源，
  `verify-f06` 有静态判据指向 `perf.mjs` 里的定义；为一次渲染重构去动它，属于超出范围的搬迁。
