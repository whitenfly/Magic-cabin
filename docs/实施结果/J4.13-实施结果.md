## 1. 问题解剖

### 1.1 现象：两条规则各自成立，合起来互相矛盾

| 规则 | 内容 | 出处 |
|---|---|---|
| **§0.2 禁 1** | `dev` 上不许有开发提交。判定 `git log --no-merges "<最新 tag>..dev"` **应为空** | `VERSIONING.md` §0.2 |
| **§4⑥.1 回填** | 收尾实测结果可事后回填：**独立分支 + `--no-ff` 合并**，且**不打新 tag** | `VERSIONING.md` §4⑥.1 |

回填提交是**非 merge 提交**（`docs(<编号>): …`），而规则**不许**它带 tag ⇒
它**必然**落在最新 tag 之后 ⇒ 那条字面命令**必然非空**，而它的语义是「你违反 R1 了」。

**注意责任的归属**（这一点决定了版本位的判定）：

| | 对错 |
|---|---|
| **R1（规则本身）** | ✅ 没错。回填经 `--no-ff` 合并，**从不违反** R1 |
| **§4⑥.1（回填路径）** | ✅ 没错。不打新 tag 是对的（R8：序号不因回填而变） |
| **§0.2 的判定命令（测量手段）** | ❌ **错了**。它把「非 merge 提交」**等同于**「`dev` 直提」 |

⇒ 这是**尺子坏了**，不是**东西不合格** ⇒ 按 §12.3 属「措辞澄清 / 补漏 / 修错」⇒ **补丁位**。

### 1.2 根因：`--no-merges` 滤不掉「经由 merge 到达的提交」

`git log` 默认遍历**整张有向无环图** —— 合并的**第二父侧**（任务分支 / 回填分支）会被完整列出。
`--no-merges` 只把「merge 这个提交本身」从输出里去掉，**不影响**它带进来的那些提交。

```
dev  ──●────── M1 ────── M2 ──────●── … ──●(HEAD)
              ↑          ↑
              │          └─ M2 = merge task/J4.7-backfill
              │                第二父侧：docs(J4.7): 回填 ×2   ← 非 merge 提交
              └─ M1 = merge task/J4.7
                     第二父侧：J4.7 任务提交               ← 非 merge 提交
```

于是这两种东西在旧判据的输出里**长得完全一样**：

| 提交 | 真实身份 | 旧判据的看法 |
|---|---|---|
| `2fda17a` `J3 物件模块化（一）` | **直接 `commit` 到 `dev`** ＝ 真违规（判例 P1） | 违规 ✓ |
| `d442a2f` `docs(J4.11): 回填 —— …` | 经 `--no-ff` 合并进入 ＝ **完全合规** | **也报违规 ✗（假红）** |

### 1.3 为什么它**间歇显形**（★ 这一点决定了不能"跑一下看是否为空"）

旧判据背后的隐含假设是——*"`dev` 上的非 merge 提交一定是直提"*。
它在**没有回填路径**时成立：`task:done` 的顺序是「先 `merge`、**紧接着打 tag**」，
tag 指向 merge commit（＝`dev` 尖端）⇒「最新 tag 之后」**必然是空的**。

而 §4⑥.1 规定回填**不打新 tag** ⇒ 回填提交**永久**停留在最新 tag 之后，
直到**下一个任务**打 tag 才被淹没 ⇒ **假设在这里破了**。
（若回填是阶段最后一个动作，后面没有任务来打 tag，它就**永久非空**。）

| 时刻 | `最新tag..dev` 的非 merge 提交 | 结论 |
|---|---|---|
| `J4.7` 收尾当时（其 §2.6 记录） | **3 个** | 假红 |
| **本任务开工时**（`v0.4.0-dev.11..dev`） | **0 个** | 恰好绿 |

> ⚠️ **两条命令现在都是绿的** ⇒ 光看当前状态**验证不出修复是否有效**，
> 必须拿**历史区间**做 A/B（见 §2）。这也解释了为什么这个缺陷能活这么久：
> 它只在"回填之后、下一个 tag 之前"这个窗口里现形，而那时人往往正在忙收尾。

### 2.1 ★ 被证伪的备选判据（`J4.7` §2.6 留下的）

提示链上原本的说法是"**证据与替代判据已备好**"。
本任务按 A/B 检验它，结论是**它恒真、等于没有判据**：

```bash
# 用 J3 的 6 个【已知真直提】（判例 P1）检验"存在后代 merge"判据
$ git rev-list --no-merges "v0.2.5-dev.1..v0.3.0-dev.1" | while read c; do
    echo "$c  后代merge数=$(git rev-list --merges --ancestry-path "$c..dev" | wc -l)"
  done
f00bf115  后代merge数=30   判为[通过] ✗ 假绿
28fd863d  后代merge数=30   判为[通过] ✗ 假绿
87843b14  后代merge数=30   判为[通过] ✗ 假绿
666eb6d3  后代merge数=30   判为[通过] ✗ 假绿
d9e99b63  后代merge数=30   判为[通过] ✗ 假绿
2fda17ad  后代merge数=30   判为[通过] ✗ 假绿
```

**根因**：真直提之后的**任何** merge 都是它的**后代** ⇒ `--ancestry-path <提交>..dev` **永远非空**。
它只能抓到 `dev` 尖端那**一个**提交。

⇒ `J4.7` 当时"**2/2 全部通过**"是**空转**的结果，**不构成"判据守住了 R1"的证据**。
该脚本（`scripts/oneoff/_j4-ancestry-check.mjs`）已随本次修订 `git rm` 退役，
并在 `J4.7-实施结果.md` §2.6 追加了**更正块**（保留原文 + 追加，不改写历史）。

### 2.2 采纳的判据为什么是对的

```bash
git log --oneline --no-merges --first-parent "$(git describe --tags --abbrev=0 dev)..dev"
```

`--first-parent` 让遍历**只走 `dev` 自己那一侧**，跳过全部第二父侧：

- 回填提交 / 任务分支提交住在**第二父侧** ⇒ 天然不在其中 ⇒ **不再假红**；
- 真直提**必然**落在第一父链上 ⇒ **必然被抓**（`J3` 区间 6/6 已证）；
- **语义与规则本意完全一致**：§3.2「唯一判据」＝"任何改动都必须能追溯到某次 `--no-ff` 合并"，
  而「第一父链上无非 merge 提交」⟺「所有非 merge 提交都在第二父侧」⟺「全部经合并引入」；
- **顺带守住 R4**：若有人用不带 `--no-ff` 的合并（ff），任务提交会落到第一父链上 ⇒ 同样变红。

> ⚠️ **明确否决的替代做法**：「按提交信息排除回填提交」（`| grep -v 回填`）。
> 那会让判据**可被伪造** —— 给真直提起个 `docs(<编号>): 回填` 的名字即可绕过。
> 判据必须建立在**分支拓扑**上，不能建立在**提交信息**上。
