### 1.2 三处关键设计（不在原路线图里，但缺了就不成立）

#### ① aim 通路桥 —— 不加它，搬走的物件会"点不动"，而**没有任何测试能发现**

`J3` 期间 aim（准星 / 点击）仍由 monolith 的老机制驱动：

```
magicMeshes（命中集合） + userData.onClick（激活） + userData.aimLabel（提示文案）
   ↑ 由 interaction.registerAimSource({ id: 'magic', … }) 消费 —— 它正是 regMagic 的等价物
```

于是把 `regMagic(o, onClick)` 换成 `interactables` 之后，**必须等价补上这三件事**，否则：
画面**逐字节相同**（像素回归全绿）、冒烟只覆盖壁炉与书堆（全绿），而用户点扫帚**没有任何反应**。

`installProp()` 的 ⑤.2 节做了这件事，并额外写 `userData.cabinProp` 作为**来源标记** ——
`registry.stats().magicPropIds` 因此能回答"哪些物件真的有准星入口"，`tests/e2e/j3-probe.mjs` 断言它。
这是 `J3` 唯一一条"靠可观测判据而不是靠人记得"守住的隐性通路。

#### ② 原地 tick —— `UpdateScheduler` 在 `J3` 期间**只被登记、不被执行**

`animate()` 仍然直接调用 `tickOnce()`（约 940 行的更新体还在里面），调度器要到 `J4` 才接管。
所以把物件的每帧分支搬进 `update()` 之后，它会**静默不执行**（画面立刻变，回归当场红）。

解法：`install()` 返回一个 `tick` 句柄，monolith 在**原位置**调用它：

```js
const broomApi = installProp(broom);   // 装配点
…
broomApi.tick(dt, time);               // tickOnce() 里的原位置 —— 顺序一个字节没变
```

`update` 同时已经登记进 scheduler，`J4` 删掉这一行即可（切换零成本）。

#### ③ 惰性装配环境 —— 让"装配点早晚"不再决定能不能用共享工具

装配器在文件**早段**求值，而部分共享工具定义在**很后面**（`smooth` 在 18.8 段、
`cbox`/`crboxCol` 在 18.10 段、`colEdge` 在 18.12 段）。若 `ctx` 写成对象字面量，
这里会立刻撞上它们的 TDZ ⇒ 每件搬到二楼的小物件都只能**把工具函数复制一份**（模块化的反面）。

`ctx` 因此改成 **getter 惰性求值**，`installProp` 用 `Object.create(ctx)` 传递（不展开）。
效果：`rugLarge` / `junkBoxes` 里逐字复刻的 `crboxCol` / `cbox` / `colEdge` **已删除**，
改回调用 monolith 那同一个函数本身。教训写进 `world/README.md`。

### 2.3 为什么要有 `j3-probe.mjs`（一条"测不出来"的通路）

`test:visual` 只比较**画面**。而"物件的点击入口没了"在画面上**毫无痕迹** ——
搬迁前后三张基线逐字节相同，`test:smoke` 也只点壁炉与书堆。
`j3-probe.mjs` 因此直接断言 `registry.stats().magicPropIds` 覆盖每一件声明了交互的已搬迁物件。

探针里还留了一条**端到端参考**（对准物件点一下看画面变化）—— 它**不计入判定**：
那要求相机朝向、物件几何中心、命中体粗细三者同时对上，而扫帚柄只有 0.044m 宽、还带 0.33rad 倾角，
很容易点空。判据用清单，参考留给人工。

### 2.4 零差异是怎么被证明的（不只靠像素）

除像素回归外，搬迁方为高风险批次留了**只读的场景图比对**脚本
（`scripts/oneoff/_j3-verify-b4-scene.mjs` 等）：把迁移前的原文切成函数跑一遍、
新模块按原顺序装配一遍，逐项比对层级路径 / 类型 / 位姿 / 缩放 / 可见性 / 几何全参数 / 材质颜色与
`polygonOffset` / 契约 `userData`，并推进 420 帧比对动态状态 ——
`269 / 269` 节点逐行相同、`420 / 420` 帧相同。这条证据比像素更强（它证明的是**构造过程**相同）。

## 3. 偏差与留痕：剩余 46 件为什么没搬

**这不是"没做完"，而是四类可复核的结构性阻塞。** 每一类都经过至少两组独立研判。

### ① 每帧分支与主循环耦合，而应用器摘不掉 `animate()` 里的分支（约 20 件）

`_j3-apply.mjs` 只替换**一个连续区间**（几何段）。若某物件的每帧分支住在
`tickOnce()` / `updateNewDecor()` 里、且该分支**读了区间外的变量**，则：搬走几何 ⇒ 分支
`ReferenceError` ⇒ 整个应用起不来。

**典型**：`18.1 大床`（`pillowOpen/pillowT/pillowG` 被 `animate()` 读）、
`18.13 前墙挂画`（`picState`/`drawPicImage` 被 `updateNewDecor()` 读）、
`12.5`（已搬，靠人工改 `movingPlatforms` 才解开）、`floor2/pull-stool`（同上，未搬）。

**本阶段已给出解法的一半**：`tick.old` / `tick.new` 字段 + 应用器的 tick 自动接线
（本轮自动接了 6 处、人工接了 5 处）。**剩下的一半**是"分支本身依赖跨物件状态"，
那要等 `J4` 把主循环收成调度骨架。

### ② 光源槽位顺序不可保（约 6 件）

`lightField.register(...)` 的**注册顺序 = shader 闪烁相位 `float(i)` 的槽位**
（槽序：lantern / cauldron / magic-circle / kotatsu / crystal-ball / candle / veil / moon-plant）。
含光源的物件若把光源写进 `lights()`，它会在**物件所在位置**注册 ⇒ 变成槽位 0 ⇒ 8 盏灯的相位全移位 ⇒ 画面必变。

**典型**：`12.11 水晶球`、`12.13 暖桌`、`18.3 蜡烛`、`12.7 吊挂木灯`、`12.9e 大坩埚`、`12.x 月光盆栽`。
阻塞行与下一轮前置条件逐件写在 `floor1-crystal-ball.SKIP.md` 等文件里。
**解锁条件**：`J4` 把光源注册也收进"按原槽序批量注册"的通道。

### ③ 室外整片：`addStatic` 合并链不可切分（7 件全部）

树 / 草 / 石 / 树桩 / 木板 / 花全部经 `addStatic` 推入 `staticFillGeoms` / `staticEdgeGeoms`，
由 `mergeStatic` **一次性合并成 1 Mesh + 1 LineSegments** —— 拆开就改变 `scene.children` 构成
与合并策略（像素必变），不拆则模块拿不到 `addStatic`。

而花段与萤火虫段**必须留在 monolith**（`flowerMats` 被 `animate()` 按名字引用、
`ffTarget/ffOpacity/ffUniforms` 同理），它们又引用 `addStatic` / `yardSpotFree` ⇒ 基础设施也得留。
详见 `scripts/oneoff/_j3-b6-report.md`（含依赖地图与将来唯一的干净切法）。

**附带发现（TDZ）**：室外段在 `L407–L608`，**早于**装配器求值点 ⇒ 现在写 `installProp(...)` 会
`ReferenceError: Cannot access 'installProp' before initialization`。今次因为 ③ 本来就不能搬而未暴露，
但 `J4` 若要让更早的段也能搬迁，需把装配器求值提前（惰性 ctx 已为它铺好路）。

### ④ 自建射线类交互（1 件，一半已还）

`18.14 全身镜` 的**自建射线**（不看遮挡 + 需要命中点局部坐标，`J2.6` §5 明确留给 `J3`）没能等价搬迁：
它需要 `renderer.domElement`、`camera` 与命中点局部坐标，而 `ctx` 里没有 `camera`/`renderer`，
aim 通路又只传"激活"、不传命中点，且镜子**不能**改走主射线（进了 `magicMeshes` 就变成"被家具挡住就点不到"）。

**已还的那一半**：几何、状态（涟漪数组 / 画布 / 星表）、`drawMirror` 绘制、`spawnMirrorRipple`、
每帧刷新 —— 并把 J4 需要的两样交了出去（`parts.pane` 求交对象、`state.spawnRipple` 加涟漪入口）。
**诚实后果**：`J3` 期间镜面**点不出涟漪，但画面零差异**（高光扫过与星星闪烁由 `dirtyT` 每 0.12 秒重绘驱动，时序未变）。

## 6. 结论

`J3` 交付的是**一条可复制的搬迁流水线**：契约 + 装配器 + 挂载点表 + 应用器 + spec 格式 +
两条新门禁（探针、场景图比对），并用 21 件物件把它验证到像素逐字节零差异。

剩下 46 件**不是流水线不行，而是它们的前置条件在 `J4`**（主循环收编、光源槽序、`addStatic` 链、`ctx` 补 `camera`/`renderer`）。
每一件的阻塞点、边界与解锁条件都已逐件留痕（`.SKIP.md` 与 `_j3-b6-report.md`），`J4` 可以直接照着做。
