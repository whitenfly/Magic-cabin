## 1. 两件判据

### 1.1 `test:board` —— 计划板（`tests/e2e/board-notes.mjs`）

| 交互 | 判据（只断言确定性事实） |
|---|---|
| **3 张便签** | 点便签 ⇒ 编辑器弹出 + **回填该便签当前文字** → 写入新文字 + 点「确定」⇒ 收起 → ★ **读部件 `notes[0].txt` 确认真的改了** → ★ **再点开一次，输入框回填的正是新文字**（闭环证据，不依赖内部数组） |
| **板擦** | 点 ⇒ `eraserOpen` 翻转；推 120 帧 ⇒ `eraserT` 一阶低通逼近 1（实测 **0.99940**）；再点 + 推 120 帧 ⇒ 回到 ≈0（**0.00060**） |
| **粉笔** | 点 ⇒ `chalkActive=true`；逐帧推到自动结束（实测 **504 帧 = 8.40s**）⇒ ★ **粉笔回到 `CHALK_HOME`**（分量差 `0.00e+0`） |

★ 不断言任何画布像素 —— 那是 `test:visual` 的领域，且会让判据变脆。

### 1.2 `test:book` —— 魔法书本六相位（`tests/e2e/magic-book.mjs`）

```
closed ──点──▶ opening ──▶ flipping ──▶ fanning ──▶ open
  ▲                                                   │
  └──────────── closing ◀────────点───────────────────┘
```

- 初始 `closed`；点一次 ⇒ **去重后的相位序列按序出现** `opening → flipping → fanning → open`
  （实测 **122 帧**）；
- 停在 `open` 再点 ⇒ `closing → closed`（实测 **105 帧**）；
- ★ **过渡相位上点击无效**（只在两端响应）：点击前 `opening` → 点击后 `flipping`（没被拽去 `closing`）。

★ **不断言角度与时长** —— 那是逐字搬运的实现细节，断言它会让"合理调参"变成误报。

## 2. ★ 一次真实的开发事故：判据把开发机的核吃满了

### 2.1 现象与取证

用户报告"浏览器一开 CPU 立刻飙升"。实测取证：

| 证据 | 数值 |
|---|---|
| 残留 `chrome.exe` 进程 | **4 个**（2 个 `--type=gpu-process` + 2 个 crashpad-handler） |
| 其中两个 GPU 进程的**累计 CPU 时间** | **4295 秒** 与 **1809 秒** |
| `%TEMP%` 里 `cabin-cdp-*` 目录 | **360 个**（每个 ≈17.5 MB，合计 **≈6 GB**，时间跨度 09/13–09/17） |
| 渲染方式 | `--headless=new --use-angle=swiftshader` = **纯 CPU 软件渲染**（实测 **3.5 FPS**） |

### 2.2 根因（三个叠加，缺一不可）

1. **`cdp.mjs` 的 `chrome.kill()` 只杀 root 进程** —— Chrome 的 `gpu-process` / `crashpad-handler`
   是**独立进程**，root 一死它们就成孤儿；而且它们**不再持有调试端口**，事后只能靠
   `--user-data-dir=…cabin-cdp-*` 特征去认。
2. **`proc.kill()` 是异步的**，紧接着的 `fs.rmSync(userDataDir)` 撞上未释放的文件句柄 ⇒ 抛错
   ⇒ 被 `catch` **静默吞掉** ⇒ 目录留下（所以"代码里明明删了"却删不掉）。
3. **没有兜底** —— 脚本抛异常/被中断时，连那个（本来就删不掉的）`kill()` 都不会走到。

触发条件是"**点击打不中目标**"：判据的 `runUntil` 会一路推满上限（当时 2400 帧）才放弃，
而每帧都是一次软件渲染 —— 于是"排查一次点击问题"就等于把一个核烧满。

### 2.3 修法

`tests/e2e/cdp.mjs`：

- `killTree()`：Windows 走 **`taskkill /PID <pid> /T /F`**（`/T` 连带整棵进程树），其它平台 `SIGKILL`；
- `removeProfileDir()`：**先杀树、再删**，带退避重试（25 × 120ms）—— 因为 `taskkill` 返回时句柄可能还没释放；
- `liveInstances` + `process.on('exit' / 'SIGINT' / 'SIGTERM')` → `cleanupAll()` **兜底**；
- `launch()` 的"端口未就绪"分支也走同一套回收（原来只 `proc.kill()`）。
- `kill()` 保持**同步**语义：调用方一律是 `finally { chrome.kill() }`，改成 async 就得逐个改调用方。

**单元测试**（`tests/unit/cdp-cleanup.test.mjs`，4 条全过）—— 不依赖真 Chrome：

| 测试 | 钉住的行为 |
|---|---|
| ★ killTree 连**孙进程**一起杀 | 用"父进程 + 孙进程"模拟 root 与 gpu-process，断言**孙进程也必须死** |
| killTree 对已退出进程安全 | 不抛异常 |
| removeProfileDir 删**非空**目录 | 返回 true 且真的删掉 |
| removeProfileDir 幂等 | 对不存在的路径返回 true |

### 2.4 ★ 全部"不比对基线"的判据切到真实 GPU

`launch({ gpu: true })` 会**不注入** GPU 相关开关，让 Chrome 自己挑 —— 实测确认**真的用上了 GPU**：

```
launch({ gpu: false })  →  ANGLE (Google, Vulkan 1.3.0 (SwiftShader Device…))          ← 软件
launch({ gpu: true  })  →  ANGLE (NVIDIA, NVIDIA GeForce RTX 5060 Laptop GPU, D3D11)   ← 真实 GPU
```

**量化收益**：

| 判据 | 软件渲染 | 切 GPU 后 |
|---|---|---|
| **`test:smoke`（最重）** | **236.8s** | **9.8s**（**24×**） |
| `test:collision` | 几十秒 | **2.2s** |
| `test:magic-book` | 曾吃满核 | **3.4s** |
| `test:board` | 曾吃满核 | **5.9s** |

**切了**（9 个）：`wand-cast` · `collision` · `board-notes` · `magic-book`（纯状态断言）+
`smoke` · `j3-probe` · `cart-shelf` · `mirror-ripple`（比"交互前后的像素**变化量**"，非基线）。

**刻意不切**（2 个）：`test:visual`（与**基线 PNG 逐字节**比对，基线是软件渲染录的）·
`test:perf`（`--compare` 的基线就是 `profile=swiftshader`）。

**并且**：点击没生效时**不再空推满帧**（`p1 === 'closed'` / `p2 === 'open'` / `chalkActive === false`
直接跳过推帧），推帧上限也从 2400/1800 降到 **600**。

## 3. ★ 判据自身的三处错误（都是实测逼出来的）

1. **拿物件 id 去匹配 aim 目标** —— `registry.aimTargetOf()` 返回的是**交互条目** id
   （`magic-book/toggle`，注册时加 `magic:` 前缀），不是物件 id（`floor2/magic-book`）。
   结果 42 个候选机位**全被判成"没命中"**，而逐机位详情显示其中 41 个命中的**正是书本自己**。
2. **测试设计错误**：magic-book 的"过渡相位不响应"原本是在书**已经合上**时点的第三次 ——
   那当然会重新翻开，于是"收尾等它回到 `closed`"永远等不到。改成**趁它处于过渡相位时**点击。
3. **模板字符串里写反引号** —— 在 `page.eval(\`…\`)` 内部写注释时用了反引号，把模板提前终止
   ⇒ `SyntaxError`。同一个坑在本任务里踩了**两次**（`wand` 判据也曾踩过）。

## 6. 遗留

### 6.1 ★ 点开输入框后拿不到焦点（**发现但未修**，需单独处理）

`board` 判据发现：点开便签后 `document.activeElement` 是 **`BODY`** —— 用户**并不能直接打字**，
必须再点一下输入框。取证：

- 紧接着手动 `focus()` **有时**成功（`{ok:true, at:'noteInput'}`）、**有时**失败（`{ok:false, at:'BODY'}`）
  ⇒ 行为随运行**抖动**，更像 headless 环境下的焦点不可靠，而非稳定的产品缺陷；
- 三种修法实测**都没改变结果**：同步 `focus()` / `setTimeout(…,0)` 延后 / `pointerup` 上 `preventDefault`；
- `J4` 只搬不改这段逻辑（`verify-migration` 保证逐字未变），且 `shell.js` 的**路牌编辑器是同一份代码**
  （`inp.focus(); inp.select();`）⇒ **不是搬迁回归**。

⇒ 判据**只报告、不判红**，避免把"一直存在的行为"当成回归。**待办**：在带真实窗口的浏览器里复核
一次（那里焦点语义正常），确认是否真的需要修（以及路牌 / 画像编辑器是否同样）。

### 6.2 `cdp.mjs` 的回收已修，但"强杀进程"仍无法兜底

`process.on('exit')` 能覆盖异常与正常退出；但**被 `Stop-Process -Force` 这类强杀**时，
Node 没有机会跑任何 handler —— 那种情况下只能靠 `--user-data-dir=…cabin-cdp-*` 特征事后清理
（本任务就是这样清掉 360 个目录的）。

### 6.3 `board` 判据未覆盖"板擦与粉笔的**视觉**结果"

它断言的是状态（`eraserT` 收敛、粉笔归位），不是"板擦真的翻过来了"的画面。
后者属于像素判据的领域，本任务不涉及。

## 8. 顺带修掉的一个潜伏 6 个任务的缺陷

跑 `unit` 时发现**2 条测试一直红**：「段序 = 执行序」「每个段都有模块」。

- 根因：`J4.43` 删掉 `NoteEditor.js` 段、也改了 `installCabin.js`，但**漏了同步段表**
  `scripts/oneoff/_j4-segments.mjs`（L114 还留着 `installNoteEditor`）；
- **为什么潜伏 6 个任务**：`J4.42` §2.4 记的"段表不参与门禁"在当时**成立** ——
  `release.mjs done` 的门禁只有 `typecheck + verify + build`，**不含 `test:unit`**，
  所以这两条红了也没人跑、没人看见；
- ⇒ 修法一行（删段表项），`unit` 从 **203/205 → 205/205**。
- ⚠️ **建议**：把 `test:unit` 纳入 `done` 的门禁链（或至少纳入交接清单）——
  否则"测试红了但没人跑"还会再发生。
