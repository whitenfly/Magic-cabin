## 1 · 四项遗留的处理

### L1 · `dev.N` 序号算法（数量法 → 最大法）

**问题**：`nextDevVersion()` 原用 `st.localTags.filter(t => t.startsWith('v<base>-dev.')).length + 1`。
**数量法在删过 tag 后会算错**：`dev.1/dev.2/dev.3` 删掉 `dev.2` 后数量变 2 ⇒ 下一个又算出 `dev.3` ⇒ **与现存 tag 冲突**（`git tag` 直接报 already exists）。

**修法**（对齐 §2.4 / R8「序号取历史最大 N + 1，不重用」）：

```js
const esc = base.replace(/[.*+?^${}()|[\]\\]/g, '\\$&');
const re = new RegExp(`^v${esc}-dev\\.(\\d+)$`);
const used = st.localTags.map((t) => re.exec(t)).filter(Boolean).map((mm) => Number(mm[1]));
const nextN = used.length ? Math.max(...used) + 1 : 1;
```

（`base` 里的 `.` 必须转义 —— 否则 `0.3.0` 会匹配到 `0x3y0`。）

### L2 · `package.json` 版本号：**强制校验**，而非自动代改 ★

**这是一个需要解释的取舍**。两种实现都可行：

| 方案 | 做法 | 问题 |
|---|---|---|
| A · 自动代改 | `done` 直接写入 `version`，并自动追加提交 | ⚠️ 会让规范 §3④ 的描述**失真**（§3④ 明确把"对齐版本号"列为**开发者在 ④ 步的动作**）；要改 §3④ 就得走 §12.2 **规范修订**流程，而那是**另一个任务**（R14 禁止混入） |
| **B · 强制校验** ✅ | `done` 在 merge 前**校验** `version` 是否等于将要打的 tag；不一致就 `die` 并给出准确的修改指令 | 不改变规范描述的分工（**开发者对齐、工具验证**），且同样消除"忘了改" |

**⇒ 选 B**。理由：它把 R9 从"靠附录 A5 人工自检"升级为**机械强制**，同时**不制造新的"规范与实现不一致"**——而这个项目已经被那类问题咬过好几次（`J3.4`/`J3.6` 都在修它）。

实现位置：`nextDevVersion()` 返回 `nextN` 之后、执行 merge 之前：

```js
const wantVersion = `${base}-dev.${nextN}`;
const pkgVersion = String(JSON.parse(readFileSync(join(ROOT, 'package.json'), 'utf8')).version);
if (pkgVersion !== wantVersion) die(/* 指明应改成什么 + 依据 R9 */);
ok(`版本号已对齐：${wantVersion}`);
```

顺带把记录里的提示由「package.json 的 version **请同步**」改为「**已校验**与 package.json 一致」。
