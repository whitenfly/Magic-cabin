## 2. 覆盖的关键路径

```
S0 启动与确定性前提    canvas / manual 时钟 / 两个测试钩子 / 9 个 UI 节点 / 无页面异常
S1 门外               提示条指向「打开 / 关上大门」
S2 按 E 开门          门的弹簧动画
S3 按 W+D 前进        穿过大门进屋：提示条变为「点亮 / 熄灭魔法吊灯」（174 帧）
S4 点燃 / 熄灭壁炉    火焰与光照响应（像素变化 1.027%）
S5 切 3 视角          固定 → 第三人称 → 第一人称 → 按 V 互换 → 回固定（逐项断言 `.on`）
S6 点击书堆           书籍类物件响应（像素变化 2.191%）
S7 切天气             菜单打开 → 7 个选项齐全 → 选「雪」→ `#clock` 文本 + 选中态 + 画面变化 81.1%
S8 退出               关闭菜单 + 全程无未捕获异常
```

`S3` 一步同时验证了**移动 / 碰撞 / 门开合 / 交互可达性**四件事 —— 门没开就过不去，
过了门就说明「按 E 开门」真的生效了（门的开合状态在 IIFE 内部，外部读不到，但"能否穿过"是它的直接后果）。

## 3. 设计：为什么它可复现

和 `J0.4` 一样跑在 **manual 时钟**下：

```
?deterministic=1&frames=1     ← 只推进一帧建立场景，此后页面不自行推进
keydown(W) + keydown(D)  →  逐帧推进 174 帧  →  提示条变成"魔法吊灯"
```

每一帧都由脚本调用 `window.__cabinStepFrame()` 推进，于是：

| 观测量 | 第 1 次运行 | 第 2 次运行 |
|---|---|---|
| 走进屋所用帧数 | 174 | **174** |
| 壁炉像素变化 | 1.027% | **1.027%** |
| 书堆像素变化 | 2.190% | **2.191%** |
| 天气切换像素变化 | 81.114% | **81.114%** |
| `#clock` 文本 | 10:05 · 晴 → 10:06 · 雪 | **同上** |

没有"等 1.5 秒看看"这种写法 ⇒ 失败可以稳定重放。

### 3.1 断言写在"可观测的副作用"上

场景状态全部在 `legacy/monolith.js` 的 IIFE 里，外部拿不到。所以只用三类证据：

| 证据 | 用在哪 |
|---|---|
| `#hint` 的文本与 `show` 类（提示条 = 当前可交互对象） | 可达性：走到哪、能不能交互 |
| DOM 状态（`.on` / `.open` 类、`#clock` 文本） | 视角、菜单、天气 |
| **像素差分**（操作前 vs 后） | 3D 物件是否真的响应了 —— "操作后画面确实变了"就是交互生效 |

第三类是通用判据，也是本阶段最省事的一条：**不必知道物件内部发生了什么，只要证明它响应了**。

## 4. 排查记录：两个真实的坑

### 4.1 走位方向：单按 W 会被门框挡住

固定视角下 `camYaw = fixYaw + π`，单按 `W` 的移动方向是 `(sin, cos)(camYaw) ≈ (-0.63, -0.77)` ——
**斜着走**。走到 `z = 4` 时 `x ≈ -0.98`，正好落在**门左侧的墙**里
（`solidBoxes` 的 `x∈[-4.85, -0.78]`），人卡在门外、提示条停在"开 / 关前左窗"。

叠加 `D` 后的合方向 ≈ `(0.10, -1.00)`，正对门洞（`x∈[-0.78, 0.78]`）⇒ 顺利穿过。

> 这条不是脚本 bug，而是**场景的真实约束**被冒烟暴露出来了 —— 记在 `tests/e2e/README.md` 里，
> 后续 `R1`（固定视角下点不开博客道具）相关改动能用得上。

### 4.2 页面内长循环会撞 CDP 超时

`Runtime.evaluate` 里一次推进 400 帧，在 headless + SwiftShader 下每帧渲染 1440×900 约 0.2s，
必然超过默认的 60s 超时。

修法两条：**分批推进**（每批 40 帧）+ 给 `page.eval` 与 `step()` 显式传 `timeoutMs`（按帧数放大）。
`tests/e2e/cdp.mjs` 的 `eval()` 因此增加了 `timeoutMs` 参数。

## 5. 已知偏差（诚实记录）

| 路线图原文 | 实际做法 | 原因 |
|---|---|---|
| "**抽出书架上的一本书**" | 点击**书堆**（`bookPileG`） | 书架是**装饰 + 实心阻挡**，不是交互物件；"书架即博客"要 `J6` 才有。到 `J6` 时这一步替换为真正的抽书路径（`mapping.yaml` 的 `M01`） |
| "退出" | 关闭菜单 + Esc | 网页应用没有"退出"语义；`J0.6` 之后若引入门厅策略（`J1.5`），这里改为"返回门厅" |
| `P0.5` 里的"施法 / 重置" | 未覆盖 | 施法需要先装备魔杖（`Digit2`）并对准目标，属于 `J2` 统一交互契约要收敛的部分；`R1` 修复后再补 |

> 这三条不是缩水，而是**把"这一阶段能证明的"和"要等后续阶段的"分清**。
> 对照 `ArtLine-Part/09` 的验收口径，`J0.5` 的目标是"关键路径可用"，不是"全部 64 + 9 处交互可用"
> （后者是 `F6`，判定方式是逐项核对清单）。

## 6. 使用方式

```bash
pnpm serve          # 另开一个终端（零构建兜底路径）
pnpm test:smoke     # 28 项断言；约 200s（时间主要花在逐帧推进上）

# 排查某一步失败：看操作前后的对照图
node tests/visual/view.mjs _shots/e2e/stove-before.png --diff _shots/e2e/stove-after.png
```

脚本逐项打印 `✓ / ✗` 与证据（帧数、像素变化率、提示条文本），失败时列出全部失败项并以非零码退出。

**页面上的测试钩子**（都**只在 manual 模式存在**，正常游玩路径上没有这些接口）：

| 钩子 | 来源 |
|---|---|
| `window.__cabinStepFrame()` | `F0.3` |
| `window.__cabinSetTestCamera([px,py,pz,lx,ly,lz])` | `J0.4` |
| `window.__cabinSetFullHouse(bool)` | `J0.4` |

> ⚠️ 需要真实浏览器：受限沙箱禁止命名管道时 Chrome 会以
> `FATAL: platform_channel.cc … 拒绝访问 (0x5)` 退出（与 `J0.4` 同一限制）。

## 7. 与后续阶段的关系

- **`J0.6`（性能基线）** 是 `J0` 的最后一项，不阻塞任何阶段，但建议在 `J2` 动相机与调度器**之前**补上。
- **`J2`/`J3`/`J4`** 的每批搬迁都要跑 `pnpm test:smoke` —— 物件从 `legacy` 搬出后，
  提示文案与交互行为不得退化（`F6`：`label` 必须有语义）。
- **`J6`** 在 `tests/e2e/` 追加层次（`layer-regression`）与闪烁（`flicker-diff`）脚本，
  并把 `S6` 的"点书堆"替换为真正的"抽书 + 翻页"。
