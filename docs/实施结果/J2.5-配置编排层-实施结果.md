## 2. ★ 三条核心机制

### ① schema 驱动：加一个配置项 = 改 **1 个文件** + 加 **1 个字段**

```
src/config/settings.config.js   加一个字段（type / default / group / label）
         │
         ▼  SettingsForm 按 type 选控件，不认识任何具体的键
#menuPanel 里该分组的锚点 [data-setting-group="<group>"]
         │
         ▼  点击 / 拖动
store.set(key, v) ──► localStorage（cabin: 前缀）+ 通知订阅者（场景据此变化）
```

`SettingsForm.js` 里有**一条** `switch` 在 `type` 上（`boolean` / `number` / `enum`），
**没有**任何一处出现具体的设置键 —— 这一条由门禁守着：

```
✓ SettingsForm 里不出现任何具体设置键（不认识 view.mode 之类）  零硬编码
```

**锚点机制**：分组的**位置与标题**仍写在 `cabin/dom.js` 的菜单 HTML 里（那里还夹着
**不是设置项**的东西：天气选择 chips、时刻滑杆、魔法槽位），`SettingsForm` 只往锚点里**填控件**。
锚点找不到时（模块自己新增的分组）会**连标题一起生成**，追加到 `#settingsAuto` —— 那部分才是"零 HTML 改动"。

### ② 单向数据流：控件只写 store，场景只读 store

搬迁前每个控件都是"**自己改值 + 自己应用 + 自己更新外观**"三件事写在一起：

```js
// 搬迁前（monolith L7383）—— 一个函数干三件事
function setViewMode(m) { viewMode = m; store.set('view.mode', m); cameraRig.setMode(m);
  viewFixedBtn.classList.toggle('on', m === 'fixed'); /* …还有两个按钮 */ }
```

现在拆成三条互不重叠的职责：

| 角色 | 职责 | 谁 |
|---|---|---|
| **写** | 只调 `store.set(key, v)` | `SettingsForm`（面板） / 键盘 `KeyV`（经 `setViewMode`） |
| **应用** | 订阅 store，把值变成画面 | `cabin/legacy/monolith.js` 的 `store.subscribe(...)` |
| **显示** | 订阅同一个 store，更新控件外观 | `SettingsForm` 的 `store.subscribe('*', …)` |

于是"从面板改"与"从键盘改"走的是**同一条路**，不会出现两套状态。
`store.subscribe` 只在**值真的变化**时触发，所以首屏那一次显式应用仍由 `applyFullHouse(...)` /
`applyViewMode(...)` 负责（与 `J2.8` 的行为逐点一致）。

### ③ 模块总开关：关掉一个模块 = 改一个布尔值

`blog/registry.js` 按 `modules.config.js` 过滤 `features/_index.js` 的清单，
**未启用的模块连 `load()` 都不调用** —— 它的 chunk 不会被浏览器请求（对齐 Firefly 的
`siteConfig.pages.*`，验收 `CF1`）。清单里的 id 在开关表里**缺项即抛错**（不是静默按关闭处理），
这是 `04` §3.2 规则 4「可缺省即失败」的落点，防 `R30` 漂移。

## 7. ★ 一个真实逃逸过的 bug（留痕）

**现象**：像素回归报 `3 个机位零差异 / 0 个有差异 / **3 个无效截图**`，
且 `compare.mjs` 只在"哈希不同"的分支里打印 `shot.problems`（`compare.mjs:151`），
所以**看不到原因** —— 只看到"结果不可信"。

**根因**：`createSettingsForm` 的默认参数写成了 `SETTINGS`
（`cabin/app/settings.js` 派生出的**数组**），而 `planGroups` 用 `Object.entries` 遍历 ——
数组给出的"键"是 `'0' / '1' / …` 索引，于是 `store.get('0')` 全是 `undefined`，
面板在格式化读数时 `undefined.toFixed(2)` 抛错、整个面板挂载失败。

**为什么 46 项单测没抓住**：所有用例都**显式注入**了 `settingsSchema`（对象），
生产路径（`boot.js` 不传 `settings`）恰好是唯一没被覆盖的那条。

**三个修复**（都留下了护栏）：

| # | 修复 | 护栏 |
|---|---|---|
| 1 | 默认值改用 `settingsSchema`（对象） | 新增单测「不传 settings/groups/display 时也能挂载」——**专门走生产路径** |
| 2 | `planGroups` 收到数组时**抛错**（而不是把索引当键） | 新增单测 + 门禁可复用 |
| 3 | `formatSettingValue` 对非有限数返回占位 `—` | 面板不该因为一个坏值全挂 |

**顺带证明了一件好事**：`boot.js` 的 `mountSettingsForm` 用 `try/catch` 兜住了面板挂载失败，
所以**3D 场景照常启动、像素零差异、冒烟全绿** —— 面板坏了没有把小屋拖下水。
而门禁仍然把这件事**报了出来**（`invalid: 3`）—— 判据是有效的。

**诊断工具**：`scripts/oneoff/probe-j25-errors.mjs`（一次性探针，打印 `page.errors()` 与
设置面板的 DOM 体检表）。留着它，下次再遇到"无效截图但看不到原因"可以直接用。

## 9. 一句话总结

**"用户唯一需要看的目录"从第一天就存在了** —— `src/config/` 不再是一份说明书，
而是真的在驱动画面：改一个字段，面板自己长出控件、值自己存进 `localStorage`、场景自己跟着变
（`CF2`）；关一个布尔，那个模块的代码**根本不会被下载**（`CF1`）。
而这两条路都有机器守着 —— 31 项 `verify-cf` 断言 + 46 项单测，
以及一次真实逃逸后被补上的回归测试。
