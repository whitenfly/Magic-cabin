## 1. 问题：「能点开」≠「点开后行为正确」

`J4.20` 就写下过这个结论。落到魔杖上，它此前只有两条**弱保证**：

| 弱保证 | 它实际证明的事 |
|---|---|
| `j3-probe` | `wand/cast` 这个 aim **入口存在**（`magicMeshes` 命中 + `aimLabel` 可读） |
| 「同构先例」 | 别的物件搬完也正常 ⇒ 它大概也正常 |

而下面三件事，**画面回归一件都看不见**（三个机位是**没人去点的**定格帧）：

- 五段状态机是否真的**依次推进**（还是卡在第一段）；
- `circleHolder` / `crea` 是否被**清理**（还是每点一次就往场景里漏一对对象）；
- `wandG` 是否**回到静止位姿**（还是歪着停在半空）。

## 2. 判据形态

### 2.1 三个测试支撑钩子（都挂在 `?stats=1` / manual 约定下）

| 钩子 | 作用 | 为什么必须存在 |
|---|---|---|
| `window.__cabinPropState(id)` | 任一已装配物件的 `state` + `parts` 的**可序列化视图** | 数据源是 `ctx.propInstalled`（`installProp` 的装配记录 Map）——它本来就导出了 `get(id)`（注释写着"诊断与测试用"），**这里只是把已有通路接到页面**，不新增状态 |
| `window.__cabinAdvance(n, dt)` | 推进 N 帧**并推进时钟** | 见 §3 缺陷 ② |
| `window.__cabinSceneHas(uuid)` | 按 `uuid` 回查对象**是否仍在场景图** | 见 §3 缺陷 ③ |

`__cabinPropState` 的视图规则：原始值原样；`Object3D` 给 `type / uuid / inScene / 位姿`；
几何 / 材质 / 数组 / 函数只给占位符 —— 避免把整个场景图塞进测试。

### 2.2 断言清单（**只断言确定性事实**）

★ `wand.js` 有 **9 处 `runtimeRng()`**，施法时**抽元素**（`s.idx = Math.floor(runtimeRng() * ELEMENTS.length)`）
本来就是随机的 ⇒ 判据**绝不断言"抽到哪个元素"或"造物长什么样"**，只问"**走完了、清理了、归位了**"：

| # | 断言 |
|---|---|
| 1 | 初始 `phase === 'idle'`，`circleHolder`/`crea` 均为 `null` |
| 2 | 点击**真的**触发了施法（`phase` 离开 `idle`）—— 防止"点空了"变成无声通过 |
| 3 | ★ 五段状态机**依次**推进（去重后按序匹配 `fly → cast → fade → return → idle`） |
| 4 | `circleHolder` / `crea` **真的进过场景**（不是只有状态变量被赋值） |
| 5 | ★ 两者最终**彻底清理**（状态置空 **且** 对象离开场景图） |
| 6 | ★ 出现过的造物对象**按 `uuid` 回查全部离开场景图** |
| 7 | ★ `wandG` 回到静止位姿：位置 = `WAND_REST`、四元数 = 单位（容差 `1e-3`） |
| 8 | 末帧 `phase === 'idle'`；全程无未捕获页面异常 |

## 3. ★ 三个缺陷都是**实测/负例逼出来的**（这一节是本文档的重点）

### ① 点击落在**视口外**（第一版判据直接红）

第一版照 `cart-shelf.mjs` 的写法用 `canvas.getBoundingClientRect()` 推点击点，得到 **(450, 900)** ——
而视口只有 **900×600**。`bare=1` 下 canvas 的 CSS 高度实测远大于视口 ⇒ 事件落在**视口外**，
点击根本到不了场景。

**处置**：改用 CDP 真实输入事件（`Input.dispatchMouseEvent`，照 `j3-probe`）+ **视口中心**
—— aim 通路的射线本来就走**准星**（屏幕中心）。

### ② `__cabinStepFrame` **不推进时钟** ⇒ 状态机永远走不出第一段

第一版用 `window.__cabinStepFrame()` 推 330 帧，结果 `phase` **一直停在 `fly`**。

**根因**：`__cabinStepFrame` 就是 `ctx.tickOnce()`，**不推进 `clock`** —— 这正是 `J0.4`「定格帧」要的语义
（120 帧定格后画面必须停住）。但魔杖状态机由**绝对时间** `e = time - s.t0` 驱动
⇒ 时钟冻结时 `e` 恒为 0。

> ⚠️ **这条对所有未来写运行期判据的人都是坑**：`cart-shelf` / `j3-probe` 能用 `__cabinStepFrame`，
> 是因为它们的动画按 **dt 累积**；凡是按 **绝对时间**驱动的（魔杖 · 沙漏 · 魔术书 · 塔罗牌…）
> 都必须用 `__cabinAdvance`。已记进 `J4.32-实施结果.md` §5。

**处置**：新增 `window.__cabinAdvance(n, dt)`（`clock.step(dt)` + `tickOnce()`，默认步长 `1/60`）。

### ③ 只看状态变量 ⇒ **"状态清了、对象却还留在场景里"会假绿**

第一版把"清理"断言写成 `s.crea === null`。负例 B（**删掉 `scene.remove(s.crea)`、只留 `s.crea = null`**）
**照样绿** —— 因为对象一旦不再被状态引用，状态视图就再也看不见它了。

**处置（两层）**：

1. 钩子给 `Object3D` 增加 `inScene: !!v.parent`（`scene.remove()` 会把 `parent` 置回 `null`）；
2. ★ 更关键的一层：采样时**记下出现过的 `uuid`**，最后由 `window.__cabinSceneHas(uuid)`
   **回场景图逐个复查** —— 断言的是"它**确实离开了**"，而不是"状态变量被清空了"。

**这一层加对了**：同样的负例再跑一次 ⇒ **红**（`crea:1A1ED572-… 仍在场景里`），而基于状态变量的
那条断言**依然绿** —— 两条断言的差别被实测钉死。

| # | 操作 | 期望 | 实测 |

**未做的事**（明确边界）：

- **`board` / `magic-book` 没补**（用户拍板本轮只做 `wand`）。它们的状态机同样是**绝对时间驱动**
  （`J3` 搬迁时都把 `clock.now` 换成了 `s.now`），因此**可以直接复用**本次的三个钩子与
  `__cabinAdvance` —— 补起来比本次更快。
- **没有把"抽到哪个元素"接进判据** —— 那是随机的（9 处 `runtimeRng`），断言它等于把判据变脆。
  若将来想覆盖"六种元素造物都长得对"，正确做法是**固定 `runtimeRng` 种子**后逐个跑一遍，
  而不是在同一次随机里断言结果。
- **`__cabinPropState` 只做浅层视图**：`state` 里嵌套的普通对象只显示成 `<Object>`。
  本次够用（`phase` / `idx` / 两个对象引用都是浅的）；若将来某个物件把状态藏在嵌套对象里，
  需要按需加深。
