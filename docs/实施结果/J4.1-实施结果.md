## 1. 做了什么

### 1.1 为什么 `J4` 不能沿用 `J3` 的搬法（这是本任务存在的理由）

`J3` 的搬法是「一件物件一个区间」：读分区 → 写模块 → 用 `_j3-apply.mjs` 把一个**连续区间**
换成一次 `installProp(...)`。它跑了 35 件，很成功。

但 `J4` 要搬的是**系统**，而系统的代码不是连续区间 —— 它们与主循环、与彼此**交错**在同一
个 IIFE 里，靠"函数声明提升 + 同一个作用域链"活着。`scripts/oneoff/_j4-analyze.mjs` 量出：

| 指标 | 值 |
|---|---|
| `installCabin()` 里的 IIFE 体 | **L111–L6215**（6105 行） |
| 顶层声明 | **780**（`const` 580 / `let` 90 / `function` 110） |
| 对顶层声明的引用 | **2190 处是"立即求值"的**（随执行流程立刻读） |
| **立即执行的前向引用** | ★ **0 处** |

最后一行是整件事的可行性证明：**原文里"立刻要用"的引用全都指向更早（或同段）的声明**。
那 33 处跨行"前向引用"（如 `smooth` 声明在 L2471、最早引用在 L696）**全部住在函数体里**，
是延迟求值 —— 切片后走 `ctx` 完全安全。

> 逐件手搬在这里走不通：每搬一处都要手改 2190 处引用中的一部分，
> 而漏改**不会让编译报错**，只会在运行时炸。

### 1.2 段切片：一次机械变换，换掉全部跨段引用

**段表**（`scripts/oneoff/_j4-segments.mjs`）把 IIFE 体切成 21 段，每段有 `hint`（定性行号）、
`module`（目标模块，可暂空）、`fn`（导出函数名）。**段序 = 执行序** ——
`rng` 调用顺序、`scene.add` 顺序、`lightField.register` 的槽序都由它决定。

**应用器**（`scripts/oneoff/_j4-apply.mjs`）是 `monolith.js` 的**唯一写者**（沿用 `J3` 的纪律），
两个动作：

```bash
node scripts/oneoff/_j4-apply.mjs --ctxify          # ① 全段 ctx 化（只做一次，不搬代码）
node scripts/oneoff/_j4-apply.mjs --check           # ② 逐引用验证段间通信完整
node scripts/oneoff/_j4-apply.mjs --move=<段id>     # ③ 把一段剪进它的目标模块
```

`--ctxify` 的改写规则只有三条：

| 情形 | 处理 | 为什么 |
|---|---|---|
| `d` 在**别的段** | 引用 → `ctx.<name>` | 段已经不是同一个作用域了 |
| `d` 在**本段**且是 **`let`** | `let x = …` → `ctx.x = …`；引用 → `ctx.x` | **可变的跨段共享状态**，留成局部就会各持一份副本 |
| `d` 在**本段**且是 `const`/`function`/`class` | 原名保留 + 导出到 `ctx` | 段内代码几乎零改动，只有跨段才走 `ctx` |

实测规模：**2245 处引用改写 + 90 处 `let` 绑定改写 + 59 处 `let` 前缀删除**，
`monolith.js` 6217 → 6702 行。

### 1.3 ★ 五个只有"跑起来"才会发现的坑（全部已修，全部留了判据）

这一段是本任务最值钱的部分 —— 它们**没有一个能被 `tsc` 或 `build` 拦住**。

| # | 现象 | 根因 | 现在的判据 |
|---|---|---|---|
| **①** | 页面完全起不来，`TypeError: cbox is not a function`；像素回归只报「等待超时（120000ms）」 | 第一版把整段导出**统一放在段末**。而 `floor2/wardrobe` 在 floor2 段**中间**装配时，经 `propTool('cbox', () => ctx.cbox)` 这条**惰性 getter** 读 `ctx.cbox` —— 段末还没到 ⇒ `undefined`。原文里 `function` 声明是**提升**的，任何位置都可见 | 导出位置复刻原文的可见性窗口：**`function` 挂在段的最前面**（借提升）、**`const`/`class` 紧跟声明** |
| **②** | `createRoundBox({ edge })` 里的 `edge` 拿到 `undefined` | `checker.getSymbolAtLocation(简写属性的 name)` 返回的是 **`ShorthandPropertyAssignment` 节点自己**的属性符号（`declName` 就是它自己），**不是**被引用的变量 ⇒ 改写被静默跳过。5 处真漏网全在 `createRoundBox` / `createSolid` 的参数对象里 | 改用 `checker.getShorthandAssignmentValueSymbol()`；`--check` 专门检查这一形态 |
| **③** | 段标记与段导出**错位**，段边界随之算错 | 同一偏移上的两次**零长插入**，在"从后往前应用"时会按**后应用者在前**落位 | 段标记与函数导出**合成同一个 edit** |
| **④** | `ctx.mqCoarse = mqCoarse; mqFine = mqFine;` —— 给 `const` 赋值（严格模式直接 TypeError） | 导出行的生成只给**第一个**名字加了 `ctx.` 前缀 | 每个名字各自带前缀；`--check` 逐条重算 |
| **⑤** | `--move` 把 `document` / `Math` 报成"搬出去以后没人给" | `checker` 对 `document` 解析到 `lib.dom.d.ts` 里的声明，其偏移落在 `monolith.js` 之外 | 只认**本文件内**的声明（`d.getSourceFile() === sf`） |

> **共同的教训**：这一层改动里，`tsc --noEmit` 与 `astro build` **全程零错误**，
> 而页面完全起不来。拦住它的是**像素回归**（它把"页面崩了"报成"等待超时"）——
> 这正是 [`VERSIONING-QA.md`](../VERSIONING-QA.md) 里反复出现的那条：
> **门禁必须能表达问题本身，否则它只是问题的影子**。

### 2.4 一处门禁判据的适配（`verify-f06`）

`verify-f06.mjs` 有一条按**字面**匹配 `legacy/monolith.js` 的断言：

```js
check('数据源是 three 的 renderer.info', /const r = renderer\.info;/.test(cur))
```

段切片把 `renderer` 变成了 `ctx.renderer`（它现在住在 `core3d` 段），于是这条字面匹配失败。
**判据的语义没有变**（"渲染统计的数据源必须是 three 的 `renderer.info`"），变的只是名字怎么解析 ——
所以按同样语义补上可选的 `ctx.` 前缀，而**不是**放宽或删除它：

```js
check('数据源是 three 的 renderer.info', /const r = (?:ctx\.)?renderer\.info;/.test(cur))
```

同一条 `check` 的下一行（`scene.traverse`）一并做了相同处理。

> ★ 这是 `J4` 后续任务的**通用注意点**：凡是对 `legacy/monolith.js` 做**字面匹配**的校验脚本，
> 都会在段切片后遇到同一件事。适配时只改"名字的形态"，**不改判据的强度** ——
> 一旦为了让它变绿而放松阈值，就回到了"判据只是问题的影子"那条老路。

`J4.1` 是**阶段内任务**，规范 §5.3 的「五处状态副本」是**阶段收尾**动作。但 §5.4 同时规定
「**禁止**让一个已打出 `-dev.N` 的阶段停留在「⬜ 计划」」—— 本任务打出了 `v0.4.0-dev.1`，
因此把 `J4` 从 ⬜ 计划 改为 🟡 开发中（写最新 `dev.N`）已在本次一并完成，五处见
[`BuildPlaning/01`](../BuildPlaning/01-完善路线图.md) 与 [`VERSIONING.md`](../VERSIONING.md) §5.4。

### 5.4 已知的、留给后续的风险

1. **`ctx` 是 `Object.create(null)`**：780 个键会让 V8 落到字典模式，属性访问比局部变量慢。
   本次**没有做性能优化**（段内 `const` 仍保留原名，只有跨段引用才走 `ctx`），
   渲染统计全项 +0.0% 说明当前代价可接受；真要优化留给 `J8`（按 `tier` 裁剪）。
2. **段内 `const` 的导出是"值快照"**：对对象是引用共享（正确），对基本类型是复制。
   `const` 本来就不重新赋值，所以语义等价 —— 但 `let` **必须**走 `ctx`，这条不能破。
3. **段表里的 `hint` 是相对"原始 monolith"的行号**：`--ctxify` 之后行号已变，
   `--report` 会失真。段边界从此刻起**以 `[J4:seg …]` 标记为准**，`--move` 用的也是标记。

## 6. 结论

`J4.1` 交付的不是"搬了 64 行 ui 代码"，而是**让 `J4` 剩下的 6100 行变得可以安全搬运的那套机制**：

- 21 段段表（段序 = 执行序），`monolith.js` 的**唯一写者**，以及 `--check` 这条**逐引用**判据；
- 五个"只有跑起来才会发现"的坑，每个都留了判据 —— 它们全都**通过了 `tsc` 与 `build`**，
  只被像素回归拦下；这再次说明：**判据的粒度决定它能不能发现问题**；
- 像素 **3/3 逐字节相同**、冒烟 **32/32**、探针 **7/7**、单元 **182/182（+3）** ——
  段切片这一步对画面**零影响**，与 `J3` 的判据同级。
