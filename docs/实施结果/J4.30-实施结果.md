## 1. 按配方做了什么（1 个新文件 + 4 处改动）

| 文件 | 动作 |
|---|---|
| `world/floor2/magicClock.js` | **新增**：`state`（`clockLastKey`）+ `build`（canvas / 表盘 / 三个装饰八面体）+ `update`（`paintClock`） |
| `world/floor2/install.js` | `const clockCanvas …` 起的那一段 → `installProp(magicClock)`；**删** `ctx.clockHand` / `ctx.drawClock` 两个段导出分句；`updateNewDecor()` 第一行 `drawClock();` → `clockApi.tick(dt, time)`；新增 import |
| `world/layout.js` | **新增** `CLOCK_X = -2.95`（原段内硬编码，按 `N9` 落 layout；**数值一个没改**） |

### 1.1 ★ 唯一的关键偏离：**跳过 `colEdge` 那 6 行**

`18.12` 分区标题行的**后 6 行**是一个**共享工具** `colEdge(g, col, th)`，被**四处**使用
（`mirror.js` / `junkBoxes.js` / `picture.js` 的 `build` 各 1 处 + 时钟自己 3 处）。
整段搬会让那三件在**装配时立刻 `ReferenceError`**（启动崩，不是像素差异）。

⇒ 本件区间**从 `const clockCanvas` 那一行开始**，`colEdge` **原地留在 `install.js`**
（`ctx.colEdge` 导出**必须保留**）。代价是 `install.js` 里留下一段
「标题 + 分隔线 + `colEdge` + 空行」的碎片 —— 与 `J4.15` §3 的配方完全一致。

### 1.2 又一处段导出的悬空引用（**第四次**同类，主动拦下）

`install.js` 的段导出里有 `ctx.clockHand = clockHand; ctx.drawClock = drawClock;` ——
靠**函数声明提升**引用本段局部函数。两个函数随时钟搬走 ⇒ 该分句会在装配期抛
`ReferenceError`。全局搜索确认**无外部读者**后删除（保留同行的 `ctx.colEdge`、
`ctx.updateNewDecor`、`ctx.regWobble` 等）。

> 前三次：`J4.20` 的 `startQuill`、`J4.26` 的 `makeCup`、`J4.28` 的 `makeCushion`。
> 「搬物件前先查段导出清单」这个动作已连续四次拦下同类故障。

### 1.3 一处必要的结构改写（有理由）

原实现里 `clockHand(ang, len, w, col)` 是**闭包捕获 `cctx`** 的局部函数。
本件把它与 `paintClock` 一起放到**模块作用域**，**显式接收 canvas 上下文**：
`clockHand(c, ang, …)` / `paintClock(c, tex, st)` —— 这样 `build` 与 `update` 才能共用它们
（`cctx` / `clockTex` 经 `parts` 交出）。**函数体逐字未改**，只多了第一个参数。

## 3. ★ 捷径实验（`J4.15` §2.5 的"下一步第一个实验"）

`J4.15` §2.5 原文建议：

> 下一轮第一个实验应当是**把 `paintClock` 的调用从 `build` 里移到 `update` 里**
> （即装配期不画、只在第一帧画）—— 它一次性区分「装配期绘制的环境问题」与「绘制内容问题」。

### 3.1 做法与结果

注释掉 `build` 末尾那一次 `paintClock(cctx, clockTex, state)`，重建后跑像素回归：

```
✓ default-fixed   sha256 相同（182422 B）
✓ floor1-indoor   sha256 相同（117059 B）
✓ floor2-desk     sha256 相同（138670 B）
```

### 3.2 结论

**去掉装配期绘制后画面丝毫不变** ⇒ 两条推论：

1. **`update` 通路能在第一帧独立把表盘画对** —— 它不依赖装配期那一次绘制；
2. 因此 `J4.15` 当年的 184 像素**不是"绘制内容"问题**（内容本身是对的，
   否则去掉装配期绘制后表盘会整片空白、判据必红）。

⇒ 反推出 `J4.15` 当年的失败**只能**落在"它那版实现里 `update` 通路没有把画补上"这一类，
即它 §2.4 未排除的**假设 3（`state` 对象的传递路径）**所在的区间 ——
而本次实现里 `parts.cctx` / `state` / `updateNewDecor` 三处替换**全部验证有效**（实验 1 + 画面零差异）。

### 3.3 ⚠️ 为什么**不**把根因归到某一行

`J4.15`（`v0.4.0-dev.14`）到本次（`v0.4.0-dev.28`）之间 `dev` 上新增了 **14 个任务**的改动
（`J4.16` 起的工具层清理、`J4.17` 状态副本、`J4.18`–`J4.29` 的物件与光源搬迁……），
**没有任何手段**能回溯性地判定"当年那 184 像素具体由哪一行引起"。

⇒ 本任务的结论**严格限定**为：**按同一配方在当前代码基线上重做，像素零差异**；
并**附带**给出了 `J4.15` §2.5 那个实验的答案（§3.2）。这是可复现、可复核的表述。

## 4. `N3` 例外的记账：`world → app` 的具体实现依赖

`paintClock` 必须读 `clock.mode` / `clock.frozenDateMs` 才能决定"此刻显示几点" ——
这是**相机外的真实墙上时间**（`new Date()`），**不是**动画时间，所以 `floor2/rubik.js`
那套 `s.now` 的替身在这里**不适用**。

`J4.15` §3 给了两条路，本次采用 **②「由物件 `import { clock } from '../../app/clock.js'`」**：

| 路 | 取舍 |
|---|---|
| ① 给 `propCtx` 加 `propTool('clock', () => clock)` | 改动落在段切片的装配器清单里，多一个"全局可用"的隐式通道；后搬的物件会**看不出**自己依赖了时钟 |
| **② `import { clock } from '../../app/clock.js'`（本次采用）** | 依赖**显式可见**（在文件头的 import 里一目了然）；`app/clock.js` 是**核心模块**（无场景依赖、与 `defineProp` 同层），且 `app/installProp.js` 早已为"契约定义"开过同类先例（依赖 `systems/interaction/types.js`） |

⇒ 这是一次**按不变量 `N3` 记账的例外**：`world/**` 直接依赖 `app/**` 的**具体实现**。
账目写在**本文件 + 模块文件头**两处（`magicClock.js` 的「`world → app` 的具体实现依赖」一节）。
