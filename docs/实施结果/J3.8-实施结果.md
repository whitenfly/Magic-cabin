### ★ 为什么是**次版本位**而不是补丁位

§12.3 的判定标准是「**是否改变任何规则含义**」：

| 本次改动 | 性质 | 版本位 |
|---|---|---|
| §5.3 清单"四处 → 五处" | **补漏**（清单本来就与实际不符） | 补丁位 |
| §5.2 明确「冲突是预期的 + 处理方式」 | **新增操作步骤** | **次版本位** |
| §5.2 新增「发布提交不回流 `dev`」 | **新增规则**（旧规范对此完全空白） | **次版本位** |

**⇒ 取较高者：`1.1.0`**（次版本位 = 新增规则，不改既有规则）。

> 保守升位的好处：万一"不回流"这条判断将来需要改，改动发生在 `1.x` 序列内，不会让引用 `SPEC-1.0.x` 的地方失效。

## 2 · 依据：`v0.3.0` 发布时的实测证据

本次修订**不是推测**，而是 `v0.3.0` 发布那一刻的真实暴露：

**① 冲突实测**：

```
node scripts/release.mjs exec -- git merge --no-ff dev -m "release: v0.3.0（J3 物件模块化）"
→ Auto-merging package.json
→ CONFLICT (content): Merge conflict in package.json
     HEAD (main): 0.2.5          ← v0.2.5 发布时改的
     dev        : 0.3.0-dev.7
```

**② `main` 独有提交实测**（`git log --oneline dev..main`）：

```
1cee7ae release: v0.3.0（J3 物件模块化）        ← 本次
69e1fcc chore(release): v0.2.5
a4d4d3a release: v0.2.5（J2.5 配置编排层）
2fde4aa release: v0.2.0（J2 小屋核心设施）
```

**4 个** —— 而旧规范对此**完全没有说明**，每次发布只能现场判断。

**③ 冲突的处理反而简化了流程**：直接在冲突处写成 `0.3.0`（正式号）⇒ merge commit 同时完成"合并"与"去后缀" ⇒ **省掉了 `chore(release)`**。这正是 §5.2 新写法的由来。
