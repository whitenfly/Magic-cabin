# J2.2 实施结果 —— 材质与光照 shader 参数化

> 任务来源：[`BuildPlaning/01-完善路线图.md`](../BuildPlaning/01-完善路线图.md) §3 的 `J2.2`
> （落点 `cabin/core/materials/*`）。
> 版本管理：[`VERSIONING.md`](../VERSIONING.md) §3。

---

## 1. 做了什么

把全局光照材质与线材质从 `legacy/monolith.js` 提取为 5 个模块：

| 模块 | 内容 | 来源 |
|---|---|---|
| `core/materials/fill.vert.glsl.js` | FILL 顶点着色器（386 字符） | monolith 的 `vertexShader` |
| `core/materials/fill.frag.glsl.js` | FILL 片元着色器（5326 字符，含三段光照） | monolith 的 `fragmentShader` |
| `core/materials/FillMaterial.js` | `createFillMaterial()` + `POINT_LIGHT_SLOTS` | monolith 的 `FILL` unison 块 + 材质参数 |
| `core/materials/litMaterial.js` | `createLitMaterialFactory(FILL)` → `LITMAT` | monolith 的 `LITMAT` |
| `core/materials/lineMaterials.js` | `createLineMaterials()` → `MAT` / `DASHMAT` / `IN_MAT` | monolith 原 75–77 |

**monolith 净减 134 行**（`-153 / +19`），8900 → 8766 行量级。

## 2. ★ 关键决定：shader 用**脚本逐字节提取**，不手抄

`FILL` 块有 135 行，其中两段 GLSL 共 5700 字符。手抄的风险是**一个空格或一位小数**
就改变画面，而像素回归只会说"不一样"，不会说"错在哪个 uniform"。

因此本次写了两个一次性脚本（放在 `scripts/oneoff/`，与项目既有约定一致）：

| 脚本 | 作用 |
|---|---|
| `_j22-extract.mjs` | 按 `key: \`` 与花括号配对定位，把 `vertexShader` / `fragmentShader` / `uniforms` 块**原样**写进模块；打印字符数以便核对 |
| `_j22-rewrite.mjs` | 按**内容边界**（而非行号）把 monolith 里的三块替换为解构，跑完打印替换字符数（实测 294 + 8240） |

两个脚本都是**幂等**的（第二次运行会检测并跳过），且当前保留在仓库里作为"这次是怎么搬的"的证据。

## 3. 为什么**没有**做"炉火 / 吊灯 / 点光三段合一"

路线图的 `J2.2` 一行写着「炉火/吊灯/点光三段重复逻辑合一」。本次**只做了参数化，没有做 GLSL 内部重构**，
理由如下（属「偏差留痕」，不是遗漏）：

1. **原则 2「搬迁期零优化」**明确写着"搬运代码时禁止顺手改好看、改数值、换算法；优化集中在 `J8`"。
   把三段重复代码抽成 GLSL 函数属于**换算法结构**。
2. **判据不允许**：`J2` 的 DoD 是像素逐字节零差异。GLSL 函数内联后浮点运算顺序可能变化，
   `J2` 阶段无法区分"重构引入的差异"与"真回归"。
3. **真正的价值点在 `J2.3`**：注册式光源要的是**数据驱动**（谁注册谁生效、按重要性裁剪），
   而不是把三段代码合并成一段。`J2.2` 已经把这三段的**全部落点收敛到一个模块**（uniforms 与
   shader 现在同属 `core/materials/`），`J2.3` 改起来不再需要翻 monolith，`J8` 若要合并函数也只动一个文件。

**给 `J2.3` 的接口已经就位**：`POINT_LIGHT_SLOTS`（= 8）与 shader 的 `uPtPos[8]` / `uPtCol[8]` /
`uPtCfg[8]` / `uPtCount` 是同一份真相的两侧。

## 5. 新增测试：跨文件一致性（4 项）

`tests/unit/materials.test.mjs`：

| 测试 | 守什么 |
|---|---|
| 顶点着色器交出 `vWorldPos` / `vWorldNormal` | 光照在世界空间算的前提 |
| 片元着色器保留三段光照锚点 | 提取时**没有丢段**（炉火 / 吊灯 / 点光源） |
| `POINT_LIGHT_SLOTS` 与 `uPtPos[8]` 等声明一致 | JS 侧与 GLSL 侧不脱节 |
| 片元着色器的 `for (int i = 0; i < N; i++)` 上界 = `POINT_LIGHT_SLOTS` | 循环上界改了而 JS 侧没跟上的静默错乱 |

> 这 4 项是**给 `J2.3` 准备的安全网**：`LightField` 要在这两侧之间填槽位，
> 一旦一方改了另一方没跟上，画面会静默错乱（多余槽位不生效或着色器编译失败）。

## 7. 遗留与交接

| 项 | 留给谁 | 说明 |
|---|---|---|
| 三段光照的 GLSL 函数化 | `J8` | 见 §3；落点已收敛到 `fill.frag.glsl.js` 一个文件 |
| `uPtPos/uPtCol/uPtCfg` 的**填充** | `J2.3` | 现在仍由 monolith 在 `tickOnce()` 里硬编码 8 个槽位（`PP[0]…PP[7]`），`LightField` 要接管 |
| `WIN_GLASS` / `WIN_GLASS_UP` | `J3` | 玻璃材质属 `world/house/windows.js`，本次未动 |
| `LITMAT` 造出的几百个彩色材质 | `J3` | 它们的 `uTint` 由各物件决定；搬迁时保持"共享 uniform、只换 tint"的用法（性能基线靠它） |

## 8. 一句话总结

**5700 字符的 GLSL 与 1565 字符的 uniforms 被脚本逐字节搬进模块，画面未变一个像素** ——
`J2.2` 的产出不是"更漂亮的 shader"，而是把"改一处光照全场生效"这件事
从"改 monolith 里 4 个地方"变成"在一个文件里改一次"，为 `J2.3` 的注册式光源铺好接口。
