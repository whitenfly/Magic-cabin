## 0. 一句话结论

**8 个 `lightField.register` 从 `systems/weather/WeatherSystem.js` 移回 `world/lights.js`** ——
光照不再挂在天气模块上。注册内容**一字未改、次序未动**，像素 **3/3 逐字节相同**。

同时说清楚一件容易被误解的事：**C6 的原始收益已经被 `J4.7` 吸收了**（见 §1）。

## 1. C6 的"原目标"与"实际剩下的"

路线图 C6 写的是「**光源注册按原槽序批量进行**」，解锁条件是「光源槽序（shader 里的 `float(i)` 相位）可控」，
**原本要解锁的是** `J3` §3② 那 6 件含光源物件（水晶球 / 暖桌 / 蜡烛 / 吊挂木灯 / 大坩埚 / 月光盆栽）。

`J4.7` 之后这个目标**已经不是问题**了：那 6 件连同整个 `floor1` / `floor2` **段**一起被搬进了模块，
它们早就"搬完了" —— 不需要 C6 来解锁。

**但 C6 并没有变成空任务**，因为调研发现了一件更实的事：

| | 事实 |
|---|---|
| **归属错位** | 8 个 `lightField.register` 住在 `systems/weather/WeatherSystem.js` 里 —— **光照与天气毫无关系** |
| **成因** | `J4.7` 的段切片按**行区间**切：那 8 行在原 `monolith.js` 的 `L5417–L5432`，正好落进 `weather` 段的区间 |
| **危害** | 想动光照的人不会去天气模块里找；而 `WeatherSystem.js` 的职责被稀释成一个"什么都装"的文件 |

所以 `J4.10` 交付的是**归属修正** + 把"槽序不可动"这条硬约束**写进代码注释**（而不是留在搬迁者的记忆里）。

## 2. 做了什么

### 2.1 迁移

| | |
|---|---|
| 搬走 | `WeatherSystem.js` L585–L601（17 行：`lightField` 创建 + 8 个 `register` + `registry.registerLight`） |
| 落到 | **`src/cabin/world/lights.js`**（新增，`installWorldLights(ctx, app)`） |
| 调用点 | `installCabin.js` 里**紧随 `installSceneCore`**（需要 `ctx.FILL` 已就绪） |
| `WeatherSystem.js` | 605 → **588 行**（−17） |

### 2.2 ★ 只搬"注册"，不搬"强度的生产者"

`strength` 全是**惰性闭包**（`() => ctx.ptLantern`、`(time) => ctx.ptKot * (0.82 + 0.18 * …)` …），
由 `lightField.update()` **每帧**调用。所以：

- **搬**的是"注册这件事"（初始化动作，与帧顺序无关）；
- **不搬**的是那几个状态量（`ptLantern` / `ptKot` / `ptMc` / `ptCb` / `candleP` / `magicP` / `ptPlant`）——
  它们是"环境"算出来的，**仍住在 `WeatherSystem.js`**，`world/lights.js` 经 `ctx.*` 惰性读取。

这条切法把"光照"与"环境"的边界划在**正确的地方**：谁算值 vs 谁消费值。

### 2.3 ★ 硬约束：槽序 = 注册顺序（写进注释，不只写在文档里）

`FILL` shader 的闪烁相位含 `float(i)` ⇒ 第 i 个 `register` 就是第 i 个槽位。
所以 `lights.js` 的文件头用一整节写明：

> **顺序一换画面就变**（像素回归会当场抓住）。8 行的**次序不可调整**，
> 位置/颜色/半径/`yMin`/`yMax` 也必须逐字保持。

**验证手段**：像素回归 3/3 逐字节相同 + `perf` 渲染统计全项 +0.0%
（槽序若变，光照分布变化必然改变像素；而 `calls`/`triangles` 不变说明场景构成未动）。

### 2.4 为什么**不**在这一个任务里顺手做「预留槽位」通道

报告级别的想法是：给 `LightField` 加"预留槽位"，让物件将来能用 `lights()` 声明自己的光源
（而不至于在自己位置注册就变成槽位 0）。**本次没做**，理由两条：

1. **没有对象**：那 6 件含光源物件现在是**段形态**（在 `floor1/install.js` / `floor2/install.js` 里），
   不是 `defineProp` —— 没有 `lights()` 可声明。
2. **风险/收益比不佳**：改 `LightField` 的槽位分配 = 动画面，而收益是"将来更顺手"。

⇒ 记入遗留（§5），等"物件升格为 `defineProp`"那件事真的发生时再做。

### 2.5 ★ 同类债务（本次**刻意不动**）

`J4.9` 调研时发现的另一处错位：**「花 / 路牌材质 / 萤火虫不透明度」的每帧分支也住在
`WeatherSystem.js` 里**（`ctx.flowerMats` / `ctx.signSideMat` / `ctx.ffOpacity` …）。

它和本任务是**同一类**问题（段切片按行切的副产物），但**处置不同**：

| | 光源注册（本任务） | 每帧分支（不动） |
|---|---|---|
| 性质 | **初始化**动作 | **每帧**动作 |
| 与帧顺序的关系 | 无关（只要能注册就能注册） | **强相关** —— 它们依赖 `_amb` 先算出来 |
| 搬动的后果 | 无（像素可证） | **改变帧顺序 = 改变画面** |

所以它们必须**连同 `UpdateScheduler` 的登记顺序一起设计**才算干净 —— 那是另一件事，
记入遗留。

## 5. 遗留

| 项 | 说明 |
|---|---|
| **每帧分支的归属错位** | 花 / 路牌材质 / 萤火虫不透明度住在 `WeatherSystem.js`（见 §2.5）。搬它们必须**连同 `UpdateScheduler` 的登记顺序一起设计**（它们依赖 `_amb` 先算出来）—— 这是 `J4` 债务清单里**唯一一条被判定为"不该在这个阶段硬做"**的 |
| **`LightField` 的"预留槽位"通道** | 让物件能用 `lights()` 声明光源而不打乱槽序。**没有对象**（那 6 件含光源物件还是段形态，不是 `defineProp`），见 §2.4 |
| **物件升格为 `defineProp`** | `floor1/install.js` / `floor2/install.js` 里的 35 件装配点仍是"段形态"。升格是独立的一件事（`J3` 的 `defineProp` 契约还在，只是这批物件没走它） |
| **C3 `aim` 通路收进统一契约** | 最后一个缺口，`J4.11` |

## 7. 结论

C6 最初的样子是「让光源注册可批量、可控槽序」；到 `J4.10` 真正动手时，
它的**原收益已经被 `J4.7` 顺手吸收**（那 6 件物件随段搬完了），
剩下的是一件更朴素但更实的事：**把光照注册从天气模块里挪出来**。

这一轮最值得记的不是那 17 行，而是**划清了一条切分边界**：

- 搬 **"谁注册"**（初始化）—— 安全，像素可证；
- 不搬 **"谁算值"**（每帧）—— 那会动帧顺序，必须与调度器一起设计。

`J4.9` 发现的"每帧分支归属错位"就是踩在这条线的另一侧，所以它被**刻意留下**，
并写清楚了留下的理由。
