## 1. 本件的核心：两处不相邻的 `tick` 怎么合并

### 1.1 问题

`app/scene/FrameBody.js` 里原本是**三行不相邻**的调用（原 monolith `tickOnce()` 的行号保留在注释里）：

| 原行号 | 调用 | 归属 |
|---|---|---|
| L785 | `ctx.updateBook(time, dt);` | **本件** |
| L788 | `ctx.updateCal(dt);` → `prop/calendar` | 台历（`J3`，**不属于本件**） |
| L789 | `ctx.updateGlyphs(time, dt);` | **本件** |

一件物件只能有一个 `update` ⇒ 必须合并。`J4.35` 的施工图 §4 给了两条候选路线：

- **路线 ①（采用）**：登记在**靠前**的那一处（原 `updateBook` 的位置），`update` 内部先跑
  `updateBook` 段、再跑 `updateGlyphs` 段；
- 路线 ②：登记在靠后那一处 —— 会让状态机整体推迟一帧，**否决**。

### 1.2 为什么路线 ① 是等价的（施工图 §4 的判据）

合并两个帧任务的判据（`docs/VERSIONING.md` / `J4` 系列既有纪律）：

> 等价 ⟺ ① 两者在 `FrameBody` 里**相邻**，或
> ② 前者是一阶低通、且**两者之间没有读者 / 写者**（须 grep 证实）；
> 且合并后的位置仍**早于** `lightField.update`（`frame/97`）。

本件走的是判据 ②，**两段之间夹着的 `updateCal(dt)` 就是那个"中间任务"**：

| 检查项 | 结论 |
|---|---|
| `updateCal` 是否读 `glyphObjs` / `bookG` / `bookState`？ | **否** —— 它只碰 `calPages` / 台历自己的 `state` |
| `updateCal` 是否写上述对象？ | **否** |
| `updateBook` 段与 `updateGlyphs` 段之间的先后 | **与原实现一字不差**（先 `updateBook` 后 `updateGlyphs`） |
| 合并后位置是否早于 `frame/97`（`lightField.update`）？ | **是**（原 L785，远早于 L97 段） |

⇒ 唯一的实际变化是 **`updateGlyphs` 提前了一帧**（从 `updateCal` 之后挪到之前），
而它与台历无任何交互 ⇒ 不影响画面。**已由 3/3 机位零差异实证。**

### 1.3 ⚠️ 施工图点出的"唯一需要实证的地方"

施工图 §4 ③ 特别标注：

> "本帧新生成的符文会不会在本帧就被老化一次？"

**答案是：在原实现里本来就会** —— `updateBook`（可能 `spawnGlyphs`）**就在** `updateGlyphs` 之前。
本件**保持了这个顺序**，因此新旧行为完全一致，不是"新增风险"。画面零差异即为实证。

## 2. `SKIP` 记的唯一硬阻塞：`camera`

`floor2-magic-book.SKIP.md` §2 把这一件判为"拆不干净"，理由是：

```js
g.m.quaternion.copy(camera.quaternion);   // ← 符文面片永远朝向相机（billboard）
```

`camera` 当年是 monolith IIFE 里的局部 `const`，**不在 `propCtx` 的可用键里**
⇒ 搬进模块会立刻 `ReferenceError`，而它在**每帧**执行（不是只在 `build` 里）。

`SKIP` §3 给的第 1 条解锁路径是"给 `propCtx` 补 `camera`"——
**`J4.8`（路线图 J4 的缺口 C1）已照此办理**（`app/scene/PropInstaller.js` L67）：
`propTool('camera', () => ctx.camera)`。

⇒ **本件直接从装配环境解构 `camera`，零新增工具。**

`SKIP` §2 记的**第二处麻烦**（`glyphObjs` / `glyphGeoShared` / `glyphTexCache` / `bookGlyphT`
被 `spawnGlyphs` 与 `updateGlyphs` 两边共用）**随合并自动消失** —— 它们在同一个 `build` 闭包里，
经 `parts` 交出，`update` 内部两段共用同一份。

`updateGlyphs` 与 `updateBook` 共用的 `smooth` 也已由 **`J4.31`** 提取到 `core/math/easing.js`
（`propTool('smooth', …)`），本件按原名使用。

## 3. `clock.now` → `s.now`

原 `regMagic` 回调里写 `s.t0 = clock.now`。本件改为 `s.t0 = s.now`，其中 `s.now` 由
`update` 的第一行 `s.now = time;` 写入（`tickOnce()` 开头 `const time = clock.now;`）。

**为什么二者恒等**：`clock.tick()` 只在 `tickOnce()` 内推进；DOM 事件（点击）在
**两次 `tickOnce()` 之间**执行，此时 `clock.now` 自上次 tick 后**未被改动**
⇒ 事件处理器里读到的 `clock.now` **就是**上一帧写入的 `s.now`。

这与 `floor2/rubik.js` / `floor2/witchHat.js` 的处置**同一手法**（`J4.30` 起沿用）。

## 4. ⚠️ 段导出清单的第一次删项（4 项）

`floor2/install.js` 顶部有一行"段导出"：

```js
ctx.makeCandleGlow = makeCandleGlow; ctx.getGlyphTex = getGlyphTex; ctx.spawnGlyphs = spawnGlyphs;
ctx.updateGlyphs = updateGlyphs; ctx.updateBook = updateBook; ctx.glowBall = glowBall;
```

整段搬走后，后 4 项（`getGlyphTex` / `spawnGlyphs` / `updateGlyphs` / `updateBook`）
成为**指向已搬走实现的悬空导出**。这正是本项目已经犯过 **5 次**的一类错误
（`ctx.startQuill` / `ctx.makeCup` / `ctx.makeCushion` / `ctx.clockHand`+`ctx.drawClock` /
`ctx.hash01`+`ctx.jitterGeo` / `ctx.makeChair` —— 症状是 `tsc` 与 `astro build` 全绿，
但**页面启动即 `ReferenceError`**，因为函数提升让"未定义的名字"逃过了静态检查）。

**⇒ 删项前先 grep 全仓**，证据如下：

| 名字 | 读者 |
|---|---|
| `ctx.updateBook` | 仅 `FrameBody.js` L492（**本件接管**） |
| `ctx.updateGlyphs` | 仅 `FrameBody.js` L502（**本件接管**） |
| `ctx.spawnGlyphs` / `ctx.getGlyphTex` | **无任何读者**（只在 `install.js` 段内自用） |
| `tests/**` | **零命中** |
| `scripts/**` | 仅命中 `scripts/oneoff/_j3-specs/*.json` 与 `*.SKIP.md` —— **历史调研文档，不是可执行代码** |

⇒ 4 项安全删除。保留 `makeCandleGlow` / `glowBall`（它们另有读者）。

**⇒ 段导出清单现在只剩 2 项**（`makeCandleGlow` / `glowBall`），
这一类"悬空导出"的存量债**首次下降**，不再是"每搬一件新增一例"。

### 5.1 `rng`（不变量 `N8`）

`spawnGlyphs(n)` 每个符文消耗 **11** 次 `runtimeRng()`（符号 1、颜色 1、位置 3、速度 2
共 7 次 —— 即 `SKIP` §4 记的 "4 + 3" —— 另加 `life` / `ph` / `rs` 各 1）。
`updateGlyphs` 每帧**不**消耗 `runtimeRng()`。
**调用位置与顺序一字未改**：`build` 段不消耗 rng，`spawnGlyphs` 仍在运行期由 `update` 调用。

### 5.2 锚点与几何同源（不变量 `N9`）

原实现里 `bookG.position` 与交互锚点是两处**独立字面量**。本件提为模块内常量
`BOOK_X = 2.58` / `BOOK_Z = -2.80`，`build` 与 `interactables().anchor` 同读一份
⇒ 今后改几何不会漏掉锚点（**数值零变化**）。

### 5.3 交互声明

原 `regMagic(bookG, onClick)` **只有两个参数**（无 label / radius）—— 它只设
`userData.onClick` 并 traverse 收集 Mesh。本件按 `defineProp` 规范补齐：
`label` 语义化 + `mode: 'both'`（`R1`）+ `hits: parts.bookG`（等价于原 traverse 的全部 Mesh）
+ `anchor` / `radius`（`proximity` 路径必需，与 `floor2/calendar.js` 同款）。

### 6.4 `verify-migration.mjs` 的 `regMagic(` 计数（**必须说明的细节**）

```
✓ regMagic(  64 → 32  → 已知差 -32
```

**本件删除了 1 处真实调用**（`ctx.regMagic(bookG, () => {…})`），按字面理解计数应变成
`31 / -33`；但它**仍显示 32 / -32**，原因是：

> 本件的注释里写了 `regMagic(bookG, …)` 这个**字面量**（§0 与本文件 §1 的风格），
> 而该计数项统计的是**文本出现次数**（脚本的 `stripComments` 只剥块注释、**不剥行注释**）——
> 一处新增字面量恰好抵消一处删除的真实调用。

**这不是漏检，而是与本项目 33 个已升格模块的既有惯例一致**（`bookshelf` / `calendar` /
`witchHat` / `teapot` … 的注释里**全都**写了 `regMagic(` 字面量，白名单 `-32` 记的正是
这种"净效果"）。为免误读，此处如实记下**真实调用数**：

| 口径 | 数量 |
|---|---|
| 当前 `src/**` 里**真实**的 `regMagic(…)` 调用（语句） | **17** 处：`props/cup.js` 1、`house/shell.js` 1、`floor2/chandelier.js` 1、`floor2/install.js` 9、`floor1/install.js` 4、`floor1/junkBoxes.js` 1 |
| 文本计数（含注释里的字面量） | **32** 处 |
| ⇒ 注释贡献 | 15 处 |

**本件使真实调用数 −1**（仅此一项，其余 16 处属于尚未搬迁的物件）。
