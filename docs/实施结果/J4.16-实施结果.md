## 0. 一句话结论

`src/cabin/legacy/monolith.js` 在 `J4.7` 被删除后，**一批"一次性脚本"随之变成死代码** ——
它们仍然躺在 `scripts/oneoff/` 里，跑起来只会报文件不存在。现在它们被移入
**`scripts/oneoff/archive/`**（27 个文件），`README.md` 重写了归档规则与"仍在使用"清单。

`.cache/` 里 4 个**一次性改引用脚本**（`_fix-refs.mjs` 等）已删除 ——
它们正是 `J4.12` §1 那次"批量改引用把生成模板当成引用方"事故的肇事者，
留着就有重演的可能。

**判据是确定性的，不凭印象**（见 §1）。

## 1. 归档判据（为什么是这 27 个，而不是"看着像一次性"的）

> **脚本在运行时引用 `src/cabin/legacy/monolith.js` ⇒ 该文件已于 `J4.7` 删除 ⇒ 必然失效。**

复现判据（一条命令即可复核）：

```bash
grep -rn "legacy/monolith" scripts/oneoff/*.mjs | grep -v "^\s*//" | grep -v "\* "
```

其中 5 个脚本**自带"整体退役"分支**（跑一下会打印一行提示后退出），
它们是这条判据的显式化 —— 例如 `_j4-apply.mjs`：

```js
// ★ J4.7：`legacy/monolith.js` 已删除 —— 本脚本（_j4-apply.mjs）**整体退役**。
if (!fs.existsSync(MONOLITH)) { console.log('  _j4-apply.mjs：legacy/monolith.js 已删除（J4.7）—— 本脚本整体退役'); process.exit(0) }
```

**反面做法（本次刻意没做）**：按"文件名的前缀看起来是某个阶段"来批量归档。
那会误伤 `_j4-segments.mjs`（**被单元测试 import**）与 `_j4-dev-sync.mjs`（**发布收尾要用**）——
两者都带 `_j4-` 前缀，但都还活着。这是 §1 判据存在的全部理由。

### 2.2 `.cache/` 的 4 个一次性改引用脚本 —— **删除**

| 文件 | 它当年干的事 |
|---|---|
| `_fix-refs.mjs` | 实施结果文档移入 `docs/实施结果/` 后批量修正全部引用（**按"文本住在哪个文件里"算相对路径**） |
| `_fix-inner-links.mjs` | 同批：`docs/实施结果/*.md` 自身的出向链接上移一层 |
| `_fix-exec.mjs` | 改造 `release.mjs`：撤掉 trace2，换成 `exec -- git …` 唯一入口 |

删它们不是洁癖：`J4.12` §1 那次真实事故（生成模板被当成引用方，链接全部算错）
**根因就是 `_fix-refs.mjs` 那条规则**，而 `J4.12` §6.2 明确写着
"同样的误判仍可能重演"。脚本留在本地就等于把复发条件留在本地。

`monolith.*.js` 快照（6 份，各约 540 KB）与 `_hist-mono.js`（1 MB 归档）**保留** ——
它们是 `legacy/monolith.js` 唯一的历史副本，属**档案**不是**工具**。

## 3. 为什么"暂留 11 个"而不是清光

§1 的判据只覆盖"引用已删文件"这一类。剩下 11 个（`_probe.mjs` / `_probe-kill.mjs` /
`_rng-digest-test.mjs` / `_scaffold.mjs` / `_v8-msg.mjs` / `_assemble.mjs` / `_doc.mjs` /
`_extract.mjs` / `_gen-html.mjs` / `_j04-explore.mjs` / `_j3-verify-b2.mjs`）
**不读 `monolith.js`**，所以它们不会立刻失效；但也**没有活跃引用**。

把它们一起归档**收益很小、风险却不小** —— `_scaffold.mjs` 的重跑警告（会重建已删除的
`src/data/` `src/domains/`）正是"脚本还在、但语义已过期"的典型。处置它们的正确方式是
**逐个人工判定**，而那需要一个明确的对象。

> 这条自律沿用 `J3` 的原话：**「拿不准就跳过 —— 质量高于数量」**。

## 6. 遗留与交接

1. **11 个"暂留"脚本**（§3）需要一次**人工判定**：要么归档，要么在 README 里写明"它还有用、用在哪"。
   这是 `README.md` 现在唯一没有答案的一节。
2. **`_j3-specs/*.SKIP.md` 不属"退役"** —— 它们是任务 D 的施工图。
   **任务 D 全部完成后**才可以考虑把它们一起归档（届时它们是"已完成"的档案）。
3. **`.cache/` 的 6 份 `monolith.*.js` 快照**（约 3.2 MB）保留为档案。
   若将来要清，必须先确认 `_hist-mono.js` 覆盖了同样的内容 ——
   它们是 `legacy/monolith.js` 唯一的历史副本。
4. **`scripts/verify-f06.mjs` 也带"整体退役"分支，但它住在 `scripts/`（不在 oneoff）** ——
   本次**不动**：它是 `_verify.mjs` 七件套的一员，删/移会让门禁清单与实现不一致（需要另做一致性核对）。
