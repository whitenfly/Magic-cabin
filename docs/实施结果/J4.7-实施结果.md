`legacy/monolith.js` 的最终形态：**208 行**（文件头 + import + `ctx` 创建 + 21 行调用）。

### 1.2 ★ `tickOnce()` → 102 个帧任务（这次不是纯剪切）

其余 20 段都是"代码一个字不改"，`tick` 段不行 —— 它必须**换一种存在形式**。
`_j4-tick-analyze.mjs` 先量出拆解的**唯一硬约束**：113 条顶层语句里只有 **11 个名字**
被后续语句引用（`time` / `dt` + 9 个"相邻两语句成对"的局部量）。于是：

| 情形 | 处理 |
|---|---|
| `const time = clock.now;` / `const dt = clock.dt;` | 删掉 —— 改由调度器作为 `(dt, time)` 参数传入 |
| 其余 9 个成对量（`pe`/`ee`/`pulse`/`partsOn`/…） | 切分时**把语句并进同一组**（声明的名字被后续引用就不切） |
| 组序 | **= 原语句顺序**（`rng` 调用顺序 / `scene.add` 顺序压在它上面） |

生成结果：**102 个帧任务**，登记顺序 = 原执行顺序。

### 1.3 ★ 25 处原地 `.tick(dt, time)` 的构成与清零

路线图 **C4** 记的"25 处"，实测构成是：

| 来源 | 处数 | 处置 |
|---|---|---|
| `tickOnce()` 里的 `<xxx>Api.tick(dt, time);` | **22** | 随 `tickOnce()` 一起变成**帧任务的函数体**（由调度器驱动） |
| `updateNewDecor()` 装饰循环里的 3 处（`pictureApi`/`mirrorApi`/`junkApi`） | **3** | **一个字没动** —— 它本来就是与主循环并列的独立刷新 |

`installProp()` 也把物件的 `update` 登记进同一个调度器，但**登记顺序是装配顺序**，
与帧顺序不同 —— 所以 `installFrameBody()` 先把自动登记的那些**撤销**（`scheduler.remove`），
再按原位置重登。为此 `PropInstaller.js` 多交出一个 `ctx.propInstalled`。

### 1.4 `animate()` 的最终形态

```js
function animate(t) {
    requestAnimationFrame(animate);
    clock.tick(t);
    ctx.tickOnce();
}
```

而 `tickOnce()` 就是调度骨架本身：

```js
function tickOnce() { app.scheduler.update(clock.dt, clock.now) }
```

**4 行 / 60 行上限**，更新顺序完全由 `UpdateScheduler` 的登记顺序决定。

### 1.5 ★ 四个只有跑起来才会发现的坑

| # | 现象 | 根因 | 判据 |
|---|---|---|---|
| **①** | `installProp 需要一份 defineProp 声明` | `import * as diningTable` —— **default import 被当成 namespace**，拿到的是模块命名空间对象而不是 `export default defineProp({…})`。floor1/floor2 的 35 件物件**全是**这种形态 | 生成 import 时按 `default` / `namespace` / `named` **三种形态分开** |
| **②** | `monolith.js` 变成 476 行、出现**两个** `installCabin` | `--move` 对**最后一个段**算 `bodyEnd` 越界（`lineStartOffset(src, lines.length + 1)` ⇒ `indexOf` 返回 -1 ⇒ 偏移回绕到 0）⇒ `src.slice(bodyEnd)` 变成整个文件 | 最后一个段用 `src.length`；段体提取时剥掉 IIFE 收尾 |
| **③** | `clock.tick is not a function` | `SceneLoop.js` 缺 `import { clock }` | ★ 见下方"诚实记录" |
| **④** | `.tick(dt, time)` 还有 23 处"没清零" | 判据把 `updateNewDecor()` 装饰循环的 3 处也算进去了 —— **判据本身把两件事混为一谈** | 单元测试显式区分"帧任务体"与"装饰循环" |

> ⚠️ **诚实记录（③）**：`--move=boot` 是在 ② 已经把 monolith 弄坏之后跑的
> （文件里有重复内容）。它生成的**段体是对的**（靠运气），但 import 一条都没补。
> 我是**事后手工补的 `clock`**，不是脚本给的。
> 所以 ② 的修复不是"顺手"：**它是 ③ 的必要条件**。这个故事记在这里，
> 是因为它说明了那条纪律：**工具坏了要先修工具，不能靠"这次结果看起来对"过关**。

### 2.6 ⚠️ 一处判据与规则的偏差（如实记录，**未擅自改规范**）

规范 §0.2「禁 1」的判定命令是：

```bash
git log --oneline --no-merges "$(git describe --tags --abbrev=0 dev)..dev"   # 应为空
```

**本任务收尾后它不是空的**（3 个提交）—— 但它们**没有一个是 `dev` 直提**，
全部经由 `--no-ff` 合并进入（§4⑥.1 的回填路径）。逐条溯源见
`scripts/oneoff/_j4-ancestry-check.mjs` 的输出。

**根因**：§4⑥.1 允许"回填"（独立分支 + `--no-ff` 合并、**不打新 tag**），
而 §0.2 的判据以"最新 tag"为界 —— 回填提交必然落在 tag **之后**且不带 tag，
于是那条字面命令**必然非空**。两条规则各自都成立，合起来互相冲突。

**准确的判据**（R1 的本意 —— §3.2 的"唯一判据"：任何改动都必须能追溯到某次 `--no-ff` 合并）：

```bash
node scripts/oneoff/_j4-ancestry-check.mjs
# 对每个非 merge 提交，检查"是否存在一个**后代** merge 把它引入"
```

本任务实测：**2/2 全部通过**（每个回填提交都能指到它的合并节点）。

> 按 **R14** 与 §12.5 第 4 条，**本任务不修改规范**（"发现规范有缺陷时：先按现行规范做完，
> 另开 `spec:` 任务修"）。此处只留事实 + 一条可执行的替代判据，供后续 `spec:` 任务参考。

> ### ⚠️ 更正（`J4.13` · SPEC-1.3.1）—— 本节上面的"替代判据"**已被证伪，不要使用**
>
> 上面那条"存在一个**后代** merge 把它引入"的判据（`_j4-ancestry-check.mjs`）经 **A/B 实测为恒真**，
> **检不出任何历史违规**：
>
> | 检验对象 | 该判据的输出 |
> |---|---|
> | `J3` 的 **6 个真直提**（判例 P1） | **6/6 全部判为「通过」** ✗（每个都报"后代 merge 数 = 30"） |
>
> **根因**：真直提之后的**任何** merge 都是它的后代 ⇒ `git rev-list --merges --ancestry-path <提交>..dev`
> **永远非空**，它只能抓到 `dev` 尖端那一个提交。
> 本节当时实测的"2/2 全部通过"是**空转**的结果，**不构成"判据守住了 R1"的证据**。
>
> **实际被采纳的修法**（SPEC-1.3.1）：给判定命令加上 **`--first-parent`**，按**分支拓扑**判定 ——
> 见 [`VERSIONING.md`](../VERSIONING.md) **§0.2** 的注与 [`VERSIONING-QA.md`](../VERSIONING-QA.md) **Q22**。
> 该脚本已随本次修订退役（`git rm`）。
>
> **教训**：判据必须做 A/B 实证 —— **先证明"它会红"，再宣称"它守住了"**（做法见 `J4.11` §3.1、`J4.12` §3.1）。

**给后续阶段的一句话**：现在**加一盏灯 / 加一个交互 / 加一个每帧动画**的动作是

| 想加什么 | 改几个文件 |
|---|---|
| 一件物件 | 1（`world/**/<名字>.js`）+ 1 行装配调用 |
| 一个每帧行为 | 1（该物件的 `update`）—— 由 `UpdateScheduler` 自动驱动 |
| 一个设置项 | 1（`config/*.config.js`）+ 1 个字段（面板自动出现控件） |

这正是 `J2` 立下的 DoD（"改动文件数 = 1"），到 `J4` 收尾时**三条都成立**了。

## 6. 结论

`J4` 交付的是一条**可复制的系统搬迁流水线**：
**段表**（唯一事实来源）→ **`--ctxify`**（一次机械变换，把 6105 行切成 21 段）→
**`--check`**（逐引用复算）→ **`--move=<段id>`**（纯剪切）→ **六项门禁**。

它用 6217 行、21 个段、1301 行的单段最大搬迁验证到**像素逐字节零差异**；
`J4.7` 再把最后 21 段一次搬完、把 719 行的 `tickOnce()` 换成 102 个等价帧任务，
并且 `legacy/` 整目录消失后**画面仍逐字节相同**。

而这一路最值钱的产出不是"搬了多少行"，是**九个只有跑起来才会发现的坑**
（`J4.1` 五个、`J4.3` 三个、`J4.7` 四个，其中简写属性与符号解析是同一个坑的多次复发）——
它们**全部通过了 `tsc` 与 `build`**，全部只被"页面起不来"或像素回归拦下。
