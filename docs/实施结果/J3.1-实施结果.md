> 上游阶段：[`J2.6`](./J2.6-实施结果.md)（统一交互系统）与 [`J3`](./J3-实施结果.md)（物件模块化）。

## 0. 一句话结论

用户实测报告的两个问题是**两次独立回归**，不是同一个 bug：

| 问题 | 引入阶段 | 根因 | 影响面 |
|---|---|---|---|
| **① 第一人称下左键点击全部失效** | `J2.6`（`5466a34`） | 契约字段改名（`act` → `activate`）后**漏改一处调用** | 所有视角下……不，是**第一人称**下的所有点击 |
| **② 部分物品点不动** | `J3`（`2fda17a`…`f00bf11`） | aim 桥"一件物件 = 一个 `root` = 一条 `onClick`" | 5 件物件的 8 个部件 + 1 件错位触发 |

两处**都不改变画面**，所以像素回归、冒烟、"每件物件有入口"的探针三条门禁全绿 ——
这正是它们能活到用户实测才被发现的原因（§4 逐条分析）。

## 1. 两处回归的定位

### 1.1 问题 ①：`aimHit.act()` —— 契约改名漏改一处（`J2.6`）

`J2.6` 之前，`aimRay()` 返回的是 `{ label, act }`：

```js
// J2.6 之前（monolith）
if (h.length) { const g = h[0].object.userData.hingeGroup;
  return { label: g.userData.aimLabel || '交互', act: () => toggleSpring(g) }; }
```

`J2.6` 把它换成了统一契约的 `makeTarget({ id, label, activate })`（对象上**只有 `activate`**），
同一个提交里 `doInteract()` 已正确改成 `interaction.activate(aimHit)` ——
但 `pointerup` 里的这一行**没跟着改**：

```js
// src/cabin/legacy/monolith.js（修复前）
if (viewMode === 'fp' && (isLocked() || IS_TOUCH)) { if (aimHit) aimHit.act(); return; }
```

⇒ 第一人称下每次左键点击都抛 `TypeError: aimHit.act is not a function`，什么都不发生。
`git log -L` 确认这一行自 first commit 起未变，是 `J2.6` 改名时漏掉的。

**附带缺陷（同一提交）**：`updateInteractHint()` 的 fp 分支丢掉了 `nearestInteract = null`
（搬迁前那行是 `aimHit = null; nearestInteract = null; …`），于是 fp 模式下
`nearestInteract` 冻结在"进入第一人称之前"的值。两个后果：

- E 键的入口条件是 `if (e.code === 'KeyE' && nearestInteract)` ⇒ 该值为 null 时**按 E 无反应**；
- 准星没对准任何东西时按 E，会掉到近距分支触发那个**陈旧目标**（"按 E 莫名其妙开了门"）。

> 用户实测确认了这一分层：**"左键点击全无法互动，但按 E 部分可互动"** ——
> 按 E 走的是 `doInteract()` 的 fp 分支（`interaction.activate(aimHit)`，改对了的那处）。

### 1.2 问题 ②：aim 桥只认一个 `root`（`J3`）

`installProp()` 的 ⑤.2 节原本是这样：

```js
const aimEntry = interactions.find((it) => it.mode !== 'proximity')   // ★ 只取第一条
if (aimEntry && root && root.isObject3D) {
  ud.onClick = () => aimEntry.onActivate()
  root.traverse((m) => { if (m.isMesh && !m.userData.noHit) meshes.push(m) })
  registry.registerMagic(root, meshes)      // 只有 root 及其子 Mesh 进命中集合
}
```

`J3` 之前每处 `regMagic(g, cb)` 是**各自独立**的（谁被点、谁的回调跑）。搬进 `defineProp` 后，
一件物件里的多条交互被压进一个 `root`，于是产生三个形态：

| 形态 | 机制 | 受害者 |
|---|---|---|
| **兄弟节点** | `root` 只是第一个部件，其余部件的 Mesh 根本不在 `magicMeshes` 里 | 餐桌的煎蛋盘 / 松饼盘、桌上右汤匙 / 筷子×2 / 碗叠、靠门的三脚圆凳、药剂瓶软木塞 |
| **覆盖** | `root` 是共同父节点 ⇒ `traverse()` 把**已注册过**的子 Mesh 的 `magicRoot` 一并改写 | 衣柜里的三件挂衣（`regWobble(hg)` 内部就是 `regMagic(hg, …)`）⇒ 点挂衣解析成**抽屉** |
| **死条目** | `mode: 'aim'` 的条目既不被近距认领（认领条件是 `mode !== 'aim'`），也不是"第一条" | 抽纸盒的"把摊在桌上的纸巾揉成团" |

同一形态还波及 `doorHangBar`：`root` 是共同横杆，所以点**风铃**实际触发的是**晴天娃娃**。

### 1.3 用户实测如何印证（四条预测全部命中）

| 实测 | 结论 |
|---|---|
| 第一人称准星对准**鱼盘**按 E 能动 | `root` = `plates[0]` ⇒ 第一个部件保留入口 |
| 第一人称准星对准**左汤匙**按 E 能跳 | `root` = `tableItems[0]` |
| 第一人称准星对准**北边凳子**按 E 能开 | `root` = `stools[0]` |
| 煎蛋盘 / 松饼盘 / 碗叠：准星打不中，但**第三人称靠近按 E 能触发** | 缺口**纯在 aim 侧**；proximity 认领、锚点、半径全部完好 |
| 各视角点衣架都只解析到"开 / 关抽屉" | `magicRoot` 被 `wardrobeG` 覆盖（形态②） |

## 2. 修了什么

### 2.1 A 类：止血（不碰契约、不碰画面）

| # | 位置 | 改动 |
|---|---|---|
| **A1** | `legacy/monolith.js` | `aimHit.act()` → `interaction.activate(aimHit)` —— 恢复第一人称左键点击 |
| **A2** | `legacy/monolith.js` | ①`updateInteractHint()` 的 fp 分支补回 `nearestInteract = null`；②`keydown` 的 E 键去掉 `&& nearestInteract` 前置（是否真有目标由 `doInteract()` 判定）⇒ 消除"幽灵交互"与状态依赖 |
| **A3** | `app/installProp.js` | root 兜底桥的 `traverse` 加两个排除：`!m.userData.magicRoot`（**不覆盖**已注册的 Mesh）与 `!claimed.has(m)`（不重复注册） |

### 2.2 B 类：逐条命中体（契约扩展，向后兼容）

**契约**（`systems/interaction/types.js`）：

```js
interactables: (s, { L, parts }) => [{
  id: 'long-table/spin-egg',
  label: '转一转餐桌上的煎蛋盘',
  mode: 'both',
  anchor: { x: L.DT_X + 0.85, z: L.DT_Z - 0.12 },
  radius: 1.2,
  hits: parts.egg,          // ★ J3.1：这一条自己的命中体
  onActivate: () => { parts.egg.userData.spinV = 9; },
}]
```

- `hits` 接受单个 `Object3D` 或数组；省略 = 沿用物件根（`J3` 的过渡形态，**已搬物件行为一字不变**）
- 装配器为**每条**带 `hits` 的条目建一个**代理根**（普通对象即可 ——
  `registerMagic()` 只把第一个参数写进 `mesh.userData.magicRoot`，不要求是 `Object3D`；
  造 `Group` 会改 `scene.children`，是像素回归的雷区）
- 新增契约工具 `wantsAim(it)`（`mode` 含 aim 即需要有入口），供两处诊断共用

**补了 `hits` 的物件（7 件、21 条交互）**：

| 物件 | 条目 | `hits` |
|---|---|---|
| `floor1/long-table` | 鱼盘 / 煎蛋盘 / 松饼盘 | `parts.fish` / `parts.egg` / `parts.pancakes` |
| `floor1/tableware` | 汤匙×2 / 筷子×2 / 碗叠 | 各自 `parts.*` |
| `floor1/stools` | 两只三脚圆凳 | `parts.stoolA` / `parts.stoolB` |
| `floor1/hang-bar` | 晴天娃娃 / **玻璃风铃** | `parts.sunPivot` / `parts.chimePivot` |
| `floor1/potion-bottle` | 拔软木塞 | `[parts.bottle, parts.cork]`（两处原 `regMagic` 的对象都还给这条） |
| `floor2/wardrobe` | 开 / 关抽屉 | `parts.drawer`（**收紧**到抽屉本体：柜体/层板/衣物不再是交互目标） |
| `floor2/tissue-box` | **把纸揉成团** | `parts.paper`（纸是独立挂 `scene` 的兄弟节点，只能自己交出来） |

> 顺带把 `tissueBox.js` 文件头那段"这条缺口应由 `J4` 收编"改成"已由 `J3.1` 还清" ——
> 它就是 `hits` 机制的直接受益者，不必再等 `J4`。

### 3.1 新增的测试（这是"第三次复发"的唯一防线）

**单元测试（`prop.test.mjs` +5）**：

| 测试 | 守什么 |
|---|---|
| ★ 每条 `hits` 各建一个代理根 ⇒ 点哪只盘转哪只（餐桌三只盘） | 复现形态①，断言三条回调各归各 |
| ★ root 兜底桥**不覆盖** build 里已注册过的 Mesh（衣柜挂衣 = `regWobble`） | 复现形态②，断言点挂衣跑的是晃动而非抽屉 |
| ★ 没给 `hits` 的多条目会被 `stats().aimMissing` **逐条**点出来 | **门禁判据本身**：`aimMissing` 必须为空 |
| `mode: 'aim'` 的条目给出 `hits` 就有入口（抽纸盒的纸巾） | 复现形态③ |
| `hits` 必须给 `Object3D` / 不能是空数组 | 契约校验在装配期 fail-fast |

**冒烟新增 S5.5（4 项）**：第一人称下 ①左键点击 ②按 E，都必须真的激活准星目标
（像素差分判据），并要求**全程无未捕获页面异常** —— 修复前①必然抛 `TypeError` 且无像素变化。
收尾显式还原 `pointerLockElement` 与视角，避免污染后续 S6/S7。

> 说明：无头环境里 `requestPointerLock()` 不一定成功，而第一人称的准星通路只在
> `isLocked()` 为真时生效。用例因此**声明**"当前已锁定"（`Object.defineProperty` 覆盖
> `document.pointerLockElement`），让被测代码走它真实的那条分支 —— 即用户实测时所处的状态。

**探针新增逐条判据**：`registry.stats().aimMissing` 必须为空。
旧判据（`magicPropIds` 覆盖已搬迁物件）的粒度是"每件物件"，只要一件物件有**一个**入口就算通过 ——
三个形态全部漏网。新判据的粒度是**每条 `Interactable`**：

```
✓ ★  搬迁物件的准星入口齐全（aim 桥生效）   → 26 件有准星入口
✓ ★★ 每条声明了 aim 的交互都有自己的命中体  → 35 条交互各有 aim 入口
```

### 3.2 性能：`readyMs` 超标是环境噪声（A/B 对照为证）

`perf.mjs --compare` 报 `readyMs 858 → 1308 (+52.4%)` 超阈值（+30%，参考项）。
为判断是否本次改动引入，做了 **A/B 对照**（同样环境下把改动 `git stash` 掉、重建、重测）：

| 指标 | 基线（未修复） | 含修复 | 判定 |
|---|---|---|---|
| `calls` / `triangles` / `geometries` / `textures` / `sceneObjects` | **全 +0.0%** | **全 +0.0%** | ✅ 无渲染负担 |
| `readyMs` | 858 → **1118 (+30.3%)** ❌ 同样超标 | 858 → 1308 (+52.4%) ❌ | 基线自己就超标 ⇒ **与本次改动无关** |
| `fps` | 4.15 → 3.13 (−24.6%) | 4.15 → **3.25 (−21.7%)** | 修后反而**更好**，与 `readyMs` 方向矛盾 ⇒ 噪声 |

环境为 `SwiftShader`（软件渲染，稳态 FPS 仅 3～4），`readyMs` 是**冷启动单轮**采样，
方差本就很大。结论：**本次改动零渲染影响、无性能回归**；`readyMs` 超标是当前环境的既有现象。

## 4. 为什么四条门禁全绿却仍漏了

| 门禁 | 盲区 |
|---|---|
| **像素回归** | 交互失效**完全不改变画面** —— 三机位逐字节相同。它对这两类回归**原理上无感** |
| **冒烟**（`J3` 时 28 项） | 点击类用例（S4 壁炉 / S6 书堆）全部发生在**固定视角**，走的是 `pointerup` 的另一条分支（`interaction.activate(clickTarget)`）——**恰好绕开了出错的 fp 分支**；E 键用例同样在固定视角 |
| **单元测试** | 有 `★ aim 桥` 测试，但用的是**单条** `interactables` 的物件 ⇒ 契约是"每件物件 ≥1 个入口"，测不到"每条交互都要有入口" |
| **交互探针** | 判据 `magicPropIds` 由 `installProp` **按 root 打标**且粒度是"每件物件"：`long-table` 只要有**鱼盘**一个入口就算通过，`wardrobe` 因 `root = wardrobeG` 也照样通过 |

**教训**：一条"能表达问题"的判据 > 十条"看起来在测同一件事"的判据。
本次把探针粒度从**物件**下沉到**条目**，并让冒烟进入**第一人称**这一侧，
正是冲着上面四个盲区去的。

## 6. 结论

`J3.1` 交付的是**两条被静默打破的契约约束，以及能守住它们的判据**：

- 交互契约的字段改名必须**全量同步**（`act` → `activate` 漏了一处，代价是第一人称零交互）；
- "一条交互"与"一个命中体"不是一回事 —— `hits` 让**每条**交互都有自己的入口，
  且**省略即向后兼容**，于是 `J3` 已搬的 35 件行为一字未变；
- 交互类回归**必须由交互层判据守住**：像素看不见、冒烟绕开、单测粒度不够 ——
  三条一起漏，而"逐条"判据一次就照出了 9 个缺口。
