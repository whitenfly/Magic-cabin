## 2. ★ 专案：`floor2/magic-clock` 的 184 像素差异（已回退，待专项调查）

### 2.1 做了什么

按 `floor2-magic-clock.SKIP.md` §3 的"现成配方"完整搬迁：

- **新增** `src/cabin/world/floor2/magicClock.js`：`defineProp({ id, kind, state, build, update })`
  - `state: () => ({ clockLastKey: '' })`（原 `ctx.clockLastKey`，跨帧缓存：一秒只重画一次）
  - `build({ scene, FY, CHZ, edge, put, colEdge, state })`：canvas + `paintClock()` + `clockG` + 表盘几何
  - `update(dt, time, s, { parts })`：`paintClock(parts.cctx, parts.clockTex, s)`
  - `import { clock } from '../../app/clock.js'`（`world → app` 具体实现依赖，与 `defineProp` 同类，不违反 `N3`）
- **改** `floor2/install.js` 四处：加 import、删 `ctx.clockHand`/`ctx.drawClock` 两个导出、
  把 L1665–1737 的几何换成 `ctx.installProp(magicClock)`、把 `updateNewDecor()` 第一行 `drawClock()` 换成 `clockApi.tick(dt, time)`
  - **关键偏离**（照 SKIP 配方）：起点**跳过** `colEdge` 那 6 行 —— 它被 `mirror` / `junkBoxes` / `picture` 三件区间外使用

### 2.2 现象

| 项 | 结果 |
|---|---|
| typecheck / build | ✅ 通过 |
| 探针 `j3-probe` | ✅ **props=36**（原 35 + 时钟）、无未捕获异常、7/7 通过 |
| **像素回归** | ❌ **`default-fixed` 差 184 像素（0.0142%）**，bbox `x512–524 y271–307`（13×37），最大通道差 357 |
| 其余两机位 | ✅ `floor1-indoor` / `floor2-desk` **逐字节相同** |
| 性能统计 | ✅ `calls` / `triangles` / `geometries` / `sceneObjects` **全部 +0.0%** |

**差异内容的颜色分析**（逐像素取值）：基线是 `253,250,242`（＝ `#faf4e4`，表盘底色的 `fillStyle`）、
`157,152,139` / `196,196,196`（刻度灰）、`228,217,200`（底色与灰的混合）；当前全部是 `255,255,255`。
ASCII 亮度图显示差异呈「以表盘中心为轴的竖带、上下两块中间断开」——
**即表盘上的**指针**（分针/秒针指上、针尾在中心下方）**。

### 2.3 排查过的假设（**全部排除**）

| # | 假设 | 验证方式 | 结论 |
|---|---|---|---|
| 1 | 帧顺序被改动 | 场景统计 + 另两个机位 | ❌ 全部 **+0.0%** / 逐字节相同 |
| 2 | 缓存挡住重画（少画一次） | **强制每帧重画**（`s.clockLastKey = ''`）后重跑 | ❌ **差异一字不变**（184 像素、同一 bbox） |
| 3 | `paintClock` 代码与原版不同 | `git show dev:…install.js` 抽出原 `drawClock`/`clockHand` **并排比对** | ❌ **逐字相同**（仅 `ctx.clockLastKey` → `state.clockLastKey`、`clockHand` 由模块级改为嵌套） |
| 4 | `installProp` 有渲染副作用 | 读 `app/installProp.js` / `app/Registry.js` | ❌ `registerProp` 只是 `props.push(entry)`；aim 桥因本件无 `interactables` **整段跳过**；`mount` 为 null ⇒ 不 claim |
| 5 | `clock` 状态与运行时不符 | 读 `src/cabin/boot.js` L219–228 | ❌ `setMode('manual')` + `freezeWall()` 在 `installCabin` **之前**（L255）⇒ 装配时已是冻结时间 10:00:00 |
| 6 | `parts` 传参失败 | 在 `update` 里加 `if (!parts?.cctx) throw` | ❌ 未抛错（若抛错，`updateNewDecor` 会中断，差异必然更大） |

### 2.4 尚未排除的假设（给下一轮）

1. **canvas 纹理上传时机**：`new THREE.CanvasTexture(canvas)` 在装配期创建，
   而 `paintClock` 在**同一次同步执行**里绘制 —— 原版也是；
   但原版与搬迁版的**调用栈深度/时机**不同（`defineProp` 的 build 经 `installProp` 间接调用），
   是否影响了 `needsUpdate` 的消费时机，**未验证**。
2. **字体加载竞态**：`c.font = 'bold 26px serif'` + `fillText('12'/'3'/'6'/'9'/'✦')`。
   若 `paintClock` 只被真正执行**一次**，且那一次早于字体就绪 ⇒ 文字用 fallback 渲染。
   **但实验 2（强制每帧重画）没能改变结果**，这条假说因此**未被证实也未完全排除**
   （重画时字体可能仍已在缓存里、或 key 相同导致 canvas 内容本该一致）。
3. **`state` 对象的传递路径**：`installProp` 用 `Object.create(ctx)` 造 `env` 并把 `state` 挂为**自身属性**；
   `build` 与 `update` 拿到的是同一对象 —— **静态读代码是这样，但没有运行时实证**。

### 2.5 复现步骤（下一轮直接用）

> **捷径建议**：下一轮第一个实验应当是**把 `paintClock` 的调用从 `build` 里移到 `update` 里**
