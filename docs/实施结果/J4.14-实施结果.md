# J4.14 · 每帧分支归位 —— 实施结果

> 编号 **`J4.14`** ｜ 分支 `task/J4.14-frame-branch-rehome` ｜ `--base=0.4.0`
> 上游：`J4.9` §5 与 `J4.10` §2.5 留下的债务「**每帧分支归属错位**」——
> 它是 `J4` 债务清单里**唯一一条被判定为"不该在那个阶段硬做"**的
> （`J4.10` §2.5 原话："必须**连同 `UpdateScheduler` 的登记顺序一起设计**才算干净"）。
>
> 它是 `J4` 的**收口任务**：把 `J4.7` 段切片按行切留下的最后三处错位还清。

---

## 0. 一句话结论

「花 / 路牌材质 / 萤火虫不透明度」三个**每帧分支**原本住在
`systems/weather/WeatherSystem.js`（`L461–L468`），是 `J4.7` 段切片**按行区间切**的副产物
—— 光照与材质的每帧更新挂在"天气"模块上。

现在它们**各自回到自己的模块**：

| 每帧分支 | 原位置 | 新落点（导出函数） |
|---|---|---|
| **路牌材质** | `WeatherSystem.js` L461–462 | `world/house/shell.js` → `updateSignMaterials(ctx)` |
| **花材质** | `WeatherSystem.js` L463 | `world/outdoor/yardStatic.js` → `updateFlowerMaterials(ctx)` |
| **萤火虫不透明度** | `WeatherSystem.js` L465–468 | `world/outdoor/fireflies.js` → `updateFireflyOpacity(ctx, dt)` |

**做法**：把 `updateWeatherSystem()` 拆成 `weather/atmosphere` + `weather/effects` 两段，
三个归位分支作为**独立帧任务**插回它们**原来的执行位置**：

```
weather/atmosphere → world/signMaterials → world/flowerMaterials → world/fireflyOpacity → weather/effects
      （原 :02 前半）        ⑨                    ⑩                      ⑪              （原 :02 后半）
```

**帧顺序一字未变 —— 由像素回归证明：3/3 机位 sha256 逐字节相同。**

## 1. 债务是什么（为什么之前两个任务都刻意绕开它）

### 1.1 成因

`J4.7` 用段切片把 6217 行的 monolith 按**行区间**切成 21 个段模块。切点是"行"，
不是"职责" —— 于是那几行**恰好落在 weather 段的行区间内**，就跟着天气段落进了
`WeatherSystem.js`，尽管它们与天气毫无关系（路牌在**世界**侧、花在**院子**里、
萤火虫的几何就在 `world/outdoor/fireflies.js`）。

### 1.2 危害

| 面 | 具体 |
|---|---|
| **归属** | 想改路牌材质的人不会去"天气"模块里找；`WeatherSystem.js` 的职责被稀释 |
| **数据流** | `_amb`（环境光色）是这三个分支的**隐式输入** —— 它们**依赖天气先算完** |
| **契约** | 它们经 `ctx.*` 取值（`ctx.signSideMat` / `ctx.flowerMats` / `ctx.ffOpacity`），是 `J3` 之后残留的"隐式全局"通道 |

### 1.3 ★ 为什么 `J4.9` / `J4.10` 都**刻意没做**

`J4.10` §2.5 把这条债务与它自己做的「光源注册搬迁」并排对比，结论是**性质不同**：

| | 光源注册（`J4.10` 做了） | 每帧分支（本任务） |
|---|---|---|
| 性质 | **初始化**动作 | **每帧**动作 |
| 与帧顺序的关系 | 无关（能注册就能注册） | ★ **强相关** —— 依赖 `_amb` 先算出来 |
| 搬动的后果 | 无（像素可证） | ★ **改变帧顺序 = 改变画面** |

而 `UpdateScheduler` 的纪律是「**登记顺序 = 执行顺序**」（`UpdateScheduler.js` L29 的注释），
所以**不能只搬代码、不搬位置**。这正是本任务要一起设计的东西。

## 2. 做了什么

### 2.1 把 `updateWeatherSystem()` 拆成两段

原函数是一个**整体任务**（`frame/02`），内部从"天气参数插值"一路跑到"时钟显示"，
而那三处分支夹在**正中间**（第 ⑨⑩⑪ 段，前面是"大气/环境光"，后面是"天体/降水"）。

拆成：

| 函数 | 职责 | 原行区间 |
|---|---|---|
| `updateWeatherAtmosphere(dt, time)` | 参数插值 → 天空色/雾 → `night`/`twilight` → 环境光 `_amb` → `FILL` → 窗体 | L415–L459 |
| `updateWeatherEffects(dt, time)` | 太阳 / 月亮 / 星星 / 云 / 雨 / 雪 / 闪电 / 时钟 | L470–L578 |

**两段之间的状态传递**用一个模块私有的帧内对象（`frameSt`）—— 因为 `effects` 半段要用
`atmosphere` 半段算出的 `hour` / `night` / `twilight` / **`moonFade`**：

```js
const frameSt = { hour: 0, night: 0, twilight: 0, moonFade: 0 }
// atmosphere 末尾写：frameSt.hour = hour; … ; ctx._night = night
// effects  开头读：const { hour, night, twilight, moonFade } = frameSt
```

> `moonFade` 是最容易被漏掉的那个 —— 它在 `atmosphere` 段算出（`moonGroup.position.y / 4`），
> 却在 `effects` 段被月亮透明度用到（`moonOp = … * moonFade`）。
> 这是**逐行核对**才发现的，不是靠"看起来只依赖 hour/night"猜出来的。

`ctx._night` 是给世界侧帧任务用的显式出口 —— 与既有的 `ctx._amb` 同一模式（`WeatherSystem.js` L76 已有）。

### 2.2 三个归位函数（各自回到自己的模块）

| 文件 | 新增导出 | 实现 |
|---|---|---|
| `world/house/shell.js` | `updateSignMaterials(ctx)` | `ctx.signSideMat.color.copy(ctx.FILL.uniforms.uColor.value)`（face 同理） |
| `world/outdoor/yardStatic.js` | `updateFlowerMaterials(ctx)` | `for (const f of ctx.flowerMats) f.mat.color.copy(f.base).multiply(ctx._amb)` |
| `world/outdoor/fireflies.js` | `updateFireflyOpacity(ctx, dt)` | `ffTarget`（晴/多云且入夜）+ 指数趋近 + 写 `ctx.ffUniforms.uOpacity` |

每个函数都带了**输入说明**与**顺序约束**的注释 —— 因为"它必须排在哪"是这个函数的
**语义的一部分**，不能只写在文档里（`J4.10` §2.3 的同一做法：约束写进注释，不只写文档）。

`fireflies.js` 的文件头也一并更正了 —— 它原来写着"⚠️ 每帧逻辑不在这里…本次**不动**它们"，
现在改为"每帧逻辑分两处"，并指明各自住哪。

### 2.3 `FrameBody.js`：一个任务拆成五个，**顺序不变**

```js
// 原：
F('frame/02', (dt, time) => { ctx.updateWeatherSystem(dt, time) })

// 现：
F('weather/atmosphere',    (dt, time) => { ctx.updateWeatherAtmosphere(dt, time) })
F('world/signMaterials',   (dt, time) => { updateSignMaterials(ctx) })
F('world/flowerMaterials', (dt, time) => { updateFlowerMaterials(ctx) })
F('world/fireflyOpacity',  (dt, time) => { updateFireflyOpacity(ctx, dt) })
F('weather/effects',       (dt, time) => { ctx.updateWeatherEffects(dt, time) })
```

命名从 `frame/NN`（按原行号序号）改为**语义名** —— 与既有的 `prop/stools`、`prop/rubik`
同一风格，也标明"这是归位后的结果"。三个 import 的路径是两级 `../../world/…`
（`J4.9` §2.3 坑①：级数写错只有 `astro build` 能拦下）。

### 2.4 顺序约束（写进代码注释，不只写本文档）

| 帧任务 | 必须排在 | 原因 |
|---|---|---|
| `world/signMaterials` | `weather/atmosphere` 之后 | 读它写的 `ctx.FILL.uniforms.uColor.value` |
| `world/flowerMaterials` | `weather/atmosphere` 之后 | 读它写的 `ctx._amb` |
| `world/fireflyOpacity` | `weather/atmosphere` 之后 | 读它写的 `ctx._night` |
| `world/fireflyOpacity` | **`frame/10` 之前** | `frame/10`（萤火虫**位置**更新）用 `ctx.ffOpacity > 0.01` 判可见性 |
| `weather/effects` | 以上全部之后 | 读 `frameSt` |

## 3. ★ 为什么帧顺序**真的**没变（本任务的硬约束）

**判据不是"我看着像没变"，而是像素逐字节比对。** 三个机位的 sha256 全部与基线相同：

```
✓ default-fixed   sha256 相同（182422 B）
✓ floor1-indoor   sha256 相同（117059 B）
✓ floor2-desk     sha256 相同（138670 B）
结果：3 个机位零差异 / 0 个有差异 / 0 个无效截图
```

这条判据之所以能证明"帧顺序没变"，是因为它跑在 `clock.mode === 'manual'` 的**定格 120 帧**
模式下（`FrameBody.js` 末尾的 `frame/101` 只在 manual 下追加 `updateNewDecor`）——
**逐帧推进**，任何顺序错位都会在某一帧的像素上现形。

**性能统计**进一步佐证场景结构未变：`calls` 3138、`triangles` 86158、`geometries` 2843、
`sceneObjects` 5365 —— 全部 **+0.0%**。

## 6. 遗留与交接

1. **`ctx.*` 的隐式通道仍在。** 三个归位函数读的仍是 `ctx.signSideMat` / `ctx.flowerMats` /
   `ctx.ffOpacity` / `ctx._amb` / `ctx._night` —— 本任务解决的是**归属**（谁负责更新），
   不是**存取方式**。把这些改成 `defineProp` 的 `state`/`parts` 是**任务 D**（35 件升格）的事：
   `J4.9` §2.2 已经预判到这条耦合 —— "升格为 `defineProp` 会让这些键的**存放位置**改变
   （进 `state` 或 `parts`），进而牵动那两处每帧分支"。**本任务先行，正是为了让 D 少动一次。**
2. **萤火虫的位置更新仍住 `FrameBody.js`（`frame/10`）。** 它读 `ctx.ffOpacity` 判可见性，
   且与 `frame/11`（写 `uTime`）一起构成"每帧更新顶点"的两步。把它们也搬进 `fireflies.js`
   需要把 `frame/10`、`frame/11` 一并移出 —— 收益小于风险，**不在本任务范围**。
3. **`world/lights.js` 的槽序注释**（`J4.10` §2.3）与本任务的顺序表是**同一类约束**，
   两者都靠 `FrameBody.js` 的登记顺序兜底 —— 若将来有人重排帧任务，这两处会**同时**失效。
4. `J4.9` §5 提到的另两件遗留（`outdoor/signpost` 与栅栏+蘑菇仍留在 `shell.js` 的段里）
   属**任务 D** 的范围。
