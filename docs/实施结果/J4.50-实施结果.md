## 1. 合并前的两条路径（`J4.27` §6.3 的原文条件）

```
[realtime]  install.js 的 decorLoop()  ← IIFE，build 期**立即执行一次**
              └─ rAF 自驱动 ──▶ t = performance.now() * 0.001
                                d = min(0.05, max(0.001, t - ctx.decorLastT))
                                └──▶ updateNewDecor(t, d)

[manual]    FrameBody 的 frame/101（调度器）
              └─ if (clock.mode === 'manual') ──▶ updateNewDecor(clock.now, clock.dt)
```

`J4.27` §6.3 给的合并条件（两条都必须满足）：

1. **realtime 节流不变**：`dt` 来自 `performance.now()` 差值（与 `clock.dt` **解耦**）；
2. **manual 定格不变**：像素回归靠 `frame/101` 逐帧推进。

`J4.30` 把 `magic-clock` 升格后，`updateNewDecor()` 里**只剩 4 行 `xxxApi.tick(dt, time)`**，
不再有任何"原生"重绘代码 ⇒ 剩下的**纯粹是调度问题**，与本任务的判断一致。

---

## 2. 合并做法

`FrameBody.js` 的 `frame/101` 变成唯一的驱动点：

```js
F('frame/101', (dt, time) => {
  if (clock.mode === 'manual') {
    ctx.updateNewDecor(time, dt);          // ← manual：一字不变
  } else {
    const t = performance.now() * 0.001;   // ← realtime：原 decorLoop 的节流**逐字搬来**
    const d = Math.min(0.05, Math.max(0.001, t - ctx.decorLastT));
    ctx.decorLastT = t;
    ctx.updateNewDecor(t, d);
  }
})
```

`install.js`：删掉 `decorLoop()` IIFE；同时删掉**随之失去唯一使用者的** `import { clock }`
（删完后全文件再无 `clock` 的使用，其余出现都在注释里）。

**为什么不能直接用调度器给的 `dt`/`time`**：那是 `clock.dt` / `clock.now` —— **没有 0.001 下限**，
且与装饰循环原来的时间源不同源，直接换会**改变每帧推进量**（这是 §6.3 条件 1 的实质）。

## 3. 合并会改变的两点（都实测过）

| # | 差异 | 结论 |
|---|---|---|
| 1 | **build 期那次"立即调用"不再发生** —— 原来 IIFE 会当场跑一次 `updateNewDecor` | **稳态下不可见**（`visual` 3/3 相同） |
| 2 | **调用位置从"独立 rAF"变成 `frame/101`**（= `frame/100` 渲染**之后**）—— 原来 `decorLoop` 的 rAF 在 build 期注册，**先于** `animate` 的 rAF | 最多让装饰更新**延后一帧**显示；`visual` 看的是**定格 120 帧后的稳态** ⇒ 同样不可见 |

两点都由 **`test:visual` 3/3 逐字节相同**独立覆盖。

## 4. ★ 实测出的判据边界：`test:visual` **看不见装饰循环**

本任务原本打算照惯例交一条"**故意做错 ⇒ 变红**"的负例，**结果发现这条负例不存在**，而且原因很值得记：

| 负例 | 改什么 | `test:visual` 结果 |
|---|---|---|
| **A**（本想用的） | `frame/101` 的 **manual 分支整个漏掉** —— 模拟"合并时把逐帧那条丢了"（装饰循环在定格时完全不推进） | ❌ **仍然 3/3 逐字节相同**（**没变红**） |
| **B**（有效性对照） | `frame/99` 里**不应用测试机位**（同一区域 `frame/9x`，但产物**可见**） | ✅ **2 个机位有差异**（颜色 230 / 边缘 19.94%），`exit 1` |

⇒ 合起来读：**判据本身没坏**（B 证明它对同一区域的可见改动是敏感的），
是**装饰循环的产物在三个机位里确实不可见** —— 魔法钟挂在左墙 `x = CLOCK_X = -2.95`，
而三台机位都朝 `-z` 方向看（`floor2-desk` 是 `[0.2,4.55,2.95] → [0.2,3.85,-2.6]`），
镜子 / 挂画 / 纸箱也都不在定格取景里。

**这个边界对后来的意义**：

- **不能说**"`visual` 守住了这次合并" —— 它守不住 `frame/101` 这一类"产物不可见"的改动；
- 本任务**真正的证据链**是：① 时间源**逐字沿用**（代码级等价）+
  ② `visual` / 四个运行期判据 / `smoke` / `perf` **全部不回归** +
  ③ 上表的 A/B 对照**划清了判据的适用边界**；
- **遗留建议**：若要真正守住装饰循环的推进，需要一条**能读到装饰状态**的判据
  （现在没有任何判据覆盖"时钟指针走了多少 / GIF 播到第几帧"），见 §6。

## 6. 遗留

1. **没有判据覆盖"装饰循环在 realtime 下确实在推进"** —— 见 §4。要补的话，判据需要能读到
   时钟指针 / GIF 帧号一类的装饰状态（目前 `__cabinPropState` 能读 `state`，但 `magicClock`
   的 `state` 里没有"指针角度"这类量）。
2. **`ctx.decorLastT` 仍在 `install.js` 里初始化**（被 realtime 分支使用），`ctx.mirrorDirtyT`
   仍是 `J4.27` 记的**死变量** —— 后者本任务照旧刻意不删（属"清理"，与合并无关）。
