## 1 · 问题（L16）

**现象**：`node scripts/release.mjs ship main` 生成的是「**发布 `v0.3.0`**」的计划，而 `v0.3.0` **早已发布过** —— 照做会直接撞上已存在的 tag。

**根因**：`ver` 由 `package.json` 的 `version` 去掉 `-dev.N` 推出，隐含假设
「dev 上的 version 指向**下一个**待发布版本」。但 §1.1 允许在**已发布阶段**上继续挂收尾任务
（`J3.7`–`J3.11`），此时 dev 的 version 仍是旧 base（`0.3.0-dev.N`）⇒ 假设不成立。

```
package.json version = 0.3.0-dev.10
                          ↓ 去掉 -dev.10
          ver = 0.3.0  →  但 tag v0.3.0 已存在 ✗
```

**为什么值得修**：`J4` 阶段末尾若直接照搬计划会失败；而"在已发布阶段上追加收尾任务"
**不是异常用法**，是 §1.1 明文允许的（"取最近一个已完成阶段的号"）。

## 2 · 修法

**在 `cmdShip()` 的 `target === main` 分支最前面加一个守卫**（只加一个前置 `if`，原路径代码未动）：

```js
if (st.localTags.includes(`v${ver}`)) {
  warn(`正式版 v${ver} **已经发布过** —— 不会生成重复发布的计划`);
  info(`当前 dev 的 version 是 ${pkg.version}（去掉 -dev 后缀 = ${ver}），但 tag v${ver} 已存在。`);
  info(`⇒ 说明 dev 上这些提交是【已发布阶段】的后续收尾任务（收尾 / 规范 / 工具 / 文档）。`);
  say('');
  info('两种正确做法：');
  info('  ① 无需发布（推荐）：直接 `ship` 推送 dev 与开发版 tag —— 这些收尾改动会随下一阶段一起发布。');
  info(`  ② 需要单独发布：它们属【补丁位】（修复 / 护栏 / 纯文档 / 纯重构，见 §2）。`);
  info(`     做法是在 dev 上另起一条 \`${bumpPatch(ver)}-dev.N\` 序列（package.json 的 base 改成 ${bumpPatch(ver)}），`);
  info(`     再走本节流程发布 \`v${bumpPatch(ver)}\`。`);
  return;   // 不生成计划（也不写记录 —— 没有计划可记）
}
```

新增辅助函数：

```js
/** `0.3.0` → `0.3.1`（补丁位 +1）—— 用于「已发布阶段的收尾任务需要单独发版」时给出正确版本号 */
function bumpPatch(ver) {
  const mm = /^(\d+)\.(\d+)\.(\d+)$/.exec(String(ver));
  return mm ? `${mm[1]}.${mm[2]}.${Number(mm[3]) + 1}` : ver;
}
```

**设计取舍**：

| 决定 | 理由 |
|---|---|
| **拒绝生成计划**，而不是"生成 v0.3.1 的计划" | 工具无法判断用户**是否想发布**这些收尾改动 —— 越俎代庖地猜版本号是危险的（可能造出错误版本的 tag）。**给提示、让人决定**才是对的 |
| 提示里给出**补丁位**的版本号（`0.3.1`） | 收尾/规范/工具/文档类改动按 §2 正是**补丁位**的定义，给具体数字比说"你自己想"有用 |
| **不写记录** | 没有计划可记；这不是"违规尝试"（与 `guardProtectedBranch` 的 `kind: blocked` 不同），无需留痕 |
| 走**默认 `ship`** 不受影响 | 守卫只在 `target === main` 分支内 ⇒ 推送清单生成逻辑完全未动（已实测） |
