### 2.1 ★ 帧顺序：`ptLantern` 的平滑**提前**了 —— 为什么等价

一件物件只有**一个** `update`，而原实现里几何分支（`frame/18`–`frame/22`）与强度平滑
（`frame/92`）相隔约 74 个帧任务 ⇒ 合并后必须选一个位置。本件选**几何分支的位置**（早），
于是强度平滑**提前**执行。等价性有两条可查的论证：

1. **数值序列完全相同**：它是一阶低通 `p += (目标 − p) × 0.07`，同一帧内 `dt` 相同、
   输入 `lanternLit` 相同 ⇒ 逐位相同。唯一能破坏它的是"两个位置之间有人改了输入"——
   `grep lanternLit` 的全部命中只有本物件的那五段与这里，外加 `lights()` 的闭包
   （它在 `frame/97` 才被调用）⇒ **中间没有任何读者或写者**；
2. **仍然早于读者**：`lightField.update` 在 `frame/97`，本 `update` 在 `frame/18` 位置
   ⇒ 本帧读到的强度与搬迁前是**同一帧、同一个数**。

> 这条约束 `J4.18` §6.2 已预告，并已写进 `world/lights.js` 的文件头 —— 本任务是它的**首次实践**。

### 3.3 ★★ 证伪实验：证明「物件的 `lights()` 声明真的生效」

搬迁类改动有个陷阱：**画面相同可能是"值恰好相同"，而不是"新链路真的在工作"**。
所以做了一次**破坏实验**：把物件的 `slot: 0` 改成 **`slot: 7`**（与 `world/lights.js` 里
`floor1/moon-plant` 的槽位冲突）。

```
✓ default-fixed   sha256 相同（182422 B）
✗ floor1-indoor   sha256 不同
    像素差异 1.8247%（23648/1296000）  最大通道差 5
✓ floor2-desk     sha256 相同（138670 B）
```

改回 `slot: 0` 后复验：**3/3 逐字节相同**。

⇒ 一次性证明了三件事，都是**实证**而非推断：

1. **物件的 `lights()` 声明真的进了光照场**（不是死代码 —— 否则改 `slot` 不会有任何影响）；
2. **`slot` 真的决定槽位**（`J4.18` 的定序机制在真实物件上有效）；
3. **槽位冲突时后来者被拒**（`LightField.register` 的语义：灯不亮 ⇒ 一楼照明整体变淡，
   所以差异面积极大而通道差很小 —— `maxDelta = 5` 正是"少一盏灯"的形状）。

## 6. 遗留与交接

1. **`J4.18` 的契约已被验证可用** —— 剩下 5 件（`crystal-ball` 槽 4 / `kotatsu` 槽 3 /
   `magic-circle` 槽 2 / `moon-plant` 槽 7 / `candle` 槽 5 / `magic-veil` 槽 6）可照本件的
   模式照抄：**删 `world/lights.js` 里那一行 → 在物件里写同样的 `slot` 与参数 → 
   `strength: () => s.ptXxx` → 把 `frame/9x` 的平滑并进物件的 `update`**。
   ⚠️ 每件都要**单独**核对"平滑提前/推迟"是否等价（本件的两段相隔 74 个任务，
   若某件的两段之间**有人改输入**，就不能照抄这个方向）。
2. **`world/lights.js` 现在只剩 7 行注册**（槽 1–7）。文件头已写明"槽位 0 已搬走"。
3. **`verify-migration.mjs` 的 `stripComments` 缺陷** —— 三次实证，建议优先根治。
4. **动态行为判据**：本件的"熄灭/点亮"由像素回归**间接**覆盖（`lanternLit` 初值为 `true`，
   静止画面就是点亮态）；若要覆盖熄灭态，可参照 `tests/e2e/cart-shelf.mjs` 的模式补一条。
