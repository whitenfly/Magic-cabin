## 1. ★ 为什么必须「在 `dev` 上、发布**之前**」改（git 拓扑论证）

提示词的原话是"发布后按 §5.3 改五处状态副本"。**这句话与 git 拓扑不符** —— 本任务按拓扑来。

§5.2 的**豁免边界**写得极窄：

> **`main` 上只允许一个提交** —— 那个 `release:` **merge commit**。
> 它在冲突解决时**顺带写入**了 `package.json` 的正式版本号。

推论链：

| # | 事实 | 后果 |
|---|---|---|
| 1 | `main` 上只能有**一个**提交（那个 release merge commit） | 五处副本**不能**在 `main` 上改 |
| 2 | 那五处只能在 `dev` 上改，再经 merge 带进 `main` | 改动必须**先于**发布存在 |
| 3 | 若"发布**后**才在 `dev` 上改" | ① merge 带过去的是 **🟡 旧状态** ⇒ **`main` 上的 §5.4 是过期的**；② 发布提交**不回流 `dev`**（§5.2）⇒ 两条分支的 §5.4 **永久分叉** |
| 4 | §5.3 的判定是「**五处状态一致**；不一致时以本文件 §5.4 为准」 | 分叉的直接后果就是**判据失效** |

**⇒ 五处副本必须在 `dev` 上、发布之前改好，让 `main` 通过那一个 merge commit 收到 ✅ 状态。**

> 顺带：本任务**只改状态副本**，不碰任何 `src/**` —— 这样 release merge 的冲突面**只有 `package.json` 一行**（§5.2 已把它列为**预期冲突**）。

### 2.2 额外一处：README 的「当前阶段」

`README.md` 顶部还有一行「**当前阶段**」，它不在 §5.3 的五处清单里，但**语义上是第六处**副本：


## 3. 发布前的硬要求：`verify:visual` **3 轮**

§6 门禁分级把「发布到 `main` 前」单列一档，要求 **`verify:visual`（3 轮零差异）+ 完整六项**。
提示词特别提醒过：**单轮 `compare.mjs` 证明的是"这次没变"，3 轮证明的是"每次都一样"——两件事。**

```bash
node tests/visual/capture.mjs --rounds=3
```

| 机位 | 第 1 轮 | 第 2 轮 | 第 3 轮 | 轮间 | 与**基线** |
|---|---|---|---|---|---|
| `default-fixed` | `04b442fc09ea06b6…` | 同 | 同 | ✅ 零差异 | ✅ 相同 |
| `floor1-indoor` | `ee3e5e61a710069f…` | 同 | 同 | ✅ 零差异 | ✅ 相同 |
| `floor2-desk` | `06b7affdd8c25b9a…` | 同 | 同 | ✅ 零差异 | ✅ 相同 |

**三条结论**：① 三轮之间零差异（可复现）；② 三轮与基线**同一个 sha256**（没改坏）；
③ 字节数逐轮相同（182422 / 117059 / 138670 B）。

## 4. 关于 `_j4-dev-sync.mjs --check` 现在会报差异 —— **这是预期的**

```bash
node scripts/oneoff/_j4-dev-sync.mjs --check
# ✗ 1 处定位失败（判据可能已被改写）
```

**原因**：该脚本用正则从五处提取 `v0.4.0-dev.<N>`，把它与 `package.json` 的 `version` 比对 ——
它守的是**开发期**的"六处同为 `dev.N`"。阶段一旦**发布**，五处写的是**正式号 `v0.4.0`**，
而 `dev` 上的 `package.json` 按 **R9** 必须继续等于最新的 `dev.16`。
**两者本来就该不同** ⇒ 该脚本的判据在"已发布"状态下**不适用**。

> 它没有坏，是**使命完成**：`J4` 开发期内它是"防 P4 复发"的机械防护（`J4.11` 收尾时正是它报出了
> `dev.10 / dev.11` 的不一致，见 `J4.11-实施结果.md`）。发布后的一致性由
> §5.3 清单 + §5.4 版本历史表（唯一事实来源）守住。
>
> **未做**（刻意）：改这个脚本来认识"已发布"状态 —— 那需要按 §12 之类的一致性核对，
> 超出本任务"只改状态副本"的范围。记入 §7 遗留。
