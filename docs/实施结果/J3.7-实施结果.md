## 0 · 为什么状态副本必须在 `dev` 上先改

**执行顺序上的一个关键判断**（本次要先想清楚的事）：

| 规范条文 | 要求 |
|---|---|
| §5.2 | `main` 上**只允许**两类提交：① merge commit ② **发布元数据提交（只改 `package.json` 的 `version` 一个字段）** |
| §5.3 | 阶段收尾**必须**更新**状态副本**（README / 路线图 / §5.4 表）—— 这些是**文档改动** |

两者直接冲突：状态副本是文档改动，但 `main` 上不允许文档提交。

> **⇒ 正确顺序是**：状态副本先在 `dev` 上作为**阶段收尾任务**改完（本文），
> 然后再把 `dev` 合并进 `main`、只留那一次 `version` 元数据提交。
> 这样 §5.2 的豁免边界**一点没被撑破**。

## 6 · 发布计划（§5.2，本文之后立刻执行）

```bash
node scripts/release.mjs ship main          # ① 生成发布计划
# ② 人工等价动作：
git switch main && git merge --no-ff dev -m "release: v0.3.0（J3 物件模块化）"
#   手改 package.json version → 0.3.0      ← main 上唯一允许的元数据提交
git commit -am "chore(release): v0.3.0"
git tag -a v0.3.0 -m "…"
git switch dev
node scripts/release.mjs ship               # ③ 复查 dev 与开发版 tag
node scripts/release.mjs status             # ④ 全绿判定
```

**执行前置**：`dev` 与 `main` 都必须先 push 同步（用户已在普通终端完成历史推送）。
