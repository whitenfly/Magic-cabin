## 2. 为什么必须做这一步

F0.2 完成后的实测：

```
第 1 轮  172580 字节
第 2 轮  172562 字节    场景随机序列摘要三轮完全一致 ✓
第 3 轮  172138 字节    但截图像素仍有差异 ✗（约 0.25%）
```

**布局已经固定**（树在哪、石头朝哪、星空怎么排），但像素仍不同。根源是时间：

```js
// 改动前
function animate(t) {
    requestAnimationFrame(animate);          // ← 自驱动，外部无法推进
    const time = t * 0.001;                  // ← t 是浏览器按真实时间给的时间戳
    const dt = Math.min(time - lastT, 0.05);
    lastT = time;
    ...
}
animate(0);
```

两次加载的启动耗时不同 → 第 120 帧对应的 `time` 不同 → 所有动画相位不同：

```js
updateWavyFlame(f, time, fireP)      // 火焰摆动相位 = f(time)
FILL.uniforms.uTime.value = time     // 着色器闪烁 = f(time)
b.position.y = ... Math.sin(time * 2.5 ...)
```

**这不是 bug，是"无法定格"** —— 你没法说「给我第 120 帧的画面」。

## 3. 设计：三级时钟

`clock.js` 把时间显式分成三级：

| 级别 | 用途 | API | 可控性 |
|---|---|---|---|
| **`wall`**（真实挂钟） | UI 节流、防连点、GIF 重绘节流 | `clock.wallNow()` | 只读；**manual 模式可冻结** |
| **`game`**（游戏内时间） | 昼夜、天气（原 `gameSec`） | `gameSec += timeScale * dt` | 可跳转（时间滑块）—— 已存在于 monolith |
| **`anim`**（动画时间） | 火焰 / 水面 / 粒子 / 呼吸 / 转场 | **`clock.now`** / `clock.dt` | ★ **可手动步进** |

**判定某个时间用途归哪一级**：

> 问「**这个值会不会出现在截图里？**」
> 会 → `clock.now`（anim 级）　　不会（UI 反馈、性能节流、输入手感）→ `clock.wallNow()`（wall 级）

### 两种模式

```js
// realtime（默认）：与改动前**完全等价**
clock.tick(rafTimestamp)   // dt = clamp(t - now, 0, 0.05)，即原来的 Math.min(time - lastT, 0.05)

// manual（测试）：时钟不自行推进，由外部逐帧推进
clock.step(1 / 60)         // 每帧 dt 固定，第 N 帧状态完全可复现
```

## 4. 改动清单（20 处）

### 4.1 主循环：帧体抽出（结构性改动）

```js
// ── 改动前 ──
let lastT = 0;
function animate(t) {
    requestAnimationFrame(animate);
    const time = t * 0.001; const dt = Math.min(time - lastT, 0.05); lastT = time;
    … 约 940 行帧体 …
    renderer.render(scene, camera);
}
animate(0);

// ── 改动后 ──
function tickOnce() {
    const time = clock.now; const dt = clock.dt;
    … 帧体原样未动 …
    renderer.render(scene, camera);
    if (clock.mode === 'manual') updateNewDecor(time, dt);   // manual 下由主循环驱动装饰
}
function animate(t) {
    requestAnimationFrame(animate);
    clock.tick(t);
    tickOnce();
}
// realtime 自驱动；manual 暴露单帧钩子给宿主
if (clock.mode === 'manual') {
    window.__cabinStepFrame = tickOnce;
    window.__cabinStartStillRepaint = function () { … };
} else {
    animate(0);
}
```

| # | 类别 | 位置（改动后行号） | 改动内容 |
|---|---|---|---|
| 1 | 接入 | L17 | 新增 `import { clock } from '../app/clock.js'` |
| 2 | 主循环 | L8059–8060 | `function animate(t)` → `function tickOnce()`；时间源 → `clock.now` / `clock.dt` |
| 3 | 主循环 | L8056 | 删除 `let lastT = 0;`（时间差由 clock 维护） |
| 4 | 主循环 | L9004–9009 | 新增 `animate(t)` 包装 |
| 5 | 主循环 | L9000–9001 | `renderer.render` 后：manual 模式驱动 `updateNewDecor` |
| 6 | 主循环 | L9010–9030 | manual 模式暴露 `__cabinStepFrame` / `__cabinStartStillRepaint` |
| 7 | 装饰循环 | L6056–6068 | `decorLoop` 读 `clock`；manual 模式跳过自驱动 |

| 18 | 挂钟 | L5531 | `drawClock()` 在 manual 模式使用冻结日期 |

### 4.3 第 8–17 处为何必须同尺度（最容易踩的坑）

这 10 处都是「事件触发时记下起点，之后用 `time - t0` 算进度」：

```js
// 魔方打乱
state.t0 = clock.now;
// …之后…
const k = Math.min(1, (time - state.t0) / duration);

// 沙漏
const hourState = { phase: 'flow', t0: clock.now };
```

如果只把 `time` 换成 `clock.now` 而 `t0` 仍取 `performance.now()`（真实挂钟秒数，例如 1234.5），
`time - t0` 会是个巨大负数 → **动画卡死或瞬间跳完**。

涉及：魔方 / 扑克牌 / 沙漏 ×2 / 魔法书翻页 / 粉笔书写 / 魔杖 / 魔女帽。

**这类故障静态校验查不出来**（语法完全正确），必须人工触发每个动画验证。

### 4.4 刻意**不改**的地方

| 项 | 位置 | 理由 |
|---|---|---|
| `decorLoop` 的 realtime 分支 | L6064 | 保持 `performance.now()` 原行为，确保正常模式零差异 |
| **11+ 处固定系数插值** | `updateSprings`(L384)、火/灯渐亮 `* 0.016`、宝箱/储物箱/沙漏 `* 0.02`、凳椅 `* 0.02/0.03` | 它们**按帧计数、与 dt 无关**（过渡速度随帧率变化，是原代码既有特性）。改成 dt 形式会**改变过渡速度**，属视觉变化，超出 F0.3 边界 |
| `gameSec` / `timeScale` | L7571–7595、L7889 | 它已由 `dt` 推进，`dt` 现在来自 clock，自动获得可复现性，无需改动 |

> 固定系数插值在 manual 模式下反而**更可复现**：推进 N 帧就精确插值 N 次。

## 6. 排查记录：三个真实问题

### 6.1 WebGL `preserveDrawingBuffer` —— 定格后必须持续重绘

**现象**：`frames=120` 返回 `ready`，截图 sha256 三轮完全一致，但**截图只有 9.1 KB**（正常约 172 KB）。
像素分析显示 **98.9% 是纯黑** —— 画面是黑的。

**根因**：WebGL 的 `preserveDrawingBuffer` 默认为 `false`。同步推进完 120 帧后**不再渲染**，
drawing buffer 被清空，`--screenshot` 读到的就是空白。

**修复**：定格后启动「静止重绘」循环，每帧仍 `renderer.render()` 一次：

```js
window.__cabinStartStillRepaint = function () {
    (function still() {
        requestAnimationFrame(still);
        renderer.render(scene, camera);
    })();
};
```

> **教训**：`sha256 相同` 这个"通过"的判据，在画面全黑时**同样成立**。
> 只比对哈希会得到假阳性 —— 必须同时验证画面**有内容**（本次靠 PNG 像素分析发现）。

### 6.2 静止重绘不能调用完整的 `tickOnce()`

**现象**：启动静止重绘后截图恢复正常（172 KB），但三轮仍有约 30 字节差异。

**根因**：静止重绘最初调用的是 `tickOnce()`，而帧体里有：

```js
gameSec += timeScale * dt;   // 昼夜推进
```

`dt` 固定但**每帧仍在累加** → 太阳/月亮/天空持续变化 → 像素缓慢改变。

**修复**：静止重绘**只调用 `renderer.render()`**，不推进任何状态。

### 6.3 每帧等真实 rAF 太慢 —— 改为同步推进

**现象**：`frames=30` 时页面在 30 秒虚拟时间预算内都跑不完。

**根因**：最初 `runFrames` 用 `await new Promise(r => requestAnimationFrame(r))` 逐帧等待；
在无头 + 软件渲染（swiftshader）环境下，每帧渲染 172 KB 的 3D 场景很慢。

**修复**：monolith 在 manual 模式下**不启动 rAF 自驱动**，而是把单帧函数挂到
`window.__cabinStepFrame`；boot 直接**同步**调用它 —— 120 帧瞬间完成（实测整轮 15.6 秒含浏览器启动）。
