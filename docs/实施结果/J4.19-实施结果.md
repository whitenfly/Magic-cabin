# J4.19 · `floor1/bookshelf` 升格 `defineProp` —— 实施结果

> 编号 **`J4.19`** ｜ 分支 `task/J4.19-bookshelf-prop` ｜ `--base=0.4.0`
>

> `J3` 把它判为"搬不动"，病根是 `SFX` / `SFZ` 被**碰撞表**读。

## 0. 一句话结论

书架升格为 `world/floor1/bookshelf.js`（几何 + 12 条交互 + 每帧分支一个文件）。
搬走它的两个前置条件都已就绪：

1. **位置归属**：`SFX` / `SFZ` 搬进 `world/layout.js`（`SHELF_X` / `SHELF_Z`，不变量 `N9`），
   碰撞表随之改读 layout —— **数值逐字未变**（`-3.72` / `-2.85`）；
2. **12 条交互**：`J3.1` 之后 `interactables` 支持**逐条 `hits`**
   ⇒ 12 本书**各有自己的准星入口**（`J3` 当年的代价是"只有第一本点得动"）。

画面 **3/3 机位逐字节相同**；探针 `aimMissing` 为空、`floor1/bookshelf` 出现在准星入口清单里。

## 1. 病根（`J3` 记的两条前置）

`scripts/oneoff/_j3-specs/floor1-bookshelf.SKIP.md`：

```js
const SFX = -3.72, SFZ = -2.85, SFW = 1.3;                    // ← 12.9 分区内
…
{ x1: SFX - 0.25, z1: SFZ - 0.70, x2: SFX + 0.25, z2: SFZ + 0.70, top: 2.02 },   // ← platformBoxes
```

`platformBoxes` 住在**碰撞段**（`J3` 时代还在 monolith 里），既不是本分区的几何段、
也不是它的 `tick` 块 ⇒ 应用器表达不了它，而任务书禁止手改 `monolith.js`。
搬走 = `SFX` 从 monolith 消失 ⇒ `refreshPlatforms()` 每帧 `ReferenceError`（**直接崩**，不是像素差异）。

`J3` 写下的前置条件：「**最省事**的是把这两个值写进 `world/layout.js`」—— 本任务正是这么做的。

> 这正是 `stools` 当初踩过的同一个坑（`movingPlatforms` 读 `stools[0]`），
> 它靠**人工手改两行**才过；`J3` 那轮不允许手改 monolith，故跳过。
> 现在 `collision.js` 已是模块化代码（`J4` 段切片的产物），改它是**正常开发**而非"手改禁区"。

## 2. 做了什么（1 个新文件 + 4 处改动）

### 2.1 `world/layout.js` —— 新增 `SHELF_X` / `SHELF_Z`

按不变量 `N9`（位置与几何**同源**）落在 layout 里，数值取自原分区局部常量（`-3.72` / `-2.85`）。
`SFW = 1.3` **不进 layout** —— 只有书架自己用（层板间距），不跨模块。

### 2.2 `systems/player/collision.js` —— 碰撞表改读 layout

```js
// 前： { x1: ctx.SFX - 0.25, … }
// 后： { x1: ctx.L.SHELF_X - 0.25, … }
```

★ **数值逐字未变** ⇒ 碰撞行为与搬迁前完全一致。

### 2.3 `world/floor1/bookshelf.js` —— 新增（几何 + 交互 + 每帧）

- `build` 逐字搬运原几何（层板 / 立板 / `addBook` / 三层摆书循环 / `HS` / `TS` 表），
  只把 `SFX` → `L.SHELF_X`、`SFZ` → `L.SHELF_Z`；
- 12 本书**各自直接 `scene.add(g)`**（搬迁前就没有共同父节点，加包装层会改 `scene.children`
  ⇒ 像素回归）⇒ `root: shelfBooks[0]`（同 `floor1/stools` 的处置，`root` 只是登记元数据）；
- `interactables`：**每本书一条**，各带 `hits: g`；
- `update`：原 `for (const b of shelfBooks) { … }` 逐字搬运。

**本件没有 `rng` 调用**（原段一个都没有）⇒ 不影响后续随机数序列。

### 2.4 `world/floor1/install.js` —— 原位置换装配调用

原几何段（`const shelfBooks` / `SFX`/`SFZ`/`SFW` / `addBook` / 三层循环，共 36 行）整体删除，
换成 `const bookshelfApi = ctx.installProp(bookshelf);`。
**装配调用留在原行位置**（`build` 在原来的地方被调用 ⇒ `scene.add` 顺序不变）。

### 2.5 `app/scene/FrameBody.js` —— `frame/36` 原位置调用

```js
// 前：for (const b of ctx.shelfBooks) { … }        （8 行）
// 后：ctx.bookshelfApi.tick(dt, time);
```

登记位置（`frame/36`）**一个字节没动** ⇒ 帧顺序不变。

## 3. 判据与证据

### 3.1 ★ 画面：3/3 机位逐字节相同

```
✓ default-fixed   sha256 相同（182422 B）
✓ floor1-indoor   sha256 相同（117059 B）
✓ floor2-desk     sha256 相同（138670 B）
```

### 3.2 ★ 交互通路：探针（`J3` 那类"画面看不出来"的错只有它守得住）

§7.2 的已知坑：**像素回归对"交互失效"原理上无感** —— 交互消失画面毫无变化。
本件搬走了 **12 处 `regMagic`**，正是最容易犯这类错的地方。探针（`tests/e2e/j3-probe.mjs`）：

```
✓ 已装配物件数 ≥ 9                      → props=36
✓ 近距交互条目已登记                     → interactables=80
✓ ★ 搬迁物件的准星入口齐全（aim 桥生效）  → 27 件有准星入口：… floor1/bookshelf …
✓ ★★ 每条声明了 aim 的交互都有自己的命中体 → 71 条交互各有 aim 入口   ← aimMissing 为空
```

`floor1/bookshelf` **出现在准星入口清单里**是这次搬迁的关键新证据。

**命中体数量不变（论证）**：原 `regMagic(o, cb)` 的命中体是
`o.traverse(m => m.isMesh && !m.userData.noHit)`（`world/house/shell.js` L265–271），
新路径 `hits: g` 的遍历条件**完全相同**（`app/installProp.js` ⑤.2），
且每本书只被一条 `hits` 引用 ⇒ 12 本书各贡献 **1 个 Mesh**，两条路径逐条等价。

### 3.3 破坏性实验：证明"零差异不是巧合"

搬迁类改动有个陷阱：**画面相同可能是"值恰好相同"，而不是"新链路真的在工作"**。
故做一次破坏实验：把 `layout.SHELF_X` 从 `-3.72` 改成 `-3.67`（位移 5cm）。

```
✗ floor1-indoor   sha256 不同
    像素差异 0.3937%（5102/1296000）  最大通道差 714
✓ default-fixed / floor2-desk  相同（书架只在室内机位可见，符合预期）
```

改回 `-3.72` 后复验：**3/3 逐字节相同**。

⇒ 证明了两件事：**画面对书架位置敏感**（判据抓得住），且**位置真的由 layout 接管**
（零差异不是巧合）。

## 6. 遗留与交接

### 6.1 ⚠️ ★ 碰撞表的正确性**没有自动判据守着**（本任务发现）

`collision.js` 的改动只影响**玩家碰撞**，不影响任何一帧的渲染像素：

| 判据 | 能守住碰撞表吗 |
|---|---|
| `test:visual` | ❌ 原理上无感（碰撞不参与渲染） |
| 探针 `j3-probe` | ❌ 它只看 aim / interactables |
| `test:smoke` | ⚠️ 只在它恰好走到书架附近时才可能暴露 |
| `test:perf` | ❌ 无关 |

本任务之所以安全，是因为**数值逐字未变**（`-3.72` / `-2.85`）—— 这是**靠人读**保证的，
不是靠判据。**后续搬 `cart-shelf`（`movingPlatforms` 读 `cartG`）与 `desk-chair`
（`movingPlatforms` 读 `chairG`）时会再次面对同一个缺口。**

> 建议（留给后续任务判断）：给 `platformBoxes` / `movingPlatforms` 的数值写一条
> 单元/快照判据（现在的布局是纯数据，可以脱离 three 断言）。
