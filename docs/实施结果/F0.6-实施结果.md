## 2. 基线值

采集口径：视口 1440×900、`?deterministic=1&stats=1`（**realtime**，不带 `frames`）、
预热 3s、采样 5s、**5 轮取中位数**。

| 指标 | 沙箱 / SwiftShader（默认） | 本机 / RTX 5060 Laptop（**GPU 增量**） | 可比性 |
|---|---|---|---|
| 渲染后端 | SwiftShader（软件） | **ANGLE D3D11（硬件加速）** | — |
| 采集质量 | ✅ 稳定（FPS 波动 7%） | ✅ 稳定（FPS 波动 11%） | — |
| 首屏时间（**冷启动 / 首访**） | 536 ms | **853 ms** | 同环境前后对比 |
| 首屏时间（**稳态中位**） | 858 ms（743–981） | **504 ms**（491–549） | 同环境前后对比 |
| 稳态 FPS（中位数） | 4.15（3.99–4.27） | **78.05**（75.78–84.49） | ⚠️ **仅同环境** |
| 冷启动 FPS（参考） | 4.33 | 105.62 | ⚠️ 仅同环境 |
| **draw calls** | **3138** | **3138** | ✅ 跨设备可比 |
| **triangles** | **86158** | **86158** | ✅ 跨设备可比 |
| geometries | 2843 | 2843 | ✅ 跨设备可比 |
| textures | 38 | 38 | ✅ 跨设备可比 |
| 着色器程序数 | 15 | 15 | ✅ 跨设备可比 |
| 场景对象数 | 5365（Mesh 1812 / Line 1907 / Points 7） | 同左 | ✅ 跨设备可比 |

完整报告：[`baseline.md`](../baseline.md)（默认）与 `docs/baseline.gpu.md`（GPU 增量），均由脚本生成。

### 2.1 三条实测结论

**① 渲染统计跨环境完全相同，FPS 差 19 倍。**
同一份代码：软件渲染 4.15 fps、RTX 5060 上 78.05 fps，而 `calls` / `triangles` **一个字节都没差**。
这就是"FPS 不能当判据、渲染统计才能"的实证 ——
`verify-f06` 已把"两份基线的 calls / triangles 必须相同"当作断言来查。

**② 冷启动与稳态的方向在两个环境里刚好相反 —— 不分开统计就会得出矛盾结论。**

| | 冷启动 | 稳态 | 谁更快 | 原因 |
|---|---|---|---|---|
| 沙箱 / SwiftShader | 536 ms | 858 ms | **冷启动快** | 持续满载渲染让 CPU 降频；冷启动那轮机器刚从空闲开始 |
| 本机 / RTX 5060 | 853 ms | 504 ms | **稳态快** | 驱动初始化（D3D11 设备、shader 编译）在冷启动一次性付出 |

如果只报一个"首屏时间"，这两个环境会给出**互相矛盾**的答案。
所以脚本先单独跑一轮冷启动（第 0 轮）**不计入**稳态统计，
质量自检里还带**逐轮趋势**检测（防降频被误读成波动）。

**③ headless 的 rAF 不受垂直同步限制。**
GPU 下冷启动测得 **105.62 fps**、稳态最高 84.49，都高于 60 ——
说明 headless 模式没有显示器刷新率上限。所以 GPU 环境下 FPS 是有区分度的参考项；
软件渲染下它只是"能跑"的量级，这也是它只做参考项的原因。

### 2.2 两次 GPU 采集的对比：质量自检确实拦住了坏数据

GPU 基线采了两次，可以作为质量自检有效性的实证：

| | 第一次（机器有并发负载） | 第二次（空载） |
|---|---|---|
| 采集质量 | ⚠️ **不稳**（FPS 波动 32% / 首屏 90%） | ✅ **稳定**（FPS 波动 11% / 首屏 12%） |
| 稳态 FPS 中位 | 81.81（76.25–102.25） | 78.05（75.78–84.49） |
| **FPS 区间宽度** | **26**（被负载撑开） | **8.7** |
| 首屏中位 | 615 ms（446–1002） | 504 ms（491–549） |
| 渲染统计 | 3138 / 86158 ✅ | 3138 / 86158 ✅ |

两次的**中位数其实接近**，但第一次的区间被并发负载撑开了 3 倍 ——
这正是"质量自检 + 多轮取中位数"的价值：**没有质量判定，那份数据看起来也能用**。

想在 GPU 上重采（例如换机器后）：

```bash
node tests/e2e/perf.mjs --gpu --rounds=5 --update
```

## 2.2 两种采集环境（profile）：GPU 那条是**纯增量**

| profile | 命令 | 产物 |
|---|---|---|
| `swiftshader`（默认） | `pnpm baseline:perf` | `tests/e2e/baseline/perf.json` + `docs/baseline.md` |
| `gpu`（增量） | `node tests/e2e/perf.mjs --gpu --rounds=5 --update` | `tests/e2e/baseline/perf.gpu.json` + `docs/baseline.gpu.md` |

**默认 profile 的文件名、路径与行为与最初方案完全一致**；GPU 采集只新增文件，
不覆盖、不改写任何既有产物 —— 因此不影响既有的回归判据与校验脚本
（`verify-f06` 只在 GPU 文件存在时才校验它，且会断言"两个 profile 的渲染统计必须相同"）。

`--gpu` 做的事只有一件：**去掉 `--disable-gpu --use-angle=swiftshader` 等开关，让 Chrome 自己挑后端**。
脚本会打印并记录实际拿到的渲染后端，**若显示 SwiftShader 就说明回落了**，那份不是 GPU 数据 ——
这条自检是必要的：headless 环境下"以为在用 GPU"是很容易犯的错。

## 3. 设计：为什么主判据是渲染统计而不是 FPS

| | 渲染统计（`calls` / `triangles` / …） | 首屏时间 · FPS |
|---|---|---|
| 取决于 | **场景构成** | CPU 负载、渲染后端、系统噪声 |
| 同代码多轮实测 | **完全一致（+0.0%）** | 波动 ±15%（首屏单轮 693–1390 ms） |
| 跨设备可比 | ✅ | ❌ |
| 在本基线里的角色 | **判据**（阈值 10%） | **参考项**（阈值 30% / 25%） |

把 FPS 当判据会天天误报；把它完全丢掉又会让报告失去"体感"。
所以基线里两者都记，但**只有渲染统计参与回归判定** —— 阈值表本身就标了哪一项是"判据"、哪一项是"参考项"。

### 3.1 钩子设计：`?stats=1` 而不是挂在 manual 分支

`J0.4` 的两个机位钩子只存在于 **manual 模式**（`?deterministic=1&frames=N`）。
但**性能必须在 realtime 下量** —— manual 模式页面不跑 rAF，量不到稳态 FPS。

所以渲染统计钩子用了另一条路径：**`?stats=1` 时由 boot 置位 `window.__CABIN_WANT_STATS`，
monolith 加载时看到标志才挂上 `window.__cabinRenderStats`**。

- 正常游玩（无参数）⇒ 页面上**不存在任何测试接口** ✓
- 与 manual 解耦 ⇒ 既能测 FPS，也能在 manual 下读统计 ✓

`verify-f06.mjs` 专门守这条契约（"要了才给""位于 manual/realtime 分支之外""boot 在加载实现之前置位"）。

## 4. 排查记录

### 4.1 快照链条多了一环

`verify-f04` 的判据是"撤销 J0.4 的改动后与 **F0.3 快照**一致"。J0.6 又改了 `monolith.js`，
于是链条变成四段：

```
after-f02 --F0.3--> after-f03 --J0.4--> after-j04 --J0.6--> 当前文件
verify-f03            verify-f04          verify-f06
```

这次是**事后补** `after-j04` 快照（正常应该在动手前复制）：

```
node scripts/oneoff/_j06-freeze.mjs
  → 撤销 J0.6 得到 after-j04；再撤销 J0.4，自检是否回到 after-f03
  → ✓ 自检通过（两条撤销规则都精确），才写入快照
```

**教训**：改 `legacy/monolith.js` 之前先冻结快照 —— 这次的"事后补"能成立只是因为撤销规则精确可验。

### 4.2 阈值分两档是实测逼出来的

第一版阈值统一取 10%。实测 `pnpm test:perf` 时：

```
✓ calls    3138 → 3138   +0.0%
✓ fps      3.59 → 3.07  -14.5%   ← 逼近 -15% 的阈值
```

同一份代码、同一台机器，FPS 差了 14.5%。于是把两类指标分开定阈值，并在报告里标注"参考项"。

## 5. 使用方式

```bash
pnpm serve            # 另开一个终端
pnpm baseline:perf    # 采集并写基线（沙箱 / 软件渲染，5 轮；约 90s）
pnpm test:perf        # 与基线比对（渲染统计阈值 10%，超了非零退出）
node tests/e2e/perf.mjs --rounds=5                          # 只采集不落盘（试采）
node tests/e2e/perf.mjs --gpu --rounds=5 --update           # 真实 GPU 采集（增量产物）
node tests/e2e/perf.mjs --gpu --compare                     # 与 GPU 基线比对
```

`?stats=1` 时页面上的钩子：

```js
window.__cabinRenderStats()
// → { frame, calls, triangles, renderLines, renderPoints,
//     geometries, textures, programs,
//     sceneObjects, sceneMeshes, sceneLines, scenePoints }
```

> ⚠️ **换机器或换渲染后端后必须重建对应 profile 的基线** —— FPS 与首屏时间不可跨环境比较。
> 渲染统计不受此影响，但基线文件是一份整体，重建更省事。
