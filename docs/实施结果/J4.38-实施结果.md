## 2. ★ 帧序：三条不相邻的帧任务合并 + 写入前移

### 2.1 原样

| 原帧任务 | 原行 | 内容 |
|---|---|---|
| `frame/72` | L806 | `magicP += ((magicOn ? 1 : 0) − magicP) × 0.012` |
| `frame/75` | L816 | `if (magicP > 0.01) { spinG.rotation.y += 0.020·magicP; innerG.rotation.y −= 0.008·magicP }` |
| `frame/76` | L820 | `glows[i].opacity = maxOp × magicP × pulse` + `scale` |

三条**不相邻**：`72` 与 `75` 之间夹着 `veil` 的 `73` 与 `candle` 的 `74`。

### 2.2 采取的做法（`J4.37` §3.3 决定的顺序）

合并成**一个** `update`，登记在 **`frame/35` 之后**（`J4.37` 定的组 9 顺序
`astro → candle → veil → star-particles` 的第一位）。内部顺序保持 `72 → 75 → 76` 不变。

**新执行序（本件相关部分）**：

```
frame/35(candle) → ★prop/astro(72,75,76) → frame/70(candle) → frame/71(candle)
                 → frame/73(veil) → frame/74(candle) → frame/77(stars)
```

### 2.3 等价性（`J4.37` §3.4 的三条判据，逐条对照）

| 判据 | 本件情况 |
|---|---|
| ① 所有 `magicP` 读者排在写者之后 | 读者 = `73`(veil) · `74`(candle) · `77`(stars) · 槽 6 光源（在 `frame/97`）· 以及本件自己的 `75`/`76`。**全部晚于新登记点** ⇒ 读到的仍是**本帧**值 ✓ |
| ② 中间任务不读不写本件对象 | 新登记点与 `frame/73/74/77` 之间只有 `candle` 的 `70`/`71`，它们读写 `candleP` / `candleWavy` —— 与本件的 `magicP` / `spinG` / `innerG` / `glows` **不相交** ✓ |
| ③ 写集合两两不交 | 本件写 `magicP` / `spinG.rotation.y` / `innerG.rotation.y` / `glows[].opacity·scale`；`candle` 写 `candleP` / `candleWavy` / `candleGlows` ✓ |

⇒ **三条判据全部满足**，且已由 **`visual` 3/3 逐字节相同**实证。

> ★ 这是本阶段**位移最大**的一次合并（`frame/72` 从 L806 前移到 L272 附近，
> 跨越 6 个帧任务；`magicP` 的写入相对 `candle` 的 `frame/74` 提前了 35 个帧任务），
> 结论零差异 ⇒ `J4.37` 的判据在"跨几十个帧任务"的尺度上同样成立。

## 6. ★ 本任务踩到的两个坑（**交接价值最高的一节**）

### 6.1 ⚠️ `serve.mjs` 是 **dist 模式** ⇒ **`visual` 必须在 `build` 之后跑**

本轮**第一次** `visual` 报"3/3 逐字节相同"，**但那是一次假通过**：`scripts/serve.mjs` 默认服务
**`dist/`（`astro build` 的产物）**，而不是源码实时转换（`serve.mjs` L12/L40 已写明）。
当时 `dist/` 还停留在**上一个任务**的产物 ⇒ 那次 `visual` 验证的是**旧代码**。

**正确的门禁顺序**（既有流程本来就是这么排的，本轮是我自己写反了）：

```
tsc → verify → ★ build → visual → smoke → perf → diag → probe
```

**暴露方式**：`build` 生成新产物后，`diag` 立刻报
`ReferenceError: glowBall is not defined`、`props` 只有 26（应为 48）、
页面 `ready` 超时 ⇒ 才查出真因（§6.2）。

> ⇒ 后续任务请**永远**把 `build` 放在所有"需要真实页面"的门禁之前；
> 若 `visual` 出现"通过得太顺"（尤其刚改完代码），先确认 `dist/` 是不是刚构建过。

**对 `J4.36` 的影响评估（已核实，结论：不受影响）**：`J4.36` 的 `visual` 同样跑在旧产物上，
但它的 **`smoke`（32/0，含"全程无未捕获页面异常"）、`probe`（7/0）、`diag`（0 错误）
全部是在新 `dist` 上执行的且全绿** ⇒ 该件的正确性结论仍然成立。
（本任务收尾后已另行回到 `dev` 补跑一次正确顺序的 `visual` 复核。）

### 6.2 ⚠️ 三个 `edit` 同时因"文件已被 `pwsh` 改过"而失败，重做时漏了一条

本轮用 `pwsh` 按行切除 18.5 整段后，紧接的三个 `edit`（import / 段导出清单 / 占位注释）
**全部**返回 `file changed since it was read` —— 因为 `pwsh` 写盘使"已读"状态失效。
重新 `read` 之后我补做了 import 与中文注释，**但漏掉了"从段导出清单删 `ctx.glowBall`"这一条**
⇒ 留下了一个**指向已删除函数**的悬空导出（§6.1 的真因）。

**这正是本项目已经犯过 7 次的那一类错误**，而且这次**静态检查（`tsc`）与 `build` 都没拦住**
（`build` 只做打包，不做未定义标识符的跨段检查；函数提升让"未定义的名字"逃过 `tsc`）。

> ⇒ **教训**：① 改文件的那一步**要么全用 `edit`、要么全用 `pwsh`**，混用时把"失败的 edit"
> 当成待办清单逐条重做，**不要凭记忆补**；② 合并/删除段之后，**必须 grep 一次被删段的
> 全部符号名**（本件漏的 `glowBall` 在 `grep glowBall` 里明明只有 4 处命中，
> 只要在删除**之后**再 grep 一次就会立刻发现 L50 的残留）。

### 6.3 保留：`magicP` 的过渡态

本件只搬了 `astro`，`veil` / `candle` / `star-particles` 仍在 `FrameBody` 与 `install.js` 里，
它们此刻读 **`ctx.astroApi.state.magicP`**（而不是各自经装配选项注入的 `astroApi`）。
**这是有意的过渡态**：等它们各自升格时，改成
`installProp(veil, { ctx: { astroApi } })` 的注入形式即可（`J4.37` §1.1）。
