## 0. 一句话结论

> ★ **不需要合成一件，也不需要拆两件 —— 拆四件，各自独立成模块。**
>
> 真正的耦合只有一处：**`candle` 的 `frame/74` 读 `astro` 的 `magicP`**。
> 只要把 `astro` 的 `update` 排在 `candle` 的 `update` **之前**，所有读者拿到的都是**本帧**的
> `magicP`，与原实现逐帧等价。

**并且发现了一个 §3.2 没有记录、但比它更要紧的事实**：

> ⚠️ **`candle` 有 4 个帧任务，其中最远的一个（`frame/35`）与次远的一个（`frame/70`）
> 相隔 35 个帧任务** —— 这是任务 D 到目前为止**最分散**的一件
> （远超 `magic-book` 的"相隔 1 个"）。它的合并可行，靠的是下方 §3.4 的读者排查。

**规模**：4 件合计约 **190 行**（`candle` ~33 · `astro` ~45 · `veil` ~20 · `star-particles` ~92），
**比刚刚完成的 `magic-book`（273 行）更小**。

## 1. 决策：拆四件（回答 §3.2 的问题）

`J4.32` §3.2 写的候选是 **"合成一件（`floor2/magic-veil` 作 owner）或拆两件"**（依 `SKIP` §4.2 的建议）。
**帧序分析之后，两个候选都不必选**：

| 方案 | 判定 | 理由 |
|---|---|---|
| **合成一件**（veil 作 owner） | ❌ **否决** | 4 件是**语义无关的陈设**（星象仪 / 夜幕 / 蜡烛 / 星空粒子），塞进一个文件违反"一件物件 = 一个文件"；且 `astro` 的 3 个帧任务与 `candle` 的 4 个全被包进来，文件会变成"帧序搬运站" |
| **拆两件** | ❌ **否决** | 拆法无法消除耦合：`frame/74`（candle）夹在 `frame/72`（astro）与 `frame/73`（veil）之间，无论怎么两两分组，都会有一组跨过另一件的帧任务 |
| ★ **拆四件** | ✅ **采用** | 帧序等价性**不需要靠同批来保证**，只需**登记顺序**正确（见 §3） |

### 1.1 `magicP` 这个共享状态轴怎么给

`magicP` 定义在 18.5（`install.js` L173），却被 **`veil`（L549）** 与 **`candle`（L556）** 读
（此外还有 `lights.js` L94 的槽 6 光源强度回调）。

**处置：`magicP` 归 `astro`（它本来就是星象仪的状态轴），另两件经装配选项取用** ——
用 `installProp(veil, { ctx: { astroApi } })` 注入，**这与 `J4.34` 的
`installProp(teapot, { ctx: { cupFactory } })` 完全同一手法**（已有先例，不是新机制）。

- `veil` 的 `update` 读 `astroApi.state.magicP`；
- `candle` 的 `update` 读 `astroApi.state.magicP`；
- `lights.js` 的两行收进各自的 `lights(s)`：`candle` 的 `strength: () => s.candleP`、
  `veil` 的 `strength: () => s.magicP`（`magicP` 届时已可由注入的 `astroApi` 读到）。

> ⇒ 这也是**批 2（含光源件）的收尾**：槽 5 / 槽 6 搬走之后，`lights.js` 将**清空**
> （`J4.18` 建立 `slot` 契约时留的最后 2 行）。

## 3. ★ 帧序全表与合并方案（**本任务的核心**）

### 3.1 四件的**全部**帧任务

| 帧任务 | `FrameBody` 行 | 件 | 内容 |
|---|---|---|---|
| `frame/35` | **L266–272** | **candle** | `for (f of candleWavy)`：`f.obj.visible = true` + `updateWavyFlame(f, time, 0.9 + 0.1·sin(11t))`（**无条件**） |
| `frame/70` | L528 | **candle** | `candleP += ((candleLit?1:0) − candleP) × 0.03` |
| `frame/71` | L532–539 | **candle** | `candleVisible = candleP > 0.02`；`f.obj.visible = candleVisible`；**条件** `updateWavyFlame(f, time, candleP × (0.9 + 0.1·sin(9t)))` |
| `frame/72` | L544 | **astro** | `magicP += ((magicOn?1:0) − magicP) × 0.012` |
| `frame/73` | L549 | **veil** | `veil.material.opacity = magicP × 0.28` |
| `frame/74` | L553–562 | **candle** | `candleGlows`：`opacity = maxOp × candleP × boost × flick`（**`boost = 0.30 + 0.50 × magicP`**）+ `scale` |
| `frame/75` | L566–569 | **astro** | `if (magicP > 0.01) { spinG.rotation.y += 0.020·magicP; innerG.rotation.y −= 0.008·magicP }` |
| `frame/76` | L574–578 | **astro** | `glows[i].opacity = maxOp × magicP × pulse` + `scale` |
| `frame/77` | L583–625 | **star-particles** | `magicParts`：`visible` + `scale` + `halo.h1/h2` + `spikes` + `tails`（**全部 × magicP**） |

**原执行序**（L528 起）：

```
candle(70, 71) → astro(72) → veil(73) → candle(74) → astro(75, 76) → stars(77)
```

### 3.2 为什么"按件合并"会出错（`J4.32` §3.2 已点出，此处确认）

- 若 **`candle` 的 `update` 登记在 `frame/70`**（含 70+71+74）⇒ **`74` 提前到 `72` 之前**
  ⇒ `74` 读到的 `magicP` 是**上一帧**的值 ⇒ **画面必变**（这正是 §3.2 记的"反之单独搬蜡烛也会让 `magicP` 读到上一帧的值"）；
- 若 **登记在 `frame/74`** ⇒ `70`/`71` 推后，`candleP` 的积分与火苗可见性都晚一帧 ⇒ 同样变。

### 3.3 ★ 采用的登记顺序

四件**各自一个 `update`**，在 `FrameBody` 里按下列顺序登记：

| 新登记点 | 件 | `update` 内含的原帧任务 | 原位置参照 |
|---|---|---|---|
| **①（最前）** | `astro` | `72` + `75` + `76` | **原 `frame/35` 的位置**（或更早） |
| **②** | `candle` | `35` + `70` + `71` + `74` | 紧随 ① 之后 |
| **③** | `veil` | `73` | 紧随 ② 之后 |
| **④** | `star-particles` | `77` | **原 `frame/77` 的位置** |

⇒ 新执行序：

```
astro(72, 75, 76) → candle(35, 70, 71, 74) → veil(73) → stars(77)
```

### 3.4 等价性论证（三条判据）

**判据 ①：所有 `magicP` 的读者都排在写者之后。**
写者是 `astro.update` 里的 `frame/72`；读者是 `veil(73)`、`candle(74)`、`astro(75, 76)`、`stars(77)`、
以及 `lights.js` 槽 6 的强度回调（在 `frame/97` 的 `lightField.update` 里读）。
**⇒ 在新序里全部晚于 ①** ⇒ 读到的都是**本帧**值 ✓（与原来完全相同）

**判据 ②：`frame/35` 与 `frame/70` 之间的几十个帧任务既不读也不写 `candleWavy`。**
`candleWavy` 的全部读者已 grep 全仓：**只有 `FrameBody` L268（`frame/35`）、L534/L537（`frame/71`）**
⇒ 两者**都在 `candle.update` 内部**，且内部顺序保持 `35 → 70 → 71` 不变 ⇒ 中间那些帧任务与本件无交互 ✓

**判据 ③：各组"写的对象"互不相交。**

| 件 | 写 | 读 |
|---|---|---|
| `astro` | `magicP`、`spinG.rotation.y`、`innerG.rotation.y`、`glows[].material.opacity/scale` | `magicOn`、`time` |
| `candle` | `candleP`、`candleWavy[].obj.visible`、火焰顶点、`candleGlows[].material.opacity/scale` | `candleLit`、**`magicP`**、`time` |
| `veil` | `veil.material.opacity` | **`magicP`** |
| `star-particles` | `magicParts[].visible/scale`、其 `halo` / `spikes` / `tails` 的 opacity | **`magicP`**、`time` |

**⇒ 除 `magicP`（已由判据 ① 覆盖）外，四件的写集合两两不交** ✓

⇒ **三项判据全部满足 ⇒ 合并等价**，且**每件都可以单独搬、单独过 `visual`**（不必同批）。

### 3.5 ⚠️ 施工图上仍须实测确认的一点

**`frame/35` 的 `f.obj.visible = true` 是"无条件置真"，而 `frame/71` 在 `candleVisible`
为假时会把 `visible` 置假** —— 两者在**同一个 `update` 内按原序执行**，语义与原实现一致。
但"`frame/35` 从 L543 附近搬到 `frame/70` 附近"是本批**位移最大**的一处（跨 35 个帧任务），
⇒ **第一次 `visual` 必须专门看这一处**（若画面有差异，优先怀疑它）。
