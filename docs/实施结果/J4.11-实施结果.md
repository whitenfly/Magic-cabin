## 0. 一句话结论

`aim`（准星 / 点击）通路中间那层 **`userData` 间接被删掉了**：
"哪条 Mesh 属于哪条交互"现在只记在注册中心的一个 `Map` 里，
`installProp` 不再造"代理根"、不再写 `userData.onClick` / `aimLabel` / `sfx`。

**命中顺序一字未变**（`magicMeshes` 仍是同一个扁平数组、仍是"一次性求交取最近"）⇒
像素 **3/3 逐字节相同**、冒烟 **32/32**（含 S5.5 第一人称点击）、探针 **7/7**（`aimMissing` 为空）。

## 1. 改的是什么（一条通路，两个来源）

### 1.1 改前的两段式

```
Interactable { id, label, onActivate, hits }
      │  installProp ⑤.2：造一个**代理根**（普通对象）
      ▼
proxy = { userData: { onClick, aimLabel, sfx, cabinProp, cabinInteraction } }
      │  registry.registerMagic(proxy, meshes)  → 写 mesh.userData.magicRoot = proxy
      ▼
Bridge.js 的 magic 源：hit.object.userData.magicRoot → 读 userData → makeTarget(...)
```

`Interactable` 自己就有 `label` 与 `onActivate`，却要**绕道对象属性**传一遍 —— 那层是纯间接。

### 1.2 改后

```
      registry.registerAim({ id, label, sfx, propId, onActivate }, meshes)
      ▼
aimOf: Map<Mesh, target>          ← 新增（magicMeshes 数组实例不变）
      ▼
Bridge.js 的 magic 源：registry.aimTargetOf(hit.object) → makeTarget(...)
```

| 文件 | 改动 |
|---|---|
| `app/Registry.js` | 新增 `aimOf` Map、`registerAim(target, meshes)`、`aimTargetOf(mesh)`；`registerMagic` 改为**内部经 `registerAim`**（从 `userData` 构造 target，**惰性**读 `onClick`）；`stats().magicPropIds` 改从 `aimOf` 派生 |
| `app/installProp.js` | ⑤.2 的两段（逐条 `hits` 的代理根 + root 兜底桥）都改用 `registerAim`，**不再写 `userData`**；兜底桥的"已有注册不覆盖"判据从 `userData.magicRoot` 改成 `registry.aimTargetOf(m)` |
| `systems/interaction/Bridge.js` | `magic` 命中源改走 `registry.aimTargetOf(hit.object)`；音效仍在 `resolve` 里播（`ctx.SND.play(t.sfx)`），与 `fireMagic` 行为一致 |

### 1.3 ★ 为什么 `magicMeshes` 不能改成"按目标分组求交"

原实现是 `raycaster.intersectObjects(magicMeshes)` —— **一次性对全部求交、取最近命中**。
若改成"遍历每个 target、各自求交再比较"，跨组的最近命中就会算错（`J2.6` 已声明
"命中顺序 = 注册顺序"是语义的一部分）。

所以本任务**只换"命中之后怎么找回回调"**，不动"怎么命中" —— 这也是"像素零差异"与
"探针 7/7"能同时成立的原因。

### 1.4 `regWobble()` 这类调用方一行未改

"在 `build` 里自己注册"的对象（衣柜挂衣）仍走 `registry.registerMagic(root, meshes)`：
它内部**从 `userData` 构造 target 再交给 `registerAim`** —— 于是两种来源在同一个 `Map` 里合一。
`onActivate` 是**惰性**的（调用时才读 `ud.onClick`），所以"先注册、后设 `onClick`"的既有写法仍然有效
（`prop.test.mjs` 里那条测试正是这个顺序）。

## 2. ★ 判据跟着形态走（5 条断言改写，语义不变）

改动让 5 条断言失败 —— 它们断言的是**旧形态**（`userData.magicRoot`），而不是行为：

| 断言（旧） | 断言（新） | 守的仍是同一件事 |
|---|---|---|
| `mesh.userData.magicRoot === root` | `registry.aimTargetOf(mesh)` 存在且 `propId` 正确 | raycast 命中后能问出"属于哪条交互" |
| `root.userData.onClick` 是函数 | `target.onActivate` 是函数 | 激活通路可用 |
| `root.userData.aimLabel === '…'` | `target.label === '…'` | 准星提示语义化 |
| `proxy.userData.cabinInteraction === '…'` | `target.id === 'magic:…'` | 每条交互各有自己的记录 |
| `hanger.__mesh.userData.magicRoot === hanger` | `aimTargetOf(hanger.__mesh)` 是挂衣自己的 | root 兜底桥不覆盖已有注册 |

涉及两个文件：`tests/unit/prop.test.mjs`（4 条）、`tests/unit/kernel.test.mjs`（1 条）。
**一条都没删、一条都没放宽** —— 与 `J4.7` 改造 `segments.test.mjs` 是同一条原则。

### 3.1 性能：`readyMs` / `fps` 超标是**环境噪声**（A/B 对照为证）

**主判据是渲染统计**（只取决于场景构成，与渲染后端无关）—— **全项 +0.0%**，
`magicMeshes` 也仍是 744 ⇒ 命中集合与绘制没有变化。

`readyMs` 是**冷启动单轮**采样。按 [`J3.1`](J3.1-实施结果.md) §3.2 的口径做了 **A/B 对照**
（把本次改动 `git stash` 掉、重建、重测）：

| 组 | `readyMs` | `fps` | 渲染统计 |
|---|---|---|---|
| 基线 | 858 ms | 4.15 | — |
| B（**含** C3）第 1 次 | 1288（+50.1%） | 3.18（−23.4%） | 全 +0.0% |
| B（含 C3）第 2 次 | 1297（+51.2%） | 3.35（−19.3%） | 全 +0.0% |
| **A（`stash` 掉 C3）** | **1330（+55.0%）** | **2.71（−34.7%）** | 全 +0.0% |
| B（含 C3）复测 | 1382（+61.1%） | 2.54（−38.8%） | 全 +0.0% |

**去掉改动的 A 组不比含改动的 B 组好，甚至更差** ⇒ **与本改动无关**。
采集质量自检也报出「首屏时间轮间波动 **57%** —— 采集期间可能有其它程序占用 GPU / CPU」。
（本轮连续跑了十几轮 headless Chrome —— 冒烟 ×4、像素 ×5、探针 ×4、性能 ×5 —— 机器持续降频。）

> **没有改性能基线**：那是"放宽判据"。判据的强度不动，只把事实与对照数据记在这里。

## 7. 结论

C3 是 `J4` 债务清单里**最抽象**的一条 —— 它不修任何一个用户能看见的东西，
删掉的只是一层"为了兼容旧契约而存在的间接"。

它的价值在**下一个人**身上：想加一条新的准星交互、或想改"命中之后怎么找回回调"时，
只需要看**一个 `Map` 与一个查询入口**，而不是在 `installProp` 的代理根、`registerMagic` 的
`userData` 写入、以及 `Bridge.js` 的三处读取之间来回对照。

另外这一轮把一条方法学又用了一次：**判据跟着形态走，强度不降** ——
5 条断言改写、一条没删；而性能那项超标，用 **A/B 对照**证明是环境而非改动，
**没有去动基线**。
