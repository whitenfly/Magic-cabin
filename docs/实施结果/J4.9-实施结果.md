## 1. 为什么现在能做了（`J3` 的两条阻塞如何被解除）

`_j3-b6-report.md` 给出的两条独立阻塞，以及它们现在的状态：

| | `J3` 时的阻塞 | 现状 |
|---|---|---|
| **A** | 室外区段**整体位于 `installProp` 定义之前**（装配器 TDZ）⇒ 插入装配调用必抛 `ReferenceError` | ✅ **已解除**：`J4.7` 把 `outdoor` 与 `installer` 变成两个**有序的段**，`outdoor` 在 `installer` **之后**执行 |
| **B** | `addStatic` / `staticFillGeoms` / `staticEdgeGeoms` / `yardSpotFree` 串成**不可切分的一条链**，且「花」与「萤火虫」被 `animate()` 直接引用 | ✅ **已解除**：跨段引用一律走 `ctx`（`ctx.flowerMats` / `ctx.ff*` / `ctx.signSideMat`），`animate()` 现在只是 4 行调度骨架 |

**但"不可切分"这条结论本身仍然成立**：`collector(addStatic) + 树 + 草 + 石 + 树桩 + 花 + mergeStatic`
必须**同件** —— 收集器 → 散布 → 一次性合并，拆开就改变 `scene.children` 构成与合并策略。
所以本任务兑现的是报告 §4.2 的**唯一干净切法：2 件**，而**不是**当初设想的 7 件细粒度。

`installCabin.js` 改成两次调用，**紧接 `installHouseShell` 之后**（顺序不可变 ——
`outdoorRng()` 的调用序列、`scene.add` 的先后、`mergeStatic` 消费的两个数组都压在它上面）。

`yardSpotFree` 提取成独立模块是报告 §4.2 的硬要求：两件都要用它，
**不可复制实现**（复制会让两处漂移）。

### 2.2 ★ 本次**没有**改成 `defineProp`（刻意的保守选择）

两件现在是"整段形态"（`installXxx(ctx, app)`），不是 `defineProp`。理由：

1. **`ctx.*` 的导出一个都不能删** —— `houseShell` 段经 `ctx.addStatic` / `ctx.yardSpotFree` /
   `ctx.grassClumpStatic` 引用它们；`systems/weather/WeatherSystem.js` 的每帧分支依赖
   `ctx.flowerMats` / `ctx.signSideMat`；`app/scene/FrameBody.js` 的萤火虫帧任务依赖 `ctx.ff*`。
   升格为 `defineProp` 会让这些键的**存放位置**改变（进 `state` 或 `parts`），进而牵动那两处每帧分支。
2. C7 的 DoD 是"**室外片不再是一条不可切分的链**" —— 段形态已经达成；
   升格为 prop 属**另一件事**（"每帧分支归位"，见 §5 遗留）。

> 一句话：这次的目标是**降低不可切分性**，不是**改架构风格**。把两件事混在一个任务里，
> 像素判据就说不清"差异是谁造成的"。

### 2.3 ★ 三个坑（两个被 `build` 拦下，一个只有页面能拦）

| # | 现象 | 根因 | 谁拦下的 |
|---|---|---|---|
| **①** | `Failed to fetch dynamically imported module` | `import { scene } from '../../../app/rng.js'` —— `world/outdoor/` 到 `app/` 是 **两级**，我写了三级 | ✅ `astro build`（它真的解析模块图） |
| **②** | 同上（换了个位置） | 提取 `yardSpot.js` 时直接复制原行，`const STUMPS` / `function yardSpotFree` **都没有 `export`** | ✅ `astro build` |
| **③** | 页面 `ReferenceError: outdoorRng is not defined` | `fireflies` 的段体原来住在 `installOutdoorYard` 的作用域里，`outdoorRng` 是**那个函数**顶层的绑定；切出来成独立件之后必须自己重新绑定 | ❌ **`tsc` 与 `build` 都不查** —— 只有页面起不来 |

> ③ 与 `J4.7` 的 `clock` import 是**同一类**：**切分函数边界会切断词法作用域**，
> 而 `allowJs + checkJs:false` 的 `tsc` 对"未定义的自由变量"**一声不吭**。
> 所以 `J4` 每次切开一个函数边界，都必须跑一次**页面诊断**（`_j3-diag.mjs`，20 秒）
> 或像素回归（3 分钟）—— 这是这套流水线的固定动作。

## 5. 遗留（本次**发现**的新债务，与 C6 同类）

调研时发现：**「花 / 路牌材质 / 萤火虫不透明度」的每帧分支住在 `WeatherSystem.js` 里**
（`L461–L468`）：

```js
ctx.signSideMat.color.copy(ctx.FILL.uniforms.uColor.value);
ctx.signFaceMat.color.copy(ctx.FILL.uniforms.uColor.value);
for (const f of ctx.flowerMats) f.mat.color.copy(f.base).multiply(_amb);
ctx.ffOpacity += (ffTarget - ctx.ffOpacity) * Math.min(1, dt * 1.2);
ctx.ffUniforms.uOpacity.value = ctx.ffOpacity;
```

- **成因**：`J4.7` 的段切片按**行区间**切 —— 这几行在原 monolith 里落在 weather 段的区间内。
- **危害**：光照/材质的每帧更新挂在"天气"模块上；`_amb`（环境光色）是它们的隐式输入。
- **与 C6 同源**：C6 的 8 个 `lightField.register` 也住在 `WeatherSystem.js`（见 `J4.8-实施结果.md` §7）。
- **不动的理由**：把它们移进各自物件的 `update` 会**改变帧顺序**（它们依赖 `_amb` 先算出来），
  而帧顺序 = 画面。要动就得连 `UpdateScheduler` 的登记顺序一起设计 —— 那是 `J4.10`（C6）的活。

**其它遗留**：两件仍是"段形态"而非 `defineProp`（见 §2.2）；
`outdoor/signpost`（路牌）与栅栏+蘑菇仍留在 `world/house/shell.js` 的段里
（报告 §4.2 说它们"补一行注释标题后是最省事的搬迁候选"—— 但在新架构下它们已经住在模块里，
搬迁的收益只剩"统一成 `defineProp`"）。

## 7. 结论

C7 是 `J4` 债务清单里"看起来最不可能"的一条 —— `J3` 当时判定它**整片不可搬**并留了一份
详细报告。而 `J4.7` 的段切片把它的两条阻塞**顺手解除了**（装配器 TDZ → 段序；跨段引用 → `ctx`），
于是本任务只剩下"按报告给的切法动手"。

交付面是 246 行 → 两件 + 一个共享模块，而**判据仍然是像素逐字节相同**。
另外把 `J4` 的四个搬迁期工具正式退役（对象已不存在），并留下"每帧分支归属错位"这条新债务
给 `J4.10`（C6）一并处理。
