## 4. ★ 两处不相邻 tick 的**合并方案**（本任务的核心结论）

`FrameBody.js` 里这两行**不相邻**（中间夹着 `updateCal(dt)`）：

```
L492  ctx.updateBook(time, dt);
L494  ctx.updateCal(dt);          ← 计划板台历（**不属于本件**）
L502  ctx.updateGlyphs(time, dt);
```

**一件物件只有一个 `update`** ⇒ 必须合并。**本任务给出的方案**：

### 方案（与 `J4.20`/`J4.28`/`J4.33` 同一模式）

1. **登记位置取靠前的那一处**（`frame/??` @ L492）；
2. **把 `updateGlyphs` 提前**到该位置执行；
3. **等价性判据**（每条都可 grep 复核）：
   - ① `updateGlyphs` 只依赖 `glyphObjs` 与 `time` / `dt`，**不依赖中间那两行**（`updateCal` 改的是台历自己的状态）；
   - ② 它**不写**任何被 `updateCal` 读的量，`updateCal` 也**不写** `glyphObjs` / `camera`；
   - ③ 它与 `updateBook` 之间的**唯一联系**是 `spawnGlyphs` 往 `glyphObjs` 里 push ——
     而 `updateGlyphs` 的语义是"老化的先消失、新生的下一帧才动"，**提前一帧执行**会导致
     "本帧新生成的符文在本帧就被老化一次"。
     ⚠️ **这是唯一需要实证的地方**：若画面因此变化，则改为**把 `updateGlyphs` 留在原位**、
     用**两处调用同一个 `tick`**（`installProp` 返回的 `tick` 是幂等句柄，可被调用两次）——
     但更干净的做法是**让 `update` 内部按相位排序**：
     `update(dt, time, s, ctx)` 里**先跑 `updateBook` 段的"非生成"部分、再跑 `updateGlyphs`**。
4. **落地顺序建议**：先按"登记在 L492 位置、`updateGlyphs` 提前"实现并跑 `visual`；
   **若红**，再按 ③ 的备选改（两处调用同一 tick）。

> ★ 这条"唯一需要实证的地方"是**本轮调研的直接产出** —— 它把下一轮的试探范围从
> "整件 259 行"缩小到"一个可以一次 `visual`（约 3 分钟）验证的判断题"，
> 与 `J4.15` §2.5 给 `magic-clock` 的那个捷径同一性质。

## 5. `rng` 顺序（照抄 `SKIP` §4，本任务复核）

- `spawnGlyphs(n)`：每个符文 **4 + 3 + …**，`SKIP` 记的是
  **每次 4 + 3 = 7 次**（符号、颜色、位置 3 次）+ 每条 4 次的 `v / life / ph / rs` ⇒ **共 11 次**；
- `updateGlyphs`：每帧**可能 1 次** `runtimeRng()`；
- ⚠️ **这些都必须保持调用次数与顺序不变**（不变量 `N8`），否则"运行期瞬态"的序列会变。
- 本件**不使用种子随机源**（`floor1Rng` / `skyRng` 等）—— 只用 `runtimeRng`。

## 6. 为什么本轮只交施工图（与 `J4.15` 同一处置）

按同一配方把 `magic-book` 完整搬完，需要**读约 350 行 + 写约 250 行**（几何 96 行 + 状态机 89 行 +
符文系统 95 行 + 两处 tick 接线）。本轮**已完成其中约 250 行的读取与全部设计**，
但剩余的读取与产出**超出本轮的安全余量**。

⇒ 按 `J4.15` 的先例（"把搬不动变成一份可交接的施工图，而不是把红状态写进历史"），
本轮把成果固化为本文 —— **代码零改动、门禁全绿**（§7），
下一轮可直接从 §7.1 的"下一步"接着做。
