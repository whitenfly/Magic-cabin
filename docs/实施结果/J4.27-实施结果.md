**`18.17`（`floor2/decor-loop`）不是一个物件，不应也不能升格 `defineProp` —— 它从"待搬物件清单"里关闭。**

它实质上是两件事的**旧住址**，而那两件事**现在各有归属**：

| 原来在 `18.17` 里 | 现在在哪 |
|---|---|

| 便签编辑器（DOM） | `systems/ui/editors/NoteEditor.js`（`installNoteEditor`，段 11）—— **早已归位** |

剩下的是一个**两条驱动路径的调度壳** —— 它是**主循环收口的剩余项**，不是陈设。

## 1. 为什么它不是物件（三条判据，逐条对应 `defineProp` 的必填字段）

| # | 判据 | 事实 |
|---|---|---|
| ① | **`build` 是必填项**，而它没有任何几何 | `updateNewDecor()` 一行 `scene.add` 都没有 —— 它是**调度器**，不是陈设 |
| ② | `update` 由调度器按**登记顺序**每帧调用 | 它有**两条驱动路径**：realtime 由自己的 `requestAnimationFrame` 自驱；manual 由 `FrameBody` 的 `frame/101` 调用。搬进某个物件的 `update` 等于**把其中一条拔掉** |
| ③ | 物件的 `state`/`update` 只依赖装配环境 | 两条路径都要读 `clock.mode`，而 **`clock` 不在装配环境里** |

> 这三条 `J3` 已在 `floor2-decor-loop.SKIP.md` §2 写过；本任务**逐条复核，结论不变**。

## 2. `J4.7` 之后的现状核实（本任务的实际工作）

`J4` 已把主循环收成调度骨架，所以必须重新核实现状 —— 三条：

### 2.1 便签编辑器**早已归位**（`SKIP` §3 记的归属问题**不属本组**）

`SKIP` §3 说"便签编辑器（L4246 起）直接读 18.8 计划板的私有量 `notes` / `noteEditing` / `drawNote`"，
归属应留给 `J4`。**复核结果**：

- 编辑器已抽成 `src/cabin/systems/ui/editors/NoteEditor.js`，由 `installCabin` 的**段 11** 安装；
- `floor2/install.js` 里只剩**计划板自己的**入口 `openNoteEditor(i)`（L736）—— 那是 `18.8` 的内部函数，
  **归 `floor2/board` 的搬迁任务**处理（`N3`：由 `features/**` 经 `mounts` 认领 `parts`）。

⇒ 「便签编辑器」这一项**从 `decor-loop` 的判定里划出去**，交给 `board` 组。

### 2.2 `SKIP` §2 末段那条"必须留着"的约束**已经过时**

`SKIP` 原文：

> **`let decorLastT = 0;` / `let mirrorDirtyT = 0;` 两行必须原地留着** ——
> `scripts/verify-f03.mjs` 的第 ⑥ 项断言这三行**连续存在**。删掉它们静态门禁立刻变红。

**复核结果**：该断言作用于 **F0.3 完成时的快照**（`verify-f03.mjs` 文件头 L14 原文：
"⚠️ 检查对象是 **F0.3 完成时的快照**，不是当前文件"），**不是当前 `src`**。
而段切片之后这两行已变成 `ctx.decorLastT` / `ctx.mirrorDirtyT` ⇒ **那条约束对当前代码不适用**
（实测：本任务全程 `verify` 58 项通过，`verify-f03` 亦然）。

### 2.3 `ctx.mirrorDirtyT` 是**死变量**（本任务刻意不删）

镜面的节流计时已随 `mirror.js` 升格迁进它自己的 `state.dirtyT`（`J3` 的 B4），
此后 `ctx.mirrorDirtyT` 在 `install.js` 里**只有一次赋值、无任何读者**（已 grep 确认，全局命中仅 1 处）。

**处置：不删。** 理由：删它属于"清理"，与本次判定无关；而它现在是一处**有记录的历史痕迹**
（注释里已写明它是死变量、以及那条过时约束的来龙去脉）。

### 6.2 ★ `candle` 与 `magic-veil` 是**耦合件**（本任务调研时的副产品发现）

原计划做 `candle`，读代码时发现它**不能单独搬**：

```js
// FrameBody 的 frame/74（蜡烛辉光）
const boost = 0.30 + 0.50 * ctx.magicP;      // ← 读的是 magic-veil 的状态量
for (const cg of ctx.candleGlows) { cg.m.material.opacity = cg.maxOp * ctx.candleP * boost * flick; … }
```

`magicP` 由 `frame/72`（`magic-veil` 的平滑）更新，而 `frame/74` **排在它之后**
⇒ 把蜡烛的 `update` 合并到它自己的几何分支位置（`frame/35`）会让 `magicP` 读到**上一帧的值**
⇒ **画面必变**。

**⇒ 结论：`candle` 与 `magic-veil` 应当同批搬迁**（或先搬 `veil`），
`lights.js` 的槽位 5 / 6 是它们的 `slot`。
（`candle` 的"三处每帧合并"本身也要单独论证 —— 见 `frame/35` / `frame/71` / `frame/74`。）

### 6.3 主循环收口的剩余项

**两条驱动路径的合并**（`decorLoop` 的 rAF 与 `frame/101`）仍未做。合并需要同时满足：

1. **realtime 节流不变**：`dt` 来自 `performance.now()` 差值（与 `clock.dt` 解耦）；
2. **manual 定格不变**：像素回归靠 `frame/101` 逐帧推进。

它与 `magic-clock` 的升格**耦合**（`drawClock()` 是 `updateNewDecor` 里最后一段"原生的"）
—— 建议在 `magic-clock` 专项里一并处理。
