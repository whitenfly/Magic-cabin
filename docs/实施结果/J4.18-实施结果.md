# J4.18 · 光源前置：`lights(s)` 契约与槽位定序 —— 实施结果

> 编号 **`J4.18`** ｜ 分支 `task/J4.18-lights-strength-contract` ｜ `--base=0.4.0`
>
> **任务 D 的工作包 ①（前置）。** 它是 6 件含光源物件（`hanging-lantern` /
> `crystal-ball` / `kotatsu` / `magic-circle` / `moon-plant` / `cauldron-fire`）
> 能搬家的**唯一前置条件** —— `J3` 当年把这 6 件判为"搬不动"，病根就在这里。

---

## 0. 一句话结论

`defineProp` 的 `lights()` 声明**此前是一份半成品契约**：`installProp` 拿到它之后
只调 `registry.registerLight()` —— 那只是往一张**诊断表**里塞一条，光照场 `lightField`
**根本收不到** ⇒ 物件声明的灯**不会亮**。

而槽位又**绑定在注册时机**上（`槽位 = 第几个 register`），8 盏灯全在
`world/lights.js` 一次注册完（段 03 之后），物件却在段 08–10 才装配
⇒ 把一盏灯的注册跟着物件搬走，它的槽位必然改变；shader 的闪烁相位含 `float(i)`
⇒ **槽位一变画面就变**。

本任务把这两件事一起解决：**`lights()` 真进光照场** + **槽位由声明里的 `slot` 决定、
与装配时机无关**。8 个既有注册改用显式 `slot: 0…7` 作为新契约的第一个用户，
画面**三机位逐字节相同**。

## 1. 病根（`J3` 留下的两条"走不通的路"）

`scripts/oneoff/_j3-specs/floor1-hanging-lantern.SKIP.md` 与 `floor1-crystal-ball.SKIP.md`
把病根写得很清楚 —— 两件都记了**同样的两条走不通的路**：

| # | 走不通的路 | 为什么破判据 |
|---|---|---|
| 1 | **`lights()` 里重注册这一盏** | 光照场已在 `world/lights.js` 注册过它（槽位 0），再注册一次会变成 9 盏、且新的一盏排在第 8 个槽 ⇒ 破 `defineProp` 纪律 3、破像素判据 |
| 2 | **把状态漏回 monolith**（`xxxApi.state.lanternLit`） | 需要人工改 `ptLantern += …` 那一行，超出应用器能力，且把"物件状态"漏回 monolith（违反 `N7`） |

两条路的**共同前提**是同一个事实：**灯的注册与灯的强度都不在物件手里**。

### 1.1 实测确认的第 3 条（`J4.18` 新发现）

读 `app/installProp.js` 的 ⑥ 时发现，`lights()` 分支的现状是：

```js
if (typeof prop.lights === 'function') {
  for (const src of prop.lights(state, c2) || []) {
    registry.registerLight({ ...src, prop: prop.id })   // ← 只进诊断表
  }
}
```

`registry.registerLight()` 只是 `lights.push(source)`（见 `app/Registry.js`），
**没有任何一行把它送进 `lightField`**；`lightField` 的 8 个来源是
`world/lights.js` 里那 8 行 `lightField.register(...)`（以及事后回灌 registry 的循环）。

**⇒ 即使解决了槽序问题，搬走的灯仍然不会亮。** 这是 `J3` 的两份 SKIP 都**没有**覆盖到的
第三处缺口 —— 因为它只有在"真的去搬"的时候才会暴露（`J3` 没搬，所以没撞上）。

`app/scene/PropInstaller.js` 的装配环境 getter 清单（L27–L62）里**也没有 `lightField`**
⇒ 物件连"往哪儿注册"都拿不到。

## 2. 做了什么（5 个文件）

### 2.1 `core/lighting/PointLightSource.js` —— 加 `slot`

新增可选字段 `slot`（整数）。声明它 ⇒ 槽位由它决定；省略 ⇒ 沿用原语义
（按注册顺序追加）。同时校验类型（非整数一律 `TypeError`）。

归一化后 `slot: Number.isInteger(spec.slot) ? spec.slot : null`，
`null` 与省略同义 —— 与 `defineProp` 的"`null` 即没有这项"风格一致。

### 2.2 `core/lighting/LightField.js` —— `sources` 变成"按槽位索引的数组"

`register()` 有两条落点路径：

| 声明 | 落点 | 语义 |
|---|---|---|
| `slot: i` | `sources[i]` | **槽位由声明决定**，与"第几个注册"无关 |
| 省略 `slot` | `sources[sources.length]` | 原语义：注册顺序 = 槽位顺序 |

两条路径**结果同构**：8 个都不声明 `slot` 时落点仍是 `0…7`（原行为一个字节没变）；
全声明 `slot: 0…7` 时落点是**同一批索引、同一批对象**。

**冲突与越界都显式失败**（不静默换掉先到者）：

- 槽位被占 ⇒ 后来者**不注册**，返回占位者 + `warn`（静默覆盖会让"谁在亮"取决于装配顺序）；
- 槽位越界 ⇒ 拒绝 + `warn`。

**`unregister` 由 `splice` 改成 `delete`（留洞）**：索引就是槽位号，`splice` 的移位会让
后面所有灯**集体换槽**（相位含 `float(i)` ⇒ 画面立刻变）。空洞是合法状态
（`update()` 的 `if (!s)` 分支写成强度 0）。`stats()` 相应改为"先滤洞再映射" ——
**问法没变**（"注册了哪些灯"），只是实现适应了稀疏形态。

### 2.3 `app/installProp.js` —— ⑥ 真的接进光照场

```js
if (typeof prop.lights === 'function') {
  const lf = c2.lightField
  for (const src of prop.lights(state, c2) || []) {
    if (lf && typeof lf.register === 'function') lf.register(src)   // ★ 真的亮
    registry.registerLight({ ...src, prop: prop.id })               // 诊断计数照旧
  }
}
```

**向后兼容**：拿不到 `lightField` 时（如单元测试的最小环境）自动降级为原来的行为，
只登记 registry。既有测试 `installProp：七步装配` 正是这种情况，**一字未改即通过**。

### 2.4 `app/scene/PropInstaller.js` —— 把 `lightField` 交给物件

新增一行 getter：`propTool('lightField', () => ctx.lightField)`。
`lightField` 在 `installWorldLights`（段 03 之后）就已建好，早于本段，惰性 getter 安全。

### 2.5 `world/lights.js` —— 8 个注册显式声明槽位

每行加 `slot: 0…7`（与原 `PP[0]…PP[7]` 下标一一对应）。
**位置 / 颜色 / 半径 / 强度 / yMin / yMax 一字未改。**

同时给回灌 registry 的循环加 `if (src)`（注销现在会留洞，洞要跳过）。

> ⚠️ **这 8 行本身没有搬走** —— 本任务只做**通道**。搬迁是工作包 ③（批 2）的事：
> 届时删掉对应行、由物件的 `lights()` 声明顶上，`slot` 号**原样带走**。

## 3. 判据与证据

本任务是**通道**改动，画面零差异 ⇒ "零差异"本身**不能**证明新机制在工作
（可能是死代码）。所以按方法论第 2 条，**先证明判据遇到缺陷会红**，再宣称判据有效。

### 3.1 ★ 证伪实验：交换槽位号，画面**必须**红

**做法**：把 `world/lights.js` 里 `floor1/lantern` 与 `floor1/cauldron-fire` 的
`slot` **互换**（`0 ↔ 1`），**注册的代码行顺序一个字不动**。

这个实验能一次性区分两种世界：

| 若 … | 预期 |
|---|---|
| `slot` 真的决定槽位 | 两盏灯互换槽位 ⇒ **画面变** |
| `slot` 被忽略（仍走 push） | 注册顺序没变 ⇒ **画面不变** |

**实测结果**（`node tests/visual/compare.mjs`）：

```
✓ default-fixed   sha256 相同（182422 B）
✗ floor1-indoor   sha256 不同
    像素差异 0.3947%（5115/1296000）  最大通道差 3
    差异区域 x107–1202 y253–899（1096×647）
    ↳ 灯具/坩埚都在一楼 ⇒ 只有一楼机位变，另两个机位不变（符合预期）
✓ floor2-desk     sha256 相同（138670 B）
```

**改回后复验：3/3 机位逐字节相同。**

⇒ 结论有两条，都是**实证**而非推断：

1. **`slot` 真的决定光源在 uniform 里的下标** —— 新机制不是死代码；
2. **像素回归真的抓得住"槽序错"** —— 这正是 `J3` 当年最怕的那类回归，
   现在它有了一条**被证明会红**的判据。

### 3.2 单元判据（194 → 201，新增 7 条）

| 文件 | 新增 | 守什么 |
|---|---|---|
| `tests/unit/lighting.test.mjs` | 5 | ★ **等价性**（显式 `slot: 0…7` 与原"按注册顺序填充"产出**逐位相同**的 uniform）· **定序**（乱序注册仍落自己的槽）· 冲突被拒 · 越界被拒 · `slot` 类型校验 |
| `tests/unit/prop.test.mjs` | 2 | ★ **`lights()` 真的进光照场**（此前只进 registry）· ★ **`strength` 闭包惰性读物件 state**（改 `state.ptLantern` ⇒ 槽位强度立刻跟着变，不是装配期快照）· **晚装配的物件照样占住自己的槽位**（= 6 件能搬家的前提） |

`unregister` 那一条既有断言按方法论第 1 条**改写**（不是删除/放宽）：
问法仍是"移除后 b 还在不在"，但换成新形态的等价问法，并**加了一条更强的断言** ——
`b` 没有被挤到 0 号槽（`splice` 会，`delete` 不会）。

## 6. 遗留与交接（给工作包 ③「批 2：6 件含光源件」）

### 6.1 ✅ 已经就绪的

1. **契约**：物件写 `lights: (s) => [createPointLightSource({ id, slot, position, color, radius, strength: (time) => …, yMin, yMax })]`
   即可 —— `installProp` 会把它注册进光照场。
2. **槽位**：`slot` 号从 `world/lights.js` **原样带走**（`lantern=0` / `cauldron-fire=1` /
   `magic-circle=2` / `kotatsu=3` / `crystal-ball=4` / `candle=5` / `magic-veil=6` / `moon-plant=7`）。
3. **强度**：`strength` 闭包读 `s.ptXxx`，`s.ptXxx` 的平滑搬进物件的 `update`，
   `s.lanternLit`（等）搬进 `state`；`WeatherSystem.js` L619 的初值也搬进 `state`。

### 6.2 ⚠️ ★ 搬迁时必须一起处理的**帧顺序**约束（本任务发现，尚未处理）

`ptXxx` 的每帧平滑目前**不在**灯里，而是住在 `app/scene/FrameBody.js` 的
**5 个独立帧任务**里（各占一行）：

| 帧任务 | 位置 | 内容 |
|---|---|---|
| `frame/92` | `FrameBody.js` L1045–1048 | `ctx.ptLantern += ((ctx.lanternLit ? 1 : 0) - ctx.ptLantern) * 0.07` |
| `frame/93` | L1050–1053 | `ctx.ptKot += … * 0.07` |
| `frame/94` | L1055–1058 | `ctx.ptMc += … * 0.055` |
| `frame/95` | L1060–1063 | `ctx.ptCb += … * 0.055` |
| `frame/96` | L1065–1068 | `ctx.ptPlant += … * 0.055` |
| **`frame/97`** | L1070–1073 | **`ctx.lightField.update(time, dt)`** ← 读上面这五个量 |

**⇒ 搬灯的 `update` 时，它的执行位置就是这五个任务的位置**：必须在 `frame/97`
**之前**（否则本帧读到的是上一帧的强度），并且与原来的同帧相对次序一致。

这条约束已**写进 `world/lights.js` 的文件头注释**（按 `J4.14` 的做法：
帧顺序是函数语义的一部分，只写在文档里迟早丢）。

### 6.3 ⚠️ `lights()` 的返回值类型被**收紧**了

新的 `lightField.register()` 会校验 `typeof source.strengthOf === 'function'`
（它只接受 `createPointLightSource()` 的产物）。**以前返回任意对象都能过**
（因为只进 registry，没人校验）。搬灯时请用 `createPointLightSource`。

### 6.4 未处理（本任务范围外）

- **`candle`（槽位 5）与 `magic-veil`（槽位 6）** 的强度量 `candleP` / `magicP`
  住在 `floor2/install.js`（L70 / L423 初值）与 `FrameBody.js`（L872 / L888 平滑），
  与那 5 件同源但**不在** `J4.15` §1.2 的 6 件清单里（它们在 `floor2`，是 `J4.15`
  清单之外的物件）。搬不搬由工作包 ③ 定范围。
- `world/lights.js` 里**没有任何一行被删** —— 8 个注册原样留着，槽位号已就位。
