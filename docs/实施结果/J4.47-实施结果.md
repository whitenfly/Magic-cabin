## 0. 一句话结论

碰撞表**第一次有了可自动重跑的判据**：

> ★ 页面在 `?stats=1` 下暴露 `window.__cabinCollisionDigest(probes)`，返回 **1081 项**结构化数值摘要；
> ★ 判据 `pnpm test:collision`（`tests/e2e/collision.mjs`）与基线逐项比对，**失败时直接指出是哪件家具的哪条边、差多少**；
> ★ 两条负例实测：改错盒坐标 0.1 ⇒ **红**（差 −0.100000）；改坏 `groundAt` 判据逻辑 ⇒ **红**（27 项）。

## 1. 问题：三条门禁**原理上**都看不见碰撞

| 门禁 | 为什么看不见 |
|---|---|
| `test:visual` | 三个机位是**没人去走的定格帧** —— 碰撞盒错 0.1 不改一个像素 |
| `j3-probe` | 只问"交互入口存不存在"（`magicMeshes` / `aimLabel`），不问"能不能站上去" |
| `verify-migration` | 只数**标识符出现次数**，不解释任何数值 |

而 `J4` 阶段搬走 35 件物件时，碰撞表被**大量改动**过：

- 多个盒的坐标改成从 `world/layout.js` 取值（不变量 N9：坐标只有一个来源）；
- 5 组**移动平台**改成读**装配记录里的部件实例**（`ctx.stoolsApi.parts.stoolA` / `cartShelfApi.parts.cartG` /
  `deskChairApi.parts.body` / `diningChairsApi.parts.chairs` —— 引用错了就整块失效）。

这些改动此前**只有人工论证**兜底（"数值逐字未变 + 用的是同一个实例"）。
**论证不是判据 —— 它不能被自动重跑**，下一个人也无法复核。

## 2. 判据形态

### 2.1 钩子（`src/cabin/app/scene/SceneLoop.js`）

沿用 `J0.6` 的约定：**只在 `?stats=1` 时暴露**（正常游玩路径上不存在这个接口）。

```js
window.__cabinCollisionDigest = function (probes) { … }
```

返回六个字段：

| 字段 | 内容 | 抓什么 |
|---|---|---|
| `platformBoxes` | 17 个固定碰撞盒的 `[x1,z1,x2,z2,top,bot]` | 坐标 / 尺寸被改动 |
| `activePlatforms` | 加上 10 个**移动平台**后的完整表（27 项） | 物件的**引用或初始位置**错了 |
| `ground` / `stairs` / `collide` / `rails` | 五个纯函数在**测试给定探测点**上的输出 | 数值没变、但**判据逻辑**被改坏 |

**三个设计取舍**（都写进了代码注释）：

1. **结构化数值，不是哈希** —— 用户拍板的理由正是"失败时要能定位"。实测负例里它直接给出了
   `固定盒「灶台旁固定木台」的 x1：基线 -1.84 → 现在 -1.94（差 -0.100000）`。
2. **探测点由测试传入** —— 世界坐标常量属**测试资产**，不进产品代码
   （沿用 `J0.4`「机位表不进产品代码」的边界；`src/cabin/app/poses.js` 因此当年被拒）。
3. **浮点只比到 1e-6** —— 避开 `0.30000000000000004` 这类噪声，同时远小于任何有意义的碰撞误差。

### 2.2 判据脚本（`tests/e2e/collision.mjs` · `pnpm test:collision`）

- 与 `tests/baseline/collision-digest.json` **逐项比对**，展平成 `路径 → 数值`；
- 失败时把下标**翻译成家具名**（`固定盒「二楼衣柜」的 top`），并给出**差值**；
- ★ **同时比对探测点表本身** —— 改探测点 = 改判据，必须显式 `--record` 重录，
  不能悄悄放宽（这条是防"把判据改绿"的元判据）。

## 3. ★ 判据的覆盖度是**负例逼出来的**

这一节值得单独记：**第一版判据是瞎的，是负例当场揭穿的。**

第一版探测点只有 **8×8 直角网格**（128 点）。负例测试"把 `groundAt` 的
`r < 1.20` 改成 `r < 1.10`"（**判据逻辑被改坏**）时 —— **判据照样绿**。

原因：网格点的 `r = hypot(x, z)` 取值集合是 {0.707, 1.581, 2.121, …}，
**没有一个落在 (1.10, 1.20) 里** ⇒ 那次改动对所有探测点毫无影响。

⇒ 探测点重选为「**半径环 × 角度扇区**」：

- **半径**取 `groundAt` / `railCollide` 里**出现过的每一个分界值**（0.10 · 0.30 · 0.98 · 1.12 · 1.14 · 1.20 · 1.24 · 1.25 · 1.27…，各带 ±0.01 邻域）；
- **角度**取扇区边界（18 / 30 / 60 / 62 / 160 / 300…）；
- **栏杆**探测点按半径分界**双向**跨越（内→外、外→内）× 三个高度带。

| 探测点 | 数量 |
|---|---|
| `ground`（极坐标 18×19 + 直角网格 8×8×2） | **470** |
| `stairs`（含 30 / 300 边界两侧） | 17 |
| `collide` | 21 |
| `rails`（3 组半径分界 × 8 角度 × 3 高度 × 双向） | **144** |
| 摘要总项数（含 27 个盒 × 6 字段） | **1081** |

> **教训**：判据的"灵敏度"不能用直觉担保 —— 只有"故意做错必须变红"能证明它。
> 这一次它证明的**不是判据有效，而是判据无效**，然后才把它修对。

**未做的事**（明确边界）：

- **没有断言具体位置的返回值**（用户选的是摘要形态）—— `groundAt(x,z,y)` 的第三个参数 `curY`
  参与多处判定，硬编码用例会随布局改动而脆。
- **没有接进 `release.mjs done` 的自动门禁链**（那条链是 `typecheck + verify + build`）。
  `test:collision` 与 `test:cart` / `test:mirror` 一样，属于**需要真实页面**的门禁，
  按现有惯例由人工/CI 在 `build` 之后跑。
- **没有覆盖 `collideXZ` 依赖的 `ctx.solidBoxes` / `DOOR_BOX` 的数值本身**：
  它们不是 `platformBoxes` 的一部分，但**其效果**已由 21 个 `collide` 探测点间接覆盖。
