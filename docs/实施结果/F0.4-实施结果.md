## 2. 为什么非做不可

`improve/05` 的 U3 判定：**67 件物件 × 8 步 SOP 的搬迁成本估算，只有在截图回归全自动的前提下才成立**；
而 `F0.4` 恰恰没做，且 `J3` 的 DoD（像素回归全绿）依赖它。结论是"**列入 G0 必做，不是可选项**"。

三个前提缺一不可：

| 前提 | 消除什么 | 状态 |
|---|---|---|
| `F0.2` 种子随机（`?deterministic=1`） | 场景布局的随机性（树 / 石 / 星空 / 粒子） | ✅ |
| `F0.3` 可步进时钟（`&frames=120`） | 动画相位的时间不确定性 | ✅ |
| **`J0.4` 固定机位（`&cam=…`）** | **观察点的不确定性** | ← 本文 |

## 3. 设计

### 3.1 机位 = 纯观察量（不碰玩法）

一个机位就是一座**相机位**：`cam = [px, py, pz, lx, ly, lz]`（位置 → 注视点，世界坐标）。

**为什么不写成「玩家位置 + 视角模式」**：那会引入重力、碰撞、平台判定一整套游戏逻辑，
画面会随落点是否卡进家具而变。相机位是纯观察量 —— 在 `J2`（`CameraRig`）与 `J3`/`J4`（物件与系统搬迁）
重写相机之前，它是最稳的观测锚点。

`cam: null` 表示**不做任何覆盖**：那份画面就是玩家打开页面看到的默认固定视角。

### 3.2 小屋形态也是观测条件

场景默认是**剖切模式**（省略的墙与屋顶用虚线示意，便于从外面看到室内），完整外观要显式打开
（菜单里的「小屋」按钮）。因此机位表还要声明形态（`?house=full|cutaway`）。

三个基线机位统一取 `full`（完整小屋）。

### 3.3 机位数据**不进产品代码**（架构不变量 N9）

机位表住在 `tests/visual/poses.js` —— 它是**测试判据**，与 `baseline/` 同住一个目录才不容易漂移。
产品代码只认识"六个数 + 一个开关"：

```
tests/visual/poses.js  ──拼 URL──▶  ?cam=…&house=…  ──▶  boot.js  ──▶  monolith 的钩子
```

`N9` 要求"坐标系数字必须来自 `cabin/world/layout.js`"，产品代码**不该为了测试携带一组固定观察点**。
`verify-f04.mjs` 里有一条断言专门守这件事：`boot.js 不含世界坐标常量`。

### 3.4 机位是**算出来的**，不是试出来的

相机 `fov = 50°`（垂直）、视口 16:10 ⇒ 水平半角 ≈ 36.7°，深度 `d` 处覆盖半宽 ≈ `0.746 × d`。
二楼家具分列前后两端，主体是后部的**大床**（x 最左 `-3.08`）与**书桌**（x 最右 `3.72`），相距 6.8m：

| 相机 z | 到家具带深度 | 覆盖半宽 | 结果 |
|---|---|---|---|
| 0.0 | 2.5m | 1.87m | 大床、书桌**两端都被裁掉** |
| 1.7 | 4.2m | 3.13m | 大床仍被左边缘裁掉大半 |
| **2.95** | **5.5m** | **4.10m** | **两端都完整入画** ← 采用 |

相机高度 `4.55`（离二楼地板 `3.12` 之上 1.43m）是**上界**：再高就贴到屋顶内表面（檐口 `eaveY = 4.4`、
屋脊 `ridgeY = 6.6`），天花板会吃掉半张画面。

> 这组数字由**视觉模型审查截图后反推**得到 —— 见 §6.1。

## 4. 工具链（`03` §7 的移植表逐项落实）

| 资产 | 原型 | 落点 | 说明 |
|---|---|---|---|
| 零依赖 CDP 客户端 | `_probe/cdp.mjs` | **`tests/e2e/cdp.mjs`** | 200 行直连 CDP：精确视口、轮询等 `data-cabin="ready"`、连拍多机位、收集页面报错 |
| 逐帧像素差分思想 | `_probe/probe4.mjs` | `tests/visual/compare.mjs` | 差异**比例 + 区域包围盒**（"哪一块变了"比"变了"有用） |
| 材质分类字符图 | `_probe/classify.mjs` | **`tests/visual/view.mjs`** | 终端里的"文字化视觉"：亮度图 / 边缘图 / 差异图 |
| 差异分布图 | `_probe/diffmap.mjs` | 同上 | `.` 相同 / `-` 轻微 / `+` 中等 / `#` 明显 |

**为什么不用 `chrome --screenshot`**：它只能靠 `--virtual-time-budget` 赌时间、视口受窗口边框影响、
每个机位都要冷启动一次浏览器（≈15s），而且页面报错完全静默。CDP 四样都能做。

**为什么不用 Playwright**：本工程零依赖是硬约定（`serve.mjs` / `verify-*.mjs` 都只用内置模块），
Node 22+ 自带 `WebSocket` 与 `fetch`，够了。

## 6. 排查记录：一次误判与它的代价

### 6.1 机位是"评审"出来的，不是拍脑袋定的

第一版二楼机位（相机贴桌面）被判定为**不可用**：相机几乎与桌齐平、上方被树墙封死、浑天仪被画幅裁切。
随后用视觉模型对**三轮共 19 张候选图**逐一评审（每轮都要求给出"可执行的相机调整建议"），
才收敛到现在的三个机位。评审同时纠正了一个**统计误判**（见 §6.2）。

### 6.2 ★「二楼右侧墙面没有渲染」—— 结论是**没有这回事**，问题在统计指标

**现象**：二楼机位截图右侧是一大片白，看起来像"墙没画出来"。

**实测证据**：

| 测法 | 边缘率 | 深色描边像素 | 最深像素值 |
|---|---|---|---|
| 正对右墙 `x=+4`（`full`） | 5.96% | 0.763% | 16 |
| 正对左墙 `x=-4`（`full`，**常驻墙**，作对照） | 5.45% | 0.780% | 16 |
| 贴近右墙 1.5m（`full`） | 3.59% | — | 16 |
| 同上（`cutaway`，右墙不存在，看到室外树林） | 6.24% | — | 16 |

- 最深像素值 **13–16**，正是描边材质 `MAT = 0x111111` ⇒ **描边一直在正常渲染**；
- 右墙与左墙的数据**几乎相同** ⇒ 四面墙渲染一致，不存在"右墙特殊"。

**根因**：白墙 = 「白色填充 + 每根原木一圈描边」。原木直径 0.3m，在 3.8m 处只占屏幕约 76px，
于是墙面是**一大片白 + 几条细线** —— 这是线稿风格的正常观感，不是缺失。

**真正被修掉的是统计代码**：原 `analyzeImage()` **只按水平差分**判定边缘，
而叠木墙的木纹、地板线、横梁**全都是横向的** —— 于是"一面有木纹的白墙"被统计成"空白"（0.07%），
把一次查询变成了"渲染缺失"的假警报。

```js
// 修复：同时看水平与垂直差分（tests/visual/png.mjs）
let strong = false
if (x + 1 < width) { /* 水平差分 > 30 */ }
if (!strong && y + 1 < height) { /* 垂直差分 > 30 */ }
if (strong) edge++
```

> **教训**：判据本身也会错。当"数据"与"人眼"矛盾时，先把测量方式摊开看一遍 ——
> 这次是测量方式错了，而不是画面错了。

## 7. 使用方式

```bash
pnpm serve                # 另开一个终端（零构建兜底路径，受限环境下唯一可用的服务方式）
pnpm verify:visual        # ★ DoD：连续 3 轮，轮间零差异
pnpm test:visual          # 与基线比对（搬迁/改动后）
pnpm test:visual:additive # 新增式改动：允许恰好 1 个机位有差异
pnpm baseline:visual      # 重建基线（需人工审查画面）
node tests/visual/view.mjs <png> --cols=100          # 终端里看构图
node tests/visual/view.mjs <png> --diff <baseline>   # 终端里看差异分布
```

**判据**：

| 情形 | 判据 |
|---|---|
| 搬迁式改动（物件模块化） | 全部机位 **sha256 相同**，任何差异都是 bug |
| 新增式改动（场景里原本没有的东西） | **只允许 1 个机位**有差异，人工审查后更新基线 |

### 手动复现某个机位

```
http://127.0.0.1:5173/index.html?deterministic=1&frames=120&house=full&cam=0,1.6,3,-1.6,1.1,-1.2
```

| URL 参数 | 作用 |
|---|---|
| `?deterministic=1` | `F0.2`：运行期随机切为确定 |
| `&frames=120` | `F0.3`：手动时钟，定格到第 120 帧 |
| `&cam=x,y,z,lx,ly,lz` | **`J0.4`**：固定机位（位置 → 注视点） |
| `&house=full\|cutaway` | **`J0.4`**：小屋形态（完整外观 / 剖切） |

定格完成后写入 DOM 供脚本断言：`data-cabin-cam` / `data-cabin-house` /
`data-cabin-frames` / `data-cabin-still-repaint` / `data-cabin-scene-digest` / `data-cabin-clock`。

> ⚠️ **需要真实浏览器**：受限沙箱禁止命名管道时，Chrome 的 Mojo IPC 会以
> `FATAL: platform_channel.cc … 拒绝访问 (0x5)` 退出。这是环境限制，不是脚本问题。

## 8. 与后续阶段的关系

- **`J1.5`（Astro 落地）** 的 DoD 明确要求"截图回归与 `J0.4` 基线一致"——
  若 `J1.5` 后画面有差异，**先修 `J1.5`，不要改 `cabin`**（[`03`](../BuildPlaning/03-渲染通道与构建选型.md) §5.5）。
- **`J2`/`J3`/`J4`** 的每个批次都以"像素回归零差异"作为 DoD。
- **`J0.5` 冒烟**可直接复用 `tests/e2e/cdp.mjs`（它已具备求值、等待、截图、报错收集）。
