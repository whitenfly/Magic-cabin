### 1.2 ★ 单文件产线的一个真实缺陷（已定位并修复）

收尾时发现 `dist-single/` 的 3D **在 HTTP 托管下也起不来** —— 不是环境问题，是产物缺陷：

```
TypeError: Cannot read properties of null (reading 'addEventListener')
ReferenceError: Cannot access 'yA' before initialization        ← yA = three 的打包导出
```

症状有一个很好认的特征：**canvas 已经建出来了**（`canvas: true 1440×900`，说明 WebGL 上下文成功），
却没有 `data-cabin="ready"`，且 `window.THREE` / `__cabinStepFrame` 全是 `undefined`。

**根因**：`build.rollupOptions.output.inlineDynamicImports: true`。
它把整张模块图（`boot.js` 里的 `await import('./legacy/monolith.js')` + three）塌缩进一个 chunk，
执行顺序被打乱 ⇒ three 的导出在声明前被访问（TDZ）。

**修复**：去掉这个开关。产物从 1 个 chunk 变成 2 个（`index-*.js` 10 KB + `monolith-*.js` 745 KB）；
修复后 **3D 正常启动、零页面错误、截图回归逐字节相同、冒烟 28/28 全绿**。

> ⚠️ **要记住的是**：`J1` 时期的 `vite --mode single` **也带着这个开关**，
> 所以这条产线**在此之前从未被端到端验证过**。`OD-2` 拍板"保留双管线"时，
> 它名义上存在、实际不可用 —— 这正是"保留一个没验证过的产物"的风险。
>
> 现在追加了一条**反向断言**（`verify:j15`：`inlineDynamicImports` 必须**不在**），
> 防止后人"觉得单文件就该塌缩"而把它加回来。
>
> 诊断工具：`node scripts/oneoff/probe-page.mjs <url>`（报告 3D 卡在哪一步）。

## 3. 两个"文档没写、实现必须自己定"的决定

### 3.1 岛的写法：`client:only` 在本项目里用不了

路线图与 `03` §5.4 都写的是"3D 走单个 `client:only` 岛"。实际落地时，这个指令在**没有前端框架**的项目里不成立：

| 写法 | 结果 |
|---|---|
| `client:only="cabin"` | 构建报 `NoClientOnlyHint` —— Astro 要求 hint 必须是**真实的前端框架渲染器**（React/Vue/Svelte…），本项目一个都没有 |
| `client:load` | 构建报 "Astro components do not render in the client and should not have a hydration directive" |
| **不加任何指令** ✅ | Astro 组件里的 `<script>` 本来就是"只在浏览器执行、编译成独立模块被页面引用"，**天然不做 SSR**，正是"一个岛"要的语义 |

**所以岛仍然是一个**：全站唯一 import `cabin/boot.js` 的地方就是 `CabinMount.astro`（门禁第 20 项断言这一点）。
想显式声明加载时机，由组件内部读 `cabin.config.foyer`（`preload` 立即 / `button` 等用户推门）决定，
而不是靠 hydration 指令。

> ⚠️ 岛**不 import `src/main.js`**：`main.js` 是零构建路径的入口（它自己 `void bootCabin()`，不导出任何东西）。
> 岛直接 `import { bootCabin } from '../cabin/boot.js'` —— 指向的是**同一个函数**，不新增第二个真源。

### 3.2 门厅：一份 DOM，靠显示位切换；`?bare=1` 给回归测试

`01` 与 `ArtLine-Part/03` §8.3 要求"HTML 先出 + `<noscript>` 降级"。实现时发现两件事：

1. **`<noscript>` 里再写一份列表是错的**：爬虫与阅读器拿到的是"另一份"内容，两份必然漂移。
   正确做法是**同一份 DOM**，靠 CSS 决定显示位：`#cabin-foyer` 由 Astro 构建期渲染成纯 HTML，
   禁 JS 直接可读（验收 `BB8`）；开 JS 时 3D 就绪后由 `CabinMount` 把它摘掉。
2. **3D 就绪后门厅必须真的从 DOM 里摘掉**（不是 `display:none`）：
   否则它会继续抢滚轮与指针事件（`cabin.css` 自己定了 `body { overflow: hidden }`，门厅再叠一层滚动区就会打架）。

`?bare=1` 是给**像素回归**用的"纯 3D"开关：门厅整块不渲染，页面回到与 `J0.4` 基线完全相同的起点。
它**不是测试后门**：3D 的启动、`?deterministic` / `?cam` / `?house` 的解析全部照旧走同一条产品路径，
只是不叠一层文字。零构建路径不认识这个参数，多一个 URL 参数对它无害 —— 于是**同一条测试命令对两条产线都成立**。

## 4. ★ 一个必须记录的坑：`astro/loaders` 的 `glob()` 在本项目里会让 `astro sync` 崩溃

`01` 与 `src/content/README.md` 都建议用 Astro 惯例的 `glob()`。实际不可用：

```
[GenerateContentTypesError] `astro sync` command failed to generate content collection types:
  require is not defined
  at eval (.../picomatch@4.0.7/node_modules/picomatch/index.js:6:14)
  at ModuleRunner.directRequest (vite/dist/node/module-runner.js)
```

**成因链**（在最小的空白 Astro 7.3.2 工程里复现过，与本项目代码无关）：

1. `syncContentCollections` 用 Vite 的 **ModuleRunner** 执行 `src/content.config.ts`；
2. 该 config 一旦 `import { glob } from 'astro/loaders'`，`astro/loaders` 就被 Vite **外部化**而非内联打包
   —— 实测此时 config 里的 `glob` 直接变成 `not defined`；
3. 于是 `glob()` 这条路径不可用 —— 这就是本阶段改用 `markdownDir()` 的**唯一**理由。

> ### ⚠️ 2026-09-14 更正：当时的第 3 条把两个问题混成了一个
>
> 本文件原先在这里写着"外部化的模块被 `eval`，而 `picomatch` 是 CJS ⇒ 没有 `require` 就抛错"，
> 并据此写下"`vite.ssr.noExternal` 无效，试过两种组合都不生效"。**这个结论是错的**，
> 而且它导致 `astro.config.mjs` 里加上了三键"兜底"（`ssr.noExternal: ['picomatch']` +
> `optimizeDeps.include` + `ssr.optimizeDeps.include`）—— 那三键**本身就是** `pnpm dev` 一直崩溃的原因：
>
> - **内联（`noExternal` / `optimizeDeps.include`）** ⇒ ModuleRunner `eval` 这个 CJS 包 ⇒
>   `require is not defined`（**崩溃**）；
> - **外部化（什么都不配）** ⇒ 交给 Node 的 `import()` 走 CJS↔ESM 互操作 ⇒ **正常**。
>
> 两者报错文本一模一样（都指向 `picomatch/index.js` 的 `require is not defined`），
> 所以极易被当成同一个问题"修"。
>
> **实测**：把三键全部移除后，`astro dev` 正常启动（2.4s）、三个路由 200、
> `?deterministic=1&frames=30` 下 3D 就绪且页面无异常；`astro build` 同样正常（8 页）。
> 验证脚本：`node scripts/oneoff/probe-dev-3d.mjs`。
>
> **`markdownDir()` 仍然需要**：那是第 2 条（`glob` 变成 `not defined`）的问题，与 picomatch 无关。

**采用的替代方案**：`src/blog/loaders.js` 的 `markdownDir()` —— **零第三方依赖**：

- 只用 `node:fs` / `node:path`，用**带 `@vite-ignore` 的动态 `import()`** 取用（这样 Vite 不改写，请求直达 Node）；
- 自己递归列 `*.md` + 解析 front-matter（**有意限制**为 `src/content/README.md` §3 记录的那套子集：
  标量 / 行内数组 / 块状数组 / 一层嵌套对象；不支持多行字符串与锚点 —— 真需要时 Zod 会先报字段类型错，不会静默产出错数据）；
- 正文交给 Astro 自己的 `renderMarkdown()`，校验交给 Astro 自己的 `parseData()`（Zod）——
  **Markdown 管线与 schema 校验这两件"值钱的事"仍然是 Astro 在做**。

**等价性**：entry id 规则（相对路径去扩展名）、递归子目录、动态增删条目、dev 下的 watcher 注册都与 `glob()` 一致。
若上游修掉这个外部化问题，把 `content.config.ts` 里的 `markdownDir(...)` 换回 `glob(...)` 即可，`loaders.js` 可整体删除。
（门禁会守住这一点：一旦有人把 `astro/loaders` 写回 config，`verify:j15` 立刻失败并给出原因。）

OD-2 拍板"保留双管线"。**修复了 §1.2 那个 TDZ 缺陷之后**，这条产线的真实状态是：

| 能力 | 状态 |
|---|---|
| 3D 在 HTTP 托管下启动 | ✅ `data-cabin: ready`，零页面错误 |
| `J0.4` 截图回归 | ✅ 3 机位**逐字节相同** |

| 产物形态 | 🟡 "物理单文件"名不副实：`index.html` + `assets/index-*.js` + `assets/monolith-*.js` + `assets/style-*.css`（**4 个文件**，不是 1 个） |
| `file://` 直接双击 | ⚠️ **做不到**（见下） |

### 5.1 为什么"双击即玩"做不到：`file://` 下模块脚本被 CORS 拦

`file://` 页面的 origin 是 opaque，浏览器把每个本地文件都当成跨源，
**`<script type="module">` 必须过 CORS ⇒ 被拦**。四条路都实测过：

| 配置 | `file://` 下的结果 |
|---|---|
| `type="module"` + Vite 注入的 `crossorigin` | `canvas: false`，**页面零报错**、画面空白（最坏的失败模式） |
| 去掉 `crossorigin`，保持 module | 仍 `canvas: false` ⇒ **module 本身是主因**，不是属性 |
| 经典脚本（`format: 'iife'`）+ `defer` | `canvas: true`，但 3D 未就绪：`Cannot access 'QT' before initialization`（塌缩成单个 IIFE 后踩 TDZ） |
| module 格式 + 把 JS/CSS 内联进 HTML | 内联脚本本身语法正确（`node --check` 通过）、DOM 里也在，但**整段脚本不执行** |

**结论**：这是浏览器规则，换输出格式绕不过去。真要"双击即玩"，`J8.6` 需要走
"内联 + 模块脚本"的组合（内联模块脚本不受 CORS 限制），代价是产物涨到约 1 MB 且失去增量缓存。
**`J1.5` 只负责把边界量出来，不在这一阶段决定这笔取舍。**

复现命令与全部证据：`node scripts/oneoff/probe-single-file.mjs`（真实 Chrome + CDP 读 `data-cabin`）。

### 5.2 附带发现：受限文件策略下真实浏览器起不来（已用提权验证）

`J1.5` 收尾时文件策略一度从 `danger-full-access` 回落到 `workspace-write`，随后回归测试全部以
`浏览器调试端口 9333 未就绪（可能端口被占用）` 失败 —— 这个报错**看不出真正原因**。

`scripts/oneoff/probe-cdp.mjs` 把"环境拒绝"与"项目坏了"分开：受限策略下系统临时目录**可写**（✓）
但 headless Chrome **起不来**（✗）；**提权后 370 ms 就起来了**（✓）——
证实原因是 Chrome 的进程间通信依赖**命名管道**，而受限策略禁止打开命名管道。
**与 `pnpm serve`（零构建兜底）存在的原因完全同源。**

> **由此得到一条操作规则**：`astro build` / `astro dev` / `vite build` 与三条回归测试
> 在受限策略下**都会失败**，且失败信息具有误导性（看起来像"端口被占用"）。
> 受限时应当改用：`verify:j15 --built` / `verify-migration` / `verify-f02` / `f03` / `f04` / `f06` /
> `typecheck` / `pnpm serve:legacy`（人工看画面）；
> 需要跑真浏览器时，直接申请放宽而不是反复重试。

> **为什么现在保留它而不是删掉**：OD-2 的原意是"保住零部署的分发形态"。
> 它现在做不到"双击即玩"，但仍然做到了"一个文件就能带走、放到哪都能开"。
> 把真实边界写清楚、把定稿留给 `J8.6`，比"假装它能用"更符合这份规划的性格。

### 8.1 ★ 一次自伤事故与它的恢复（必须记住的教训）

**事故**：实施过程中我用 PowerShell 的 `-replace` 处理 `tests/e2e/perf.mjs`，
触发 UTF-8 → GBK → UTF-8 的往返损坏：

- 313 处字符丢失（`U+FFFD`），其中约 **50 处是换行符** —— 注释与代码行被并成一行 ⇒ **语法错误**；
- 丢的不只是非 ASCII：被吞掉的还有引号、反引号、`$`（模板插值符）、`*`、`)`。

**当时的处置**：项目不是 git 仓库，磁盘上也搜不到第二份副本，只能**按产物反推重建**
（`docs/baseline.md` / `baseline.gpu.md` 正好是该脚本 `renderMarkdown()` 的输出，可当 oracle）。
重建后所有可被机器验证的部分都对上了（`node --check` 通过、模板能逐字节复现两份报告、`verify-f06` 41/41），
但**有一处纯注释用词无法 100% 还原**（第 498–500 行的冷启动说明，原文 4 字被吞）。

**最终处置（用户提供备份后）**：从 `FrontProj/Backup/Magic-cabin_Backup_202609132221.zip`
（备份时间 2026-09-13 22:21，**早于 `J1.5` 开工**）恢复该文件的**原始 26317 B 版本**，
再重新施加 `J1.5` 的三处入口适配。当前状态：

| 检查 | 结果 |
|---|---|
| 原始字节数 | ✅ **26317 B**（与备份逐字节相同） |
| `U+FFFD` / 典型乱码字 | ✅ **0 / 0** |
| `node --check` | ✅ 通过 |
| `verify:f06`（含它对 `perf.mjs` 的 5 条断言） | ✅ **41 / 41** |
| 端到端真实运行 `pnpm test:perf` | ✅ **全部 +0.0%**，采集质量"稳定" |

**所以 §8 上表里"重建"这件事的结论要更正为**：`perf.mjs` 的**内容已完全还原**，
不再是"接近但可能有措辞差异"。

> **教训（写给后续会话）**：
> **绝不要用 PowerShell 的 `Get-Content` / `Set-Content` / `-replace` 触碰 UTF-8 源码。**
> 那一轮操作里编码被默认按 ANSI 处理，读进来是乱码、写回去就把字符烧掉了。
> 改文本一律用 `read` / `write` / `edit` 文件工具；确需脚本处理时，
> 必须显式 `[System.IO.File]::ReadAllText($p, [System.Text.Encoding]::UTF8)`
> 与 `New-Object System.Text.UTF8Encoding($false)` 成对使用，并且**改完立刻做编码自检**：
> `U+FFFD 计数 = 0` 且 `node --check` 通过。
>
> **另一条**：备份是这类事故唯一的兜底。`FrontProj/Backup/` 下的三个 zip 是**只读资产**，
> 本项目自身也应尽快纳入版本控制（当前无 `.git`，这是 `J1.5` 反复提到"摘要基线代替 `git diff`"的根本原因）。
