## 2. ★ 三条纪律

### ① 单写者

只有 `store.set()` 会写 `localStorage`；模块之间靠 `subscribe` 得知变化。
不允许绕过 store 直接 `localStorage.setItem`（验收 `BB17`）—— 否则 `J9` 的模块各写各的，
"谁最后写谁生效"会变成随机行为。

### ② 前缀 `cabin:`

小屋现在是独立站点，但将来同域部署时前缀是唯一的隔离手段
（博客侧可能也用 `localStorage` 存阅读进度 —— `J6.9` 的进度所有者是博客侧，P6 单写者）。

### ③ ★ `?deterministic=1` 下**完全不碰存储**

```js
const app = createApp({ persist: !opts.deterministic })
```

这条不是可选项：截图回归与冒烟必须**环境无关**。
否则"上一次测试把视角切到了第一人称"会变成下一次像素比对的差异，
而这与"代码有没有改坏"毫无关系 —— 一个**会骗人的判据比没有判据更糟**。

代价是：`?deterministic=1` 下设置**不生效也不保存**。这是刻意的取舍 ——
确定性模式是"测试模式"，不是"带有存档的游玩模式"。

## 3. 顺带修掉的一处重复：小屋形态的三个应用点

搬迁前同一段逻辑写了三遍：

| 位置 | 场景 |
|---|---|
| `houseToggle` 的 click | 用户点菜单按钮 |
| `__cabinSetFullHouse` | `J0.4` 的截图测试钩子 |
| （第三个在初始化路径里） | —— |

现在收敛为一个函数：

```js
function applyFullHouse(on) { fullHouse = !!on; houseToggle.classList.toggle('on', fullHouse); fullHouseGroup.visible = fullHouse; dashedGroup.visible = !fullHouse; }
```

- 菜单按钮：`applyFullHouse(!fullHouse)` **+ 写 store**
- 测试钩子：`applyFullHouse(on)`，**不写 store**（避免测试污染用户设置）

这属于"顺手修掉既有问题"（参考 `J1.5` §8 的先例），并且是 `J2.8` 能做到单写者的前提。

## 5. 新增测试：11 项（`tests/unit/store.test.mjs`）

持久化最容易出的三类问题，每组都有测试：

| 类别 | 测试 |
|---|---|
| **脏数据** | `coerceSetting` 钳制超范围数字、拒绝非法枚举、拒绝 `"true"` 字符串当布尔；载入时 `999 → 1`、非法枚举退回默认、坏 JSON 丢弃 |
| **测试被污染** | `persist: false` 时**一行都不写存储**；拿不到后端时降级为内存而不抛错 |
| **写入风暴** | 值没变时 `set` 返回 `false`、不通知、不写盘；重复设同一个值只通知一次 |
| 契约 | `subscribe` 的 `{ key, value, prev }` 载荷；`'*'` 通配；退订后不再收到；`reset` 单项/全部 |

## 8. 一句话总结

**小屋第一次有了"记忆"** —— 音量、视角、小屋形态刷新后不再丢（风险 `R4` 消解），
而这条记忆被两条线保护着：一条是 `cabin:` 前缀与单写者（不与别人抢同一个键），
另一条是 `?deterministic=1` 下彻底关掉持久化（测试判据永远说真话）。
