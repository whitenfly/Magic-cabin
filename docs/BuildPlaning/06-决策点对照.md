## 1. OD-1 · 是否采用 Astro

### 问题

站点那一半（`/posts/<slug>/`、`/tags/`、`/archive/`、`/about/`、`/search/`、`rss.xml`、`sitemap.xml`）
用什么建？**3D 那一半与此无关**，它始终是原生 ESM。

### 选项

| 选项 | 含义 | 短期工时 |
|---|---|---|
| **① 采用 Astro**（`output: 'static'`）★建议 | Astro 管内容站与门厅；3D 走单个 `client:only` 岛 | `J1.5` 3–4 人日；`J5` **3–5** 人日 |
| ② 回到 Vite MPA | 自写约 300 行 SSG 脚本 + 多入口 plumbing | `J1.5` **取消**；`J5` 增至 **4–6** 人日 |

### 净账（`03` §5.2，必须诚实看）

| 项 | 人日 |
|---|---|
| Astro 省下的手工工作（schema / 静态页 / RSS / 多入口分块 / 面板按需 hydrate / 插件零翻译） | **+7.5** |
| Astro 自身落地成本（工程重搭 / 双路由设计 / 学习调试） | **−4 ~ −5** |
| 单文件产线的额外成本（若 OD-2 选①） | **−1** |
| **短期净账** | **≈ ±0 ~ +2.5（基本持平）** |

**所以选 Astro 的理由不是"现在能省人日"，而是三件长期的事：**

1. **同一个框架支撑 18 个模块的面板按需加载** —— 决策 4（一模块一目录增量开发）需要一个
   "每模块按需 hydrate"的机制，Astro 的 `client:visible` / `client:idle` 直接可用；
2. **与 Firefly 同栈 ⇒ remark/rehype 插件与配置编排方法零翻译移植**（决策 5 直接照搬，这是最大的一笔长期收益）；
3. **内容站那一半的维护成本长期交给框架**（SEO / RSS / 图片 / 搜索 / 路由），而不是自己维护一套 300 行脚本。

### 对 3D 那一半的影响：**零**

- `src/cabin/**` **一行不改**，通过 `CabinMount.astro` 里的一次 `client:only` 挂载；
- 架构不变量 `N12`：3D 侧不得 import `*.astro`；Astro 侧不得 import `cabin/**` 的实现；
- 而且**现在有安全网**：`J0.4` 的像素基线就是 `J1.5` 的回归门禁 ——
  若 `J1.5` 之后画面有差异，**先修 `J1.5`，不要改 `cabin`**（`03` §5.5）；
- 若 `J1.5` 整体失败，**整体 revert 回 Vite**，`J0`/`J1` 的成果不受影响（风险 `R25`）。

### 反方论据（诚实）

> 如果作者更看重"**工程轻量、完全可控、不引入新框架**"，回到 Vite MPA **完全可行**：
> 两者总工时接近，差别在长期形态。代价是 `J2.5` 的配置编排方法要自己设计一套
> （Firefly 那九条方法就没有现成参照了）。

### 拍板后的动作

- 选 ①：`J1.5` 按 `03` §5.5 落地；`04` §3 的配置编排方法可直接照搬 Firefly。
- 选 ②：删除 `J1.5`；`01` 的 `J5` 工时改为 4–6；`03` §5 标注作废；`04` §3.1 需自行设计。

## 2. OD-2 · 是否保留「双击即玩」的单文件产物

### 问题

现在 `pnpm build:single` 能把所有资源内联成**一个 HTML**，双击即玩、零部署。
**Astro 不便于产出"相对 base + 全内联"的 HTML** —— 这是选 Astro 的一个已知代价。

### 选项

| 选项 | 含义 | 成本 |
|---|---|---|
| **① 保留双管线** ★建议 | Astro 管站点；另留 `vite.single.config.ts` 只用于生成单文件 | **+1 人日**（`J8.6` 定稿） |
| ② 放弃 | 只保留 Astro 的静态产物 | 0 |
| ③ 只在发布时手工产出 | 手工跑一次旧产线 | 0（但不可复现） |

### 取舍

- **收益**：保住"零服务器、零部署、双击即玩"的分发形态 —— 对一个**完全独立的小屋博客**来说，
  这个形态有实际价值（发给朋友、离线看、当作品集附件）。
- **风险**：两条产线长期可能漂移（画面/行为不一致）。
  **缓解很直接**：单文件产物同样跑一遍 `J0.4` 的截图回归 —— 基线已经在了，多跑一次的成本几乎为零。

### 与 OD-1 的耦合

- 若 OD-1 选 ①（Astro）：本项决定是否额外维护 `vite.single.config.ts`；
- 若 OD-1 选 ②（Vite MPA）：**本项自动为"保留"**（现有产线还在），成本 0。

## 3. OD-3 · 长文兜底策略

### 问题

方案 B 的书页有容量上限。原型实测：**29 块 / 2190 有效字符 → 5 页内容**，即**约 440 字/页**。
一篇 **20000 字**的文章 = **45 页** —— 原型自己把这列为"翻几百次页不现实"（§7 第 2 条）。

### 选项（`03` §6）

| 选项 | 做法 | 评价 |
|---|---|---|
| **① 阈值 + 混合** ★建议 | 页数 ≤ **12**（≈5000 字）→ 纯方案 B（在书页里读）；超出 → 3D 仍是那本书（封面/书脊/翻页动效都在），但"走进书页"后切**全屏滚动阅读层** | 保住方案 B 的全部收益，长文退回原型方案 C 的阅读层形态；两套视图**共用同一份 DOM**（都是 DOM，做得到） |
| ② 3D 内滚动 | 书页加 `overflow: scroll` + CSS3D 缩放 | 3D 内滚动的手感与命中优先级要额外工作；而且"书页可以滚动"本身就削弱了书的隐喻 |
| ③ 全走方案 C | 3D 只做占位，正文一律走 2D 阅读层 | **放弃决策 2 的核心收益**（书页可选中/可复制/链接可点），不推荐 |
| ④ 只做方案 B，不兜底 | —— | 长文用户要翻 45 次页。**不可接受** |

### 现状

配置键**已经存在**（`src/config/reader.config.js`）：

```js
maxPagesInBook: 12,          // 页数超过它就走兜底
fallback: 'reading-layer',   // 'reading-layer' | 'in-book-scroll' | 'none'
```

也就是说：**选 ① 就是"什么都不用改"**，选 ②/③/④ 才需要动配置与 `J6` 结构。

### 为什么要留到 `J5` 之后再确认

阈值 12 页是从"约 440 字/页"推出来的**估计值**。等 `J5` 的内容管线跑起来、有真实文章排版之后，
可以量一次"一页到底装多少字"，届时再定阈值更准（改一个数字而已）。

## 4. OD-4 · 移动端默认行为

### 问题

原型**只在桌面验证过**（1280×800 / 900×1100），且**触屏翻页手势尚未实现**（原型 §7 第 3 条）。
方案 B 的 DOM 书页在移动端能否成立，没有实测依据。

### 选项

| 选项 | 含义 | 成本 / 风险 |
|---|---|---|
| **① 只读门厅 + 「进入 3D」按钮** ★建议（`K18`/`Q4` 原建议） | 移动端默认落到**门厅**（HTML 文章列表，零 JS 可读）；想进 3D 需显式点击。且**通道 B 在移动端降级为通道 D**（全屏阅读层） | 一个门厅页（`J1.5` 本来就要做）+ 一个降级开关 |
| ② 与桌面一致 | 移动端也直接进 3D、也用书页阅读 | 需补触屏翻页手势与性能适配，**且没有验证基础** |
| ③ 移动端禁用通道 B | 3D 可用，但读书一律走 2D | 比 ① 更保守（3D 里没有可读内容） |

### 现状

配置键**已经存在**（`src/config/reader.config.js`）：

```js
mobile: { channels: ['D'], skipCameraMove: true, fallback: 'reading-layer' },
```

即**已经按建议 ① 写好了默认值**。选 ②/③ 才需要改。

### 附带的一条

`J8.4`（无障碍）与 `J8.3`（低配档 / 移动端阅读时挂起渲染循环）会一并处理移动端的性能问题，
所以本项**不需要在 `J1.5` 就定死**。
