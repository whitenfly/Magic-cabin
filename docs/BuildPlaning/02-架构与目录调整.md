# 02 · 架构与目录调整（决策 1）

> **回答**：以"小屋是完全独立的静态博客"为定位，现在的项目架构与文件夹架构是否合理？需要怎么微调？
>
> **结论**：
> **① 分层架构与依赖方向 —— 合理，全部保留。**
> **② 文件夹架构 —— 骨架合理，但有 6 处需要微调**（删 1、换 1、升格 1、新增 3）。
> **③ 微调的原因是"上游失效产物"与"两个新决策"，不是原设计错了。**

## 2. 目标架构

```
┌───────────────────────────────────────────────────────────────────────┐
│  站点层（Astro，output: 'static'）                                      │
│   src/pages/*.astro      → /  /posts/<slug>/  /tags/  /archive/  /about/│
│   src/layouts/ · components/  → 门厅 HTML、SEO、JSON-LD、RSS、sitemap    │
│   src/content/           → ★ 内容源（作者唯一手写的目录）                 │
└──────────────────────────────┬────────────────────────────────────────┘
                               │ 三个契约：posts.json · 正文片段 · 命令总线
┌──────────────────────────────▼────────────────────────────────────────┐
│  应用层                                                                │
│   src/blog/     博客内核：ContentLoader · ShelfLayout · BookSpine ·     │
│                 Reader(css3d) · Router · commands · registry          │
│   src/features/ ★ 功能模块（一模块一目录 = 一个增量开发单元）             │
│                 _index.js（唯一总装文件） + 19 个模块目录（M03 拆 a/b）    │
│   src/config/   ★ 用户配置层（一模块一文件 + index + types + 环境变量）    │
└──────────────────────────────┬────────────────────────────────────────┘
                               │ ctx.commands.run(name, args)  ← 单向
┌──────────────────────────────▼────────────────────────────────────────┐
│  3D 层（原生 ESM + three r128，不做任何框架包装）                        │
│   src/cabin/app/       内核：App · Feature · Clock · EventBus ·         │
│                        UpdateScheduler · Registry · rng · store · mounts│
│   src/cabin/core/      渲染 CameraRig · 材质 · 光照 LightField · 几何 DSL │
│   src/cabin/systems/   player · interaction · weather · audio · magic · ui│
│   src/cabin/world/     layout · house · outdoor · floor1 · floor2        │
│   src/cabin/props/     跨场景复用道具                                    │
│   src/cabin/legacy/    ⬜ 待掏空（J4 删除）                              │
└───────────────────────────────────────────────────────────────────────┘
```

**依赖方向严格单向**：`pages → blog/features → cabin/{systems,core}`。
`cabin/**` **绝不** import `blog/**` 或 `features/**` 的具体实现——它只发命令名、只声明挂载点 ID。

## 3. 目录微调清单（逐条）

| # | 现状（磁盘实况） | 动作 | 理由 | 影响面 |
|---|---|---|---|---|
| **M-1** | `src/data/`（1 个 README + 9 个计划文件：`client`/`cache`/`result`/`errors`/`transport`/`source`/`contract`…） | **删除** | 它是"从远端取数据 + 三级缓存 + 结果来源标记"的**网络机制层**（吸收 Firefly 的 `utils/fetch-dedup.ts`）。而小屋是**零外部数据源的静态站**：唯一的数据加载是"构建产物 `posts.json` + 正文片段"，由 `blog/ContentLoader` 一层 `Map` 缓存即可承担。保留 9 个机制文件属于**过度设计**，且会诱导后续模块走 fetch 路线 | 删 1 个目录；`ArtLine-Part/07` 的"机制集中"边界随之作废 |
| **M-2** | `src/domains/`（19 个目录，每个预置 9 文件脚手架 `index/schema/source/fetch/adapter/query/fallback/present/ui`） | **替换为 `src/features/`** | ① 19 个目录是 **Firefly 内部切片的镜像**：`analytics` 已判定整体移除、`sponsor`（M09）不映射到场景、`srs` 不在原 17 模块内、`nav`/`site` 与 `profile` 边界重叠；② 9 文件脚手架是为"远端数据源 + 降级"设计的，小屋用不上；③ 决策 4 要的是**一模块一目录的增量单元**，与 `mapping.yaml` 的 module id 一一对应 | 删 19 个目录，新建 1 个 `features/` + **19 个模块目录**（`M03` 拆 a/b；按需创建，不预置空目录） |
| **M-3** | `src/config/`（1 个 README 占位，其内容写着"接入方式：原样保留 Firefly 的 28 个配置文件"） | **升格并重写** | 决策 5：配置是"**用户唯一需要看的目录**"，是 Firefly 的核心卖点与编排方法所在。原 README 的"保留 Firefly 28 个配置"已经不成立，需改为小屋自己的配置清单 | 重写 README；新增 `index.js` + `types.js` + N 个 `*.config.js` |
| **M-4** | `src/blog/` 不存在 | **新增** | `improve/07` §2 的核心；所有模块共享的内容内核。**没有它，`features/*` 会各自重造内容读取与书架算法** | 新增（`J5`/`J6` 填充） |
| **M-5** | 仓库根 `content/` 不存在（`improve/07` 计划放在根） | **新增 `src/content/`**（Astro 内容集合惯例） | 决策 3 采用 Astro 后，内容集合位于 `src/content/`。**少一套约定**，且能直接用 `getCollection()` 与 Zod schema。非集合类内容（自定义页）仍可放仓库根 `content/` | ✅ **J1.5 已落地**：集合骨架 + 样例文章 + `src/content.config.ts`；加载器用 `src/blog/loaders.js`（原因见 [`J1.5-实施结果`](../实施结果/J1.5-实施结果.md) §4） |
| **M-6** | `tests/` 不存在；`_shots/` 与 `scripts/verify-*.mjs` 平铺在根 | **新增 `tests/{visual,e2e,unit}/`**，把 `J0.4` 的截图基线纳入 | `J0.4` 是后续一切改动的安全网，需要有稳定位置与 CI 入口 | ✅ **J1.5 追加**：`tests/e2e/page.mjs`（首页形态解析，两条产线共用）+ `tests/baseline/cabin-digest.json`（"3D 一行未改"的判据） |
