## 3. 方案 B 的落地：四个必须逐条落实的硬约定

> 这四条全部来自原型实测踩坑。它们**不抛异常，只表现为闪烁**——
> 所以必须**写成机器校验**，不能只写进文档。对应验收 `CH1`–`CH3`。

### 3.1 层次模型：深度 + DOM 顺序，双保险

「谁在前面」由**真实深度**与**DOM 顺序**共同决定，**只做对其中一个都会翻车**。

```js
// ① 深度：每一层留出足够高度差（世界单位 0.001 ≈ 屏幕上 1.5px）
//    封底 0.0055 < 封面反面(翻开) 0.0132 < 书页 0.0232 < 翻页中的纸 0.0232 + 0.0018 ± 0.0009

// ② DOM 顺序：直接 appendChild 到 CSS3DRenderer 的 cameraElement
const STACK_ORDER = [
  backEl, coverFrontEl, coverBackEl,   // 底
  leftSlot, rightSlot,                 // 中
  flipFrontSlot, flipBackSlot,         // 顶：翻页中的纸必须压住书页
]
function restack() {
  for (const el of STACK_ORDER) cameraElement.appendChild(el)
}
```

**三条要点**：

1. `cameraElement` = `cssRenderer.domElement.firstElementChild`（CSS3DRenderer 内部的 `preserve-3d` 容器）。
   自己放进去的元素它不会再次搬动（每帧只检查 `element.parentNode !== cameraElement`），所以顺序是稳的。
2. **顺序必须在渲染之后排**：CSS3DRenderer 每帧才会把未进 DOM 的 element 追加进去，第一次渲染之后 `STACK_ORDER` 才真正可排。
   做法：状态变化置 `stackDirty`，在 `render()` 之后执行一次 `restack()`。
3. ❌ **绝不要用 `cssBook.add(...)` 去重排层次**——three 的 `add()` 只对**对象自己**派发 `'removed'`，
   而 `CSS3DObject` 正是靠它把 element 从 `cameraElement` 摘下来；**Group 没有这个事件**，挂在 Group 下的封面与纸永远不会被重新 append。
   > 原型里为此写过一个 `relayer()`，**它从未真正生效**——已删除，不要再写回来。

### 3.2 正反面：用 JS 切 `visible`，**禁用** `backface-visibility`

```js
function syncFaces() {
  const paperBack = Math.abs(book.pivots.flip.rotation.z) / Math.PI > 0.5
  flipFrontObj.visible = flipOn && !paperBack
  flipBackObj.visible  = flipOn &&  paperBack
  const coverBack = Math.abs(book.pivots.cover.rotation.z) / Math.PI > 0.5
  coverFrontObj.visible = !coverBack
  coverBackObj.visible  =  coverBack
}
```

**为什么不用 `backface-visibility: hidden`**（实测两个问题）：

1. 在「父级旋转 + 子级旋转」的组合变换下判定不可靠——纸转到 90° 附近会**两个面同时被判为背面**，整张纸消失一帧再回来；
2. 带 `overflow:hidden` / `border-radius` 的元素（封面）会建立新的层叠上下文，加上它之后**在合上状态就整体消失**。

**切换点取 90°**：那时平面对视线几乎侧向，投影退化成一条线，换内容完全看不见。
**副作用是好的**：任何时刻只有一面 `visible`，两个面"必然共面"就不再有害。

### 3.3 动画中不碰 DOM：内容只在**状态边界**装填

```
next() ──► onChange(flipping) ──► 动画推进 (t: 0→1) ──► onChange(open)
              │                                          │
        ① 装填纸面内容 + 预置目标页                   ② 左右页就位
          （纸还没转，安全）                          （纸已收起，安全）

✗ 绝不在 t 从 0 走到 1 的过程中改 DOM 结构
```

配套三件事：

| # | 做法 | 为什么 |
|---|---|---|
| ① | **预构建节点**：启动时把每一页的 DOM 建好，换页时用 `replaceChildren` **原子切换节点引用** | 不做 `innerHTML` 解析（解析 + 重排会让旋转中的元素渲染出未完成状态） |
| ② | **槽（slot）**：`CSS3DObject` 的 element 用固定容器，内容作为子节点切换 | element 本身不换，CSS3DRenderer 的缓存与 DOM 顺序都不受影响 |
| ③ | **渲染循环只做变换同步** | `loop()` 里一行 DOM 结构操作都没有 |

> ⚠️ **空白页的槽不要用"轮换池"**：同一个 DOM 节点不可能同时挂在两个槽上（`appendChild` 会把它从原处摘走）。**每个槽各持有一份空白页。**

### 3.4 平面视角：相机垂直俯视即可，**不必换正交相机**

**几何依据**：书页是一个**水平平面**。相机从正上方垂直向下看时，平面上每个点到相机的距离完全相同 → 透视除法是同一个系数 → 投影是**均匀缩放**。
**透视相机垂直俯视的投影，和正交投影没有区别。**

实测（判据：投影宽高比是否等于书页本身的 `0.19/0.245 = 0.7755`）：

| 视角 | 左右页投影宽高比 | 与设计值偏差 |
|---|---|---|
| 斜俯视 `(0, 0.40, 0.25)` | 1.0689 | **0.587**（梯形变形） |
| **垂直俯视 `(0, 1.40, 0)`** | **0.7752** | **0.0003** ← 就是正矩形 |

**三个必须注意的实现点**：

1. **姿态不能用 `lookAt` 求**。垂直俯视的视线是 `(0,-1,0)`，与默认 `up = (0,1,0)` **平行**，
   `lookAt` 内部的叉积退化成零向量，**矩阵直接坏掉且不报错**。要直接由欧拉角构造：
   ```js
   const VIEW_FLAT = { quat: new THREE.Quaternion().setFromEuler(new THREE.Euler(-Math.PI / 2, 0, 0)) }
   ```
2. **相机要拉远、fov 同比缩小**。垂直俯视消掉了梯形变形，但不同高度的平面离相机远近仍不同：
   合上时封面在 `y≈0.046`、翻开后书页在 `y≈0.023`；相机若只站在 0.42 处，两者缩放差 **6%**，翻开瞬间内容会"胀"一下。
   拉到 **1.4**（fov 缩到 **13°**，屏幕上大小不变）后降到 **1.6%**。
3. **雾（fog）必须跟着相机走**。原雾 `near 1.4`，相机一退到 1.4 正好把内容吃掉、整块发暗。
   平面视角取 `near 2.6 / far 10`，并在过渡中插值。

**过渡**：位置 `lerp`、朝向 `slerpQuaternions`、fov 与 fog 同步插值 → 看起来像镜头推拉。

### 3.5 枢轴与落点（几何约定）

- **基准高度只能由枢轴承担一次**。若枢轴和子元素都带基准量，它会被算两次（表现为"翻开时位置跳一下"）。
- **对称的双面/双位置，偏移必须取相反数**。正面 `+offset`、反面 `-offset`，否则转 180° 后两者会一起掉到另一侧。
- **旋转轴必须落在纸所在的那个高度上**，否则转 180° 会把纸沉到书页下方。
- **翻页热区默认完全透明**，只在 `pointerenter` 时浮现（否则纸收起后会"突然出现"左右边缘的细线/暗带）。
- 把所有"由 WebGL 自绘内容"的部分收进一个 `contentLayer` group，**整层关掉**（否则 DOM 页面上会再叠一层纯色 mesh，翻页完成后浮出阴影）。
- HUD 工具与常量**一律定义在文件最前面**（`onChange` 注册时会立即执行一次，引用下方 `const` 会 TDZ）。

## 4. ★ 内容呈现四通道模型

> **这是本路线相对上游文档最重要的结构新增。**
> 上游把"渲染方式"当成一个全局选择（A 还是 B 还是 C）；实际上小屋有 **19 个映射条目（18 个编号模块）**，形态差异极大，
> **正确的做法是把"呈现通道"做成每个模块各自声明的字段**，并给出清晰的选型判据。

### 4.1 四个通道

| 通道 | 载体 | 适用（一句话） | 典型模块 |
|---|---|---|---|
| **B · CSS3D 真 DOM** | `CSS3DRenderer` + 真 DOM 平面 | 需要「**读**」的长内容：可选中、可复制、可点链接、需要排版 | **M01 文章正文**、M06 关于页 |
| **A · Canvas 贴图** | `CanvasTexture` | **小体量 + 只读 + 不需选中**，且需要频繁重绘或氛围优先 | **M18 背单词卡片**、M14 热榜条目、M02 年历格 |
| **T4 · 状态量** | 物件**已有的连续属性** | 信息只是一个数：**多少 / 多久 / 多热 / 多亮** | M04 试剂液面、M13 挂钟指针、M14 星铃转速、M12 星象仪光点 |
| **D · DOM 覆盖层** | 普通 2D HTML 层 | 需要**输入**、长列表、复杂控件、无障碍刚需 | M03a 搜索框、M08 评论、M17 设置、M10 相册网格、M11 播放列表 |

> **T4 是最被低估的通道**：它**不需要交互预算**，是"免费"的信息传达。
> 例：M13 用指针位置表达"这间屋子开了 428 天"，用户不点也能看到。
> 详见 [`Blog-Part/03`](../../../docs/Blog-Part/03-映射契约与交互规范.md) §2 的四类归位（T1–T4）。

### 4.2 选型判据（五问，从上往下问）

```
① 需要用户【输入】吗（文本框 / 表单 / 拖拽排序）？
     是 → 通道 D
② 内容需要【选中 / 复制 / 点链接】吗？
     是 → 通道 B（若内容很短也可以用 D）
③ 内容量 > 约 500 字，或需要【滚动 / 搜索 / 无障碍朗读】？
     是 → 通道 B（可翻页）或 D；超过长文阈值时见 §6
④ 内容【每秒/每帧变化】且只读？
     是 → 通道 A（重绘贴图）或 T4（若能映射到物件已有属性）
⑤ 信息只是【一个数值】（多少/多久/多热）？
     是 → 通道 T4（免费）
     都不是 → 通道 A（最省心）或 D（最灵活）
```

**一条硬规则**：**一个模块可以同时用多个通道**，但**同一份数据只能有一个真源**。
例：M13 站点统计 = T4（指针角度，常驻）+ A（12 个刻度上的数字）+ D（点击后的详细面板）——
三者都读同一个 `stats` 对象，**不得各自算一遍**（对应验收 `CH6`）。

### 4.3 通道 A 的首个真实用例：M18 背单词（SRS）

| 项 | 值 |
|---|---|
| 为什么是 A 而不是 B | 单词卡是**短内容**（词 + 音标 + 释义 + 例句，远小于一页书），**不需要选中复制**，且**每张卡切换频繁**——B 的分层成本在这里没有回报，A 的合成层更省心 |
| 为什么不只走 D | 背单词的仪式感来自"**在屋里翻卡**"；纯 2D 面板会丢掉这个体验。**A 保留 3D 呈现 + 极快的换卡** |
| 场景载体（建议，待拍板） | **大魔女坩埚**（已有 `regMagic` 点击交互 + 沸腾动效 → "往锅里投入一个词，它煮出释义"） |
| 配套 | **D 通道的完整复习界面**（词书管理、统计图表、导入导出）——A 只承担"展示与快答"，重界面仍走 D |
| 数据 | FSRS 算法为**纯逻辑**，可从小屋自己的实现起步（参考 Firefly `utils/srs/fsrs.ts`）；存储用 `IndexedDB`（**小屋自己的库名，不是 `firefly-srs`**） |

> **诚实评估**：这是"**通道 A + 通道 D 并存**"的第一个案例。
> 路线把它排在 `J7` 的 P6 批次（长尾），理由是它**不阻塞任何内容能力**，但**能验证四通道模型是否成立**——
> 如果四通道在这里跑通了，后续所有"小体量内容"都有现成路径。

## 5. 决策 3：Astro 论证与落地

### 5.1 先把问题拆成两半

```
站点 = 内容站那一半  ── /posts/<slug>/  /tags/  /archive/  /about/  /search/  门厅列表
       + 3D 应用那一半 ── 小屋本体（一个长驻的 WebGL 应用） + 各模块面板
```

| 一半 | Astro 的价值 |
|---|---|
| **内容站那一半** | ✅ **价值集中在这里**：内容集合 + Zod、静态路由、零 JS HTML、RSS/sitemap/robots、Pagefind、图片管线、**按需 hydrate 的 DOM 面板** |
| **3D 应用那一半** | ⚪ **几乎为零**：小屋必须整体 `client:only`（它立即操作 WebGL 与 DOM），Astro 的岛屿架构在这个岛**内部**不起作用——岛内的模块加载仍由 `blog/registry.js` + 动态 `import()` 负责 |

**所以"Astro 有利于各模块的加载"这句话的正确形式是**：
**Astro 有利于「2D DOM 面板」与「内容页」的按模块加载；对 3D 场景内部的模块加载没有帮助。**
两者加起来仍然是一笔划算的账，但必须按下面的职责边界来用，否则会得到一个"两头不讨好"的混合体。

### 5.2 收益核算（相对自写 Vite MPA + ~300 行 SSG 脚本）

| # | 能力 | Vite MPA 要做的事 | Astro | 净收益 |
|---|---|---|---|---|
| 1 | 内容 schema 校验 | 自写 JSON Schema / Zod 调用 | `src/content.config.ts` 声明式 | **~1.5 人日** |
| 2 | 逐篇静态页 | 自写 `gen-pages.mjs`（模板拼接 HTML） | `src/pages/posts/[slug].astro` + `getStaticPaths()` | **~2 人日** |
| 3 | RSS / sitemap / robots | 自写 `gen-feeds.mjs` | `@astrojs/rss` + `@astrojs/sitemap` | **~0.5 人日** |
| 4 | 多入口 HTML + 代码分割 | 手工维护 `rollupOptions.input` 与每页的 `<script>` | 按页面自动分块 | **~1 人日** |
| 5 | DOM 面板按需加载 | 手工 `import()` + 手动挂载点 | 组件级 `client:visible` / `client:idle` / `client:media` | **~1 人日** |

**净账（必须诚实说明）**：

| | 人日 |
|---|---|
| Astro 省下的手工工作（上表） | **+7.5** |
| Astro 自身的落地成本（下表 1、3、4 项） | **−4 ~ −5** |

> **所以"选 Astro"的理由不是"现在能省人日"，而是三件长期的事**：
> ① **同一个框架支撑 18 个模块的面板加载**（决策 4 的增量开发需要一个"每模块按需 hydrate"的机制）；
> ② **与 Firefly 同栈 ⇒ remark/rehype 插件与配置编排方法零翻译**（决策 5 直接照搬，这是最大的一笔长期收益）；
> ③ 内容站那一半的维护成本（SEO / RSS / 图片 / 搜索 / 路由）长期交给框架，而不是自己维护一套 300 行脚本。
>
> **反过来，如果作者更看重"工程轻量、完全可控、不引入新框架"，回到 Vite MPA 也完全可行**——
> 代价是：`J1.5` 取消，`J5` 增至 4–6 人日并需自写 SSG 与多入口 plumbing，
> 以及决策 5 的配置编排方法要自己设计一套（见 [`04`](./04-模块增量开发与配置编排.md) §3.1 的九条）。

| 层 | 由谁负责 | 具体内容 |
|---|---|---|
| **内容源与站点页** | **Astro** | `src/content/posts/*.md`；`src/pages/{index,posts/[slug],tags,archive,about,search,404,rss.xml,robots.txt}`；SEO / OG / JSON-LD；门厅 HTML；Pagefind |
| **2D DOM 面板** | **Astro 组件 + 按需 hydrate**，或**原生 ESM 动态 `import()`**（二者取其一，见下） | 搜索、评论、设置、相册网格、播放列表、背单词复习界面 |
| **3D 场景本体** | **原生 ESM**（`src/cabin/**`，一行不改） | 渲染、交互、天气、玩家、魔法、物件 |
| **3D 内的内容呈现** | **原生 ESM**（`src/blog/reader/Css3dReader.js`） | 通道 B 的 CSS3D 书页、通道 A 的 Canvas 贴图、通道 T4 的状态映射 |
| **功能模块装配** | **原生 ESM**（`src/features/_index.js` + `blog/registry.js`） | 按 `modules.config.js` 增量装配；**Astro 不参与** |

**两条禁止（架构不变量 N12）**：

1. **3D 侧不得 import `*.astro`**；
2. **Astro 侧不得 import `cabin/**` 的实现**——除唯一入口 `CabinMount.astro` 里的一次 `client:only` 挂载。

**三个契约**（两侧只能通过它们交互）：

| 契约 | 形态 | 方向 |
|---|---|---|
| **`posts.json`** | 构建产物（轻量元数据 + 摘要），Astro 构建期写入 `src/blog/generated/` | Astro → 3D（只读） |
| **正文片段** | 每篇文章的正文 HTML，SSG 页面与阅读器共用**同一份渲染结果** | Astro → 通道 B / D |
| **命令总线** | `ctx.commands.run(name, args)`；模块注册实现，物品只发名字 | 3D ↔ 模块（双向，但只经名字） |

> **关于"面板由谁渲染"的取舍建议**：
> ① **纯展示 + 无状态**的面板（归档列表、标签页）→ **Astro 组件**（零客户端 JS，最好）；
> ② **有状态 / 需要与 3D 交互**的面板（搜索、评论、设置、播放器）→ **原生 ESM 模块**，由 `features/*/panel.js` 动态 `import()`。
> **不要**为了统一而把②也写成 Astro 岛——那会把"模块增量开发"的单元从 `features/` 目录切碎到 `.astro` 文件里，违背决策 4。

## 6. 长文兜底（决策点 OD-3）

**问题**：方案 B 的页面尺寸限制了单页容量。原型实测：**29 块 / 2190 有效字符 → 5 页内容 / 3 个跨页**，即**约 440 字/页**。
一篇 20000 字的文章 = **45 页**——"翻几百次页不现实"（原型 §7 第 2 条）。

| 方案 | 做法 | 评价 |
|---|---|---|
| **(a) 阈值 + 混合** ★推荐 | 页数 ≤ 阈值（建议 12 页，≈5000 字）→ **纯方案 B**（在书页里读）；超出 → 3D 仍是那本书（B 形态：封面/书脊/翻页动效都在），但"走进书页"后切到**全屏滚动阅读层** | 保住方案 B 全部收益，长文退回原型方案 C 的**阅读层**形态；代价是两套视图需共用同一份 DOM（可做到，都是 DOM） |
| (b) 方案 B + 缩放/滚动模式 | 在 3D 内给书页加滚动（`overflow: scroll` + CSS3D 缩放） | 原型 §7 建议②；但 3D 内滚动的手感与命中优先级需要额外工作，且"书页可以滚动"本身就削弱了书的隐喻 |
| (c) 全部走方案 C | 3D 只做占位，正文一律走 2D 阅读层 | **放弃决策 2 的核心收益**（书页可选中/可复制/链接可点），不推荐 |
| (d) 只做方案 B，不兜底 | —— | 长文用户要翻 45 次页。**不可接受** |

**推荐 (a)**，并把三个数做成 `src/config/reader.config.js` 的配置项：

```js
export const readerConfig = {
  // ── 方案 B 的书页 ──────────────────────────────
  page: { widthRatio: 0.19, heightRatio: 0.245, columns: 2, fontSize: 17, lineHeight: 1.7 },
  // 平面视角：相机拉远 + fov 同比缩小（见 03 §3.4；改这两个数要重跑 CH5）
  flatView: { distance: 1.4, fov: 13, fogNear: 2.6, fogFar: 10 },
  // ── 长文兜底 ──────────────────────────────────
  maxPagesInBook: 12,          // 页数超过它就走兜底
  fallback: 'reading-layer',   // 'reading-layer' | 'in-book-scroll' | 'none'
  // ── 移动端 ────────────────────────────────────
  mobile: { channels: ['D'], skipCameraMove: true, fallback: 'reading-layer' },
}
```

> ⚠️ **改 `flatView` 会改变实际字号**，必须重跑验收 `CH5`（平面视角下书页文字的实际字高 ≥ 14px）。

## 8. 验收（四通道专项 `CH1`–`CH6`）

| # | 验收项 | 判定方式 | 阶段 |
|---|---|---|---|
| **CH1** | **层次在任何状态下都正确**（合上 / 翻开 / 翻页中 / 平面视角） | `hit-test` 网格字符图 + 逐帧差分**双判据**（`probe1`/`probe4`/`probe5` 移植版） | `J6` |
| **CH2** | **任何时刻只有一个面 `visible`**；CSS 中**不得出现 `backface-visibility`** | 静态扫描 + 运行时断言 | `J6` |
| **CH3** | **翻页期间 DOM 结构变更成簇**；`loop()` 内不得出现 `innerHTML`/`createElement`/`replaceChildren`/`appendChild`/`querySelector`/`insertBefore` | `MutationObserver`（**只监听 `childList`**）+ 源码扫描 | `J6` |
| **CH4** | **长文（> `maxPagesInBook`）自动走兜底**，功能不缺失（可滚动 / 可搜索 / 全键盘 / 可朗读） | 端到端（构造一篇 20000 字文章） | `J6` |
| **CH5** | **平面视角下书页文字的实际字高 ≥ 14px**（目标设备实测）；键盘可聚焦到书页；屏幕阅读器可朗读 | 目标设备手测 + 无障碍检查 | `J6`、`J8.4` |
| **CH6** | **四通道不串味**：同一模块的多个通道读**同一份数据**（无二次真源）；通道 A 的重绘不进入主 `loop()` | 代码评审 + 运行时统计 | `J7` 各模块 |
| **CH7** | 管线内 `CanvasTexture` 数量 ≤ 基线 + 2（书脊用图集；通道 A 的贴图按模块登记） | 运行时统计 | `J6` 起 |
