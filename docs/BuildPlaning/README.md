# 魔法小屋 · 建设规划（BuildPlaning）

> **本目录是"接下来怎么做"的唯一入口。**
> 上游 [`FrontProj/docs/`](../../../docs/) 回答的是**为什么**（定位、现状、方案）；
> 本目录回答的是**做什么、按什么顺序做、每个功能模块怎么落地**。

---

## 0. 一句话定位（沿用 `improve/07`，不变）

**魔法小屋是一个完全独立的、有独特展示方式的静态博客项目。**
Firefly 不是数据源、不是依赖、不是集成对象——它只有两个角色：
① **未来功能的参考清单**；② **可复用代码的参考库**。

## 4. 与 `improve/07` 的差异（必须知道的四件事）

| 项 | `improve/07` | **本目录** | 原因 |
|---|---|---|---|
| 构建 | Vite MPA（自写 ~300 行 SSG 脚本） | **Astro（`output: 'static'`）** | 决策 3；收益与成本核算见 `03` §5 |
| 阅读器 | 方案 C（3D 书 + DOM 阅读层） | **方案 B（CSS3DRenderer 真 DOM 书页）** | 决策 2；原型实测证明"DOM vs 贴图不是性能瓶颈"，B 的排版成本为零 |
| 内容源位置 | 仓库根 `content/posts/*.md` | **`src/content/posts/*.md`**（Astro 内容集合惯例） | 少一套约定；非集合类内容仍可放 `content/` |
| 目录 | `src/blog/` + `src/cabin/` | 再加 **`src/features/`（一模块一目录）** 与 **`src/config/`（升格）** | 决策 4 / 决策 5 |
| 工时 | 51–85 人日 | **66–100 人日**（`J1` 后剩余 62–94） | 增量来自 Astro 落地、配置层、方案 B 的分层与长文兜底、以及 `J7` 更诚实的估算（逐项见 `01` §6） |

**不变的部分**（`improve/07` 的这些结论全部保留）：
小屋是主体且完全独立 · Firefly 零 import · `K7` 锁 three r128 · `K8` 3D 为入口 DOM 为正文（形态变为 B）·
`K9` 合并 `regMagic` + `interactables` · `K10` 视角可达性 · `K18` 门厅策略 · `H2`–`H8` 硬约束。

## 6. 怎么用本目录

### 给作者（你）

1. **改映射**：只改 [`mapping.yaml`](./mapping.yaml) 里对应模块的字段，把 `status` 从 `proposed` 改成 `confirmed`。
   —— 这是"拍板"的动作，改完模型和实现都以它为准。
2. **改配置**：实现落地后，日常只改 `src/config/*.config.js`（对齐 Firefly 的"用户唯一需要看的目录"）。
3. **看进度**：`01-完善路线图.md` §2 的表格状态列。

### 给模型 / 后续会话

1. 先读 [`mapping.yaml`](./mapping.yaml) —— 它是**结构化**的，字段含义见 `05` §2。
2. 再读 [`01-完善路线图.md`](./01-完善路线图.md) §2 确认阶段。
3. 动手前读 [`02-架构与目录调整.md`](./02-架构与目录调整.md) §5 的依赖不变量（**违反即回归**）。
4. 加模块时严格走 [`04-模块增量开发与配置编排.md`](./04-模块增量开发与配置编排.md) §2 的九步 SOP。

## 7. 本目录的维护规则

| 规则 | 说明 |
|---|---|
| **单一真源** | 模块的"承载物品 / 交互 / 呈现通道 / 状态"**只在 `mapping.yaml` 里写一次**；`05` 只做说明，不复制表格 |
| **状态即事实** | `mapping.yaml` 的 `status` 字段是进度的唯一依据，代码与文档不得与之矛盾 |
| **偏差留痕** | 实现与映射不一致时，改 `mapping.yaml` 的 `notes` 并写清原因，**不要偷偷改实现** |
| **不复制上游** | 上游文档的内容一律引用，不复述（避免漂移） |
