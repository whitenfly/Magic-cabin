## 1. 做了什么

| 新增 | 职责 |

| `systems/interaction/types.js` | 契约：`defineInteractable()` / `makeTarget()` / `ancestorVisible()` / `localPointOf()` |

| `systems/interaction/HintUI.js` | 面向用户的提示**唯一出口**（不变量 `N10`） |

| 旧机制 | 覆盖 | 新归属 |
|---|---|---|
| `aimRay()` 里的三段硬编码 | 铰链 → 魔法物件 → 壁炉 | `registerAimSource()` × 3（顺序照旧） |
| `pointerup` 里**又抄一遍**的三段逻辑 | 同上（鼠标位置） | 与准星共用 `aimTarget()` |
| `interactables[]`（9 条硬编码） | 门 / 窗 / 壁炉 / 路牌（近距） | `registerProximity()` × 9 |
| `#hint` 的 `innerHTML`（4 处直接写） | 全部提示文案 | `HintUI` |

## 2. ★ 零差异的关键：注册顺序 = 优先级

`aimTarget()` 按**注册顺序**逐组测试、命中即返回。搬迁前 `aimRay()` 的行为是：

```js
const h = raycaster.intersectObjects(hingeMeshes, …); if (h.length) return …   // ① 铰链
const m = raycaster.intersectObjects(magicMeshes, …); if (m.length) return …   // ② 魔法物件
const f = raycaster.intersectObjects(fireMeshes,  …); if (f.length) return …   // ③ 壁炉
```

所以接入时的注册次序**必须**是 `hinges → magic → fire`（代码里有 ★ 注释，测试里也锁死了
—— `interaction.test.mjs` 有一条"即使壁炉更近也先返回铰链"）。

9 条近距条目的顺序、半径、锚点也逐条照搬：

| id | label | anchor | radius | 备注 |
|---|---|---|---|---|
| `floor1/fireplace` | 点燃 / 熄灭壁炉 | `FX, FZ` | 2.0 | |
| `floor1/chandelier` | 点亮 / 熄灭魔法吊灯 | `0, 0` | 2.4 | |
| `house/door` | 打开 / 关上大门 | `0, 4` | 1.8 | |
| `house/window-front-left` | 开 / 关前左窗 | `WIN_F_L.c, 4` | 1.6 | |
| `house/window-front-right` | 开 / 关前右窗 | `WIN_F_R.c, 4` | 1.6 | |
| `house/window-left` | 开 / 关左侧窗 | `-4, WIN_LEFT.c` | 1.6 | |
| `outdoor/signpost` | 编辑路牌文字 | `3.1, 6.3` | 2.2 | |
| `house/window-right` | 开 / 关右侧窗 | `4, -1.5` | 1.7 | `fullHouseOnly` |
| `house/window-back` | 开 / 关后窗 | `1.5, -4` | 1.7 | `fullHouseOnly` |

> 锚点全部来自 `cabin/world/layout.js`（不变量 `N9`）—— 这正是 `J2.9` 的前置价值。


没有第二处改动：不加射线列表、不改 `updateInteractHint()`、不动 `doInteract()`。
（另一半"新增一盏灯"在 `lighting.test.mjs`。）

## 4. 契约的两条硬要求

`types.js` 的 `defineInteractable()` **在注册时就拒绝**不合规的条目：

| 要求 | 校验 | 验收 |
|---|---|---|
| `mode` 支持 `both` | 只接受 `aim` / `proximity` / `both` | `BB2b` |
| `label` 语义化 | 必须是非空字符串 —— **禁止**默认 `'交互'` | `BB2` |
| 近距条目必须给全 | `anchor`（含有限 x/z）、正 `radius`、`onActivate` | — |

> ⚠️ **现状的诚实说明**：`aim` 源的 `label` 仍取自各物件的 `userData.aimLabel`，
> 缺省时仍会落到 `'交互'`（搬迁前 62 处 `regMagic` 就是这样）。
> **契约已经不允许新代码这样写**，但把 64 处旧物件的文案逐条语义化属于 `J3` 的活
> —— `J3` 的 DoD 明确写着「交互冒烟全绿且 `label` 有语义（不再是"交互"二字）」，
> 那时每件物件搬进 `defineProp`，`label` 自然要写全。

## 5. 遗留：镜子仍是自建射线（**偏差留痕**）

路线图的 `J2.6` 一行包含「镜子自建射线 → 一个契约」，**本次没有迁移**，理由如下：

1. **它的行为与主射线不同**：镜子只对 `mirrorPane` 求交（**不看遮挡**），
   而 `aimTarget()` 是"射线打到的第一个东西"。迁进来会变成"被家具挡住就点不到镜子"
   —— 这是**行为变化**，而 `J2` 的判据是零差异。
2. **它需要"命中点的局部坐标"**：涟漪位置是 `mirrorPane.worldToLocal(hit.point)`，
   契约里当时没有这个概念 —— 现在已补上 `localPointOf(object, worldPoint)`（`types.js`）。
3. `J2.6` 已经解决的是**主路径**的统一（三套 → 一套）；镜子是**单件物件的特殊交互**，
   迁它的合适时机是 `J3` 把镜子搬成 `defineProp` 时（那时它会自带 `meshes` 与 `resolve`）。

`localPointOf()` 就是为它（以及 `J3` 的其它平面交互）预备的。

## 7. 实现中踩到的一个坑（记录）

单元测试里用 `new THREE.Raycaster(origin, dir)` 打自己造的 Mesh **全部打不中** ——
three 的求交用 `matrixWorld`，而它平时由渲染循环更新。
测试里必须手动 `mesh.updateMatrixWorld(true)`（已在测试文件里注释说明）。

## 10. 一句话总结

**四份"找目标"的实现变成一份，画面与交互行为未变** ——
契约把两条硬要求（`mode` 支持 `both`、`label` 必须语义化）写成**注册时就会拒绝**的校验，
于是 `R1`（固定视角下点不开道具）从"每个模块各自记得补"变成"想漏也漏不掉"；
而"注册顺序 = 优先级"这条被显式写下并测试锁死，正是它能做到零差异的原因。
