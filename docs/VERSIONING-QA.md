## 一、基础概念

### Q1 · 为什么不能直接在 `dev` 上提交？看起来多开一条分支很麻烦

因为「**可回退的边界**」是靠合并节点建立的，不是靠分支名。

规范 §3.2 只认一条判据：**任何改动都要能追溯到「某个分支的一次 `--no-ff` 合并」**。

如果直接在 `dev` 上提交，这些提交就散落在 `dev` 的线性历史里，**无法作为一个整体被撤销**。要撤掉一个任务，你只能逐个挑提交——而任务越大，代价越高。判例 P1 就是活生生的例子：`J3` 那 6 个提交直接落在 `dev` 上，结果是**6217 行 / 35 个新模块的改动无法用一条 `revert` 撤掉**。

有了 `--no-ff` 合并节点，撤掉整个任务就是一条命令：

```bash
git revert -m 1 <该任务的 merge commit>
```

开分支的成本是 `task:start` 一条命令；不开分支的代价是"以后想撤只能手工挑文件"。这笔账很不划算。

#### 而且现在**想违规也做不到了**（SPEC-1.0.0 新增的机械防护）

`J3` 的教训说明：光把禁令写进文档不够——旧版红线 1 早就写了"不在 `dev` 上直接开发"，`J3` 还是违反了。所以 SPEC-1.0.0 把 R1 做成了**两层防护**（规范 §9.3）：

| 层 | 覆盖 | 行为 |
|---|---|---|
| 第 1 层 | **模型**（变更命令必经 `exec`） | `guardProtectedBranch()` 在执行前拦截 + 写一条 `kind: blocked` 记录留痕 |
| 第 2 层 | **人工**（终端直接 `git commit`） | `pre-commit` 钩子拒绝（本仓库唯一的阻塞型钩子） |
| 第 3 层 | 事后兜底 | §附录A 的 A8 自检命令 |

**只有两种提交被豁免**：合并提交（`MERGE_HEAD` 存在）、发布元数据提交（暂存区**只有** `package.json`，即 `chore(release)`）。开发提交不可能只改 `package.json`，所以不会误伤。

紧急情况可以 `git commit --no-verify` 绕过——但它会在 reflog 留痕，**用了就要在 `GitPushHistory.md` 补一条记录说明理由**。

### Q2 · ★ 任务分支做完就删，提交记录会不会跟着没了？

**不会。一条都不会丢。** 这是最容易误解、也最值得讲清楚的一点。

#### 先看事实

本仓库里 `task/*` 分支**一个都不剩**（J2.1–J2.10、J2.5、J3、J3.1 的分支全删了），但：

```bash
$ git rev-list --parents -n 1 c55789c          # J3.1 的合并提交
c55789c…  f00bf11…  49bcf8e…
   ↑         ↑          ↑
  自己    父①原dev尖端  父②task/J3.1 分支的尖端

$ git merge-base --is-ancestor 49bcf8e dev     # 那个"被删分支"的提交还在吗？
→ exit=0                                        # ✅ 还在，是 dev 的祖先

$ git log --oneline --graph -7 c55789c
*   c55789c merge J3.1：合入 dev
|\
| * 49bcf8e J3.1 收尾：实施结果文档 + J4 承接缺口清单 + 版本号对齐
| * fa8f38f J3.1 交互通路回归修复（四/四）：…
| * 2758f25 J3.1 交互通路回归修复（三/四）：…
| * 2e33a7f J3.1 交互通路回归修复（二/四）：…
| * d9adb09 J3.1 交互通路回归修复（一/四）：…
|/
* f00bf11 J3 收尾：…
```

分支没了，这 5 条提交**一条不少，SHA 也没变**。

#### 为什么

**commit 是对象，分支只是一个指针文件。** 看磁盘上的真相：

```bash
$ cat .git/refs/heads/dev
c55789cd46032e71d4a030d84e68da7c4993f323     # 整个文件就这一行
```

- **commit**：一旦创建就不可变，存在 `.git/objects/` 里，内容是「快照 + 父提交指针 + 提交信息」。
- **分支**：只是一个 41 字节的文件，里面写着一个 SHA。

> 类比：**commit 是书，分支是书签**。你把书签扔了，书还在书架上。
> Git 的垃圾回收（`git gc`）只清理**不可达**（没有任何引用能走到）的对象，而且还要等宽限期（reflog 30 天 / 对象 90 天）。

#### 关键机制：`--no-ff` 把任务的提交「焊接」进了 `dev`

```
task/J4.1 分支上：  A ── B ── C            ← C 是分支尖端
                             ╲
dev 上：       … ── X ──────── M            ← M 是 merge commit
                              ╱
                       父① = X（原 dev 尖端）
                       父② = C（task 分支尖端）
```

merge commit `M` **有两个父**。M 的父② 是 C，C 的父是 B，B 的父是 A
⇒ **A、B、C 全部变成 `dev` 历史的祖先**。此刻删掉分支这张"纸条"，它们依然可达。

**这正是 `--no-ff` 的真正价值：把任务的提交永久焊进主线的历史图。**

#### 那删除到底失去了什么

| 东西 | 删分支后 |
|---|---|
| commit 对象、提交历史、提交信息 | ✅ 全在 |
| 每个 commit 的 SHA | ✅ 不变 |
| **分支名这块「路牌」** | ❌ 没了（`git log --decorate` 不再显示 `task/J4.1-…`） |
| 远端上的 task 分支 | ❌ 本来就不推 |

唯一失去的是"路牌"，而规范用**提交信息里的编号前缀**补上（`J4.1 player 模块化：…`）——所以 `git log --grep="J3.1"` 随时能把一个任务的全部提交捞回来。

> 📌 **`task/<编号>` tag 这个形态已废止**（SPEC-1.0.2）。0.x 版曾把它登记为"可选的人读便利标记"，
> 但事实上**工具不打它**、`ship` 也**不收它**（只收 `v*`），而且它的功能与"提交信息里的编号前缀"完全重复 ——
> 于是它从命名空间账本里被移除了（§2.1）。
>
> **孤例 `task/J3` 也已于 2026-09-16 删除**（SPEC-1.0.3）。删除是**无损**的，因为它本来就不承载任何东西：
> 它指向的提交仍被 `v0.3.0-dev.1` 引用、且是 `dev` 的祖先（**双重可达**），提交信息本身就写着 `J3 收尾：…`。
> 实测删除后：`git tag -l "task/*"` 为空、`git describe` 仍返回 `v0.3.0-dev.5`、提交与历史一字未少。
>
> 💡 **一个值得记住的判断**：`tag` 之所以"打上就不删"，是因为它是**版本快照 / 回退锚点**；
> 而 `task/<编号>` 这种**纯同义标记**不承载回退能力 —— 删它不违反那条原则的本意。

#### 什么情况才真会丢

| 情况 | 结果 |
|---|---|
| 未合并就删 | 被 Git **挡住**——`task:done` 用的是 `git branch -d`（小写），未合并会报 `error: The branch 'x' is not fully merged.` |
| 未合并 + `git branch -D` 强删 | 提交变不可达 → 90 天后 `gc` 回收 → 真丢（其间 `git reflog` 可救） |
| 用 `rebase` / `squash` 代替 `--no-ff` | 原提交被替换成新对象（旧的在 reflog 里活 30–90 天）——所以规范 R4 禁止这么做 |

#### ⚠️ 风险方向和直觉相反

> **留着 task 分支给你的「安全感」是假的；没 push 才是真的会丢。**

因为按规范 **task 分支不推远端**。一个只存在本地的分支，硬盘坏掉 / 换机器 / 误删目录就没了——它根本不是备份。

而**合并进 `dev` 并 push 之后**，提交才真正有了异地副本。判例 P5 正是这个道理的放大版：那次 37 个提交、11 个 tag 都在本地"留着"，但**没有副本**这件事本身就是隐患。

### Q3 · 为什么 `--no-ff` 是硬规则，而不是风格偏好？

两个理由：

1. **可整体撤销**（Q1 / P1 已说明）——这是功能性理由；
2. **让历史自解释**：`git log --merges` 一眼就能看出"这个阶段由哪几个任务组成"。

自检命令只有两条：

```bash
git log --merges --oneline -10          # 每个任务/阶段应当各有一个合并节点
git log --oneline --no-merges "$(git describe --tags --abbrev=0 dev)..dev"   # 应为空
```

第二条若出现本阶段的 `feat`/`fix` 提交 ⇒ 违反 R1。

---

### Q4 · 为什么不用长期 `release` 分支？

`tag` 已经能**永久冻结**任意 commit，而且**不会和后续开发打架**。多一条长期分支只会多一份需要同步的状态——对单人项目是纯负债。

**版本快照一律用 tag，不用分支。**

---

### Q5 · tag 和分支的生命周期为什么是**相反**的？

| | 谁创建 | 用完怎么办 | 推不推 | 为什么 |
|---|---|---|---|---|
| **分支** `task/…` | `task:start` | **合并后立即删** | 不推 | 它是过程中的**脚手架**；使命（提供合并节点）已完成，留着只会让 `git branch` 变乱、让旧分支名误导"这是当前任务" |
| **tag** `v0.x.0-dev.N` | `task:done` | **永不删** | **推** | 它是**版本快照**，是回退的锚点；删了就失去了"随时回到那一版并跑起来"的能力 |

一句话：**分支是便签，用完就撕；tag 是纪念章，钉上就不动。**

## 二、编号与版本号

### Q6 · `J2.5` 为什么会撞号？现在怎么保证不再发生？

**成因**（判例 P6）：骨架继承自 `improve/07` 的 `J0`–`J8`（那里**没有**阶段内编号）。后来一边为 `J2` 细化出 10 项任务（引入 `J2.1`–`J2.10`），一边又新增两个插层子阶段（`J1.5`、`J2.5`）——**两套编号共用一种形式**，于是在 `y = 5` 处撞车。

后果不是"不好看"，而是**实打实的错误**：`J2.5` 有两义 ⇒ `task:done` 无法自行判断该用 `0.2.0` 还是 `0.2.5` ⇒ 只能靠人传 `--base` ⇒ 人忘了传就打出错 tag（判例 P2）。

**现行做法**（规范 §2）：

- **C1**：`y = 5` **永久保留给插层子阶段**，阶段内任务编号**跳过 5**（`J4.4` 之后直接 `J4.6`）；
- **R7**：分支名匹配 `^task/J\d+\.5-` 即视为子阶段，阶段内任务**永远不会**出现 `.5`；
- 历史文件**不改名**（`J2.5-实施结果.md` 与 `J2.5-配置编排层-实施结果.md` 并存）——**约定随事实更新，历史不动**。

> 为什么不让未来阶段"改个号就完了"：`J2` 的 10 项任务已全部归档（文件名、tag、提交信息里都是 `J2.x`），改名要动 10 个文件名与约 60 处引用，收益仅仅是"好看"。所以选择**把约定写清楚**，而不是事后改号。

### Q7 · `--base` 是什么？为什么阶段内任务必须显式传？

`--base=x.y.z` 告诉脚本"这次任务的版本号基数是多少"。

脚本在没收到 `--base` 时会**按任务号推断**：`J3.1` → `0.3.1`。但规范要求**阶段内任务与所属阶段共用同一条 dev 序列**（`J3.1` 应用 `0.3.0-dev.N`）——两者矛盾，于是必须显式指定：

```bash
node scripts/release.mjs done J3.1 --base=0.3.0     # ✅ → v0.3.0-dev.2
node scripts/release.mjs done J3.1                  # ❌ → v0.3.1-dev.1（判例 P2 的原始事故）
```

**例外**：整阶段（`J4`）与 `.5` 子阶段（`J2.5`）可以不传——脚本能正确推断。

---

### Q8 · `dev.N` 里的 N 是怎么来的？为什么不能重用？

规范 §2.4 规定：`N` = 同 base 下**历史出现过的最大 N + 1**。

⚠️ 这里有一个**已知的工具偏差**：`scripts/release.mjs` 目前用的是「现存同 base tag 的**数量** + 1」。如果曾经删掉过中间的某个 `dev.N`（比如判例 P3 那次删 tag），数量就会少一个，**下一个 N 会与已存在的重复**，`git tag` 会直接报 `already exists`。

所以规范把它写成**硬约束 R8**（不许重用序号），而不是只描述工具行为：遇到冲突时，**用最大 N + 1 手工指定**，并在 `GitPushHistory.md` 留记录。这条偏差已列入待修的规范缺陷（走 §12 修订流程）。

**为什么序号不能重用**：tag 一旦推送过，别人可能已经克隆/引用了。`v0.4.0-dev.2` 如果先后指向两个不同的提交，所有引用它的人都会困惑。

---

### Q9 · `F0.2`–`F0.6` 和 `J0.2`–`J0.6` 是什么关系？

它们是**同一批任务的历史别名**：路线图里写 `J0.x`，而 `docs/实施结果/` 下的文件名是 `F0.x-实施结果.md`。

而且这些任务**从未单独发版**——`git tag -l` 里没有 `v0.1.2`–`v0.1.6`，它们统一由 `v0.1.5` 发布（`v0.1.5` 的内容就是「`J0` 基线护栏 + `J1` 工程化骨架 + `J1.5` Astro 落地」）。

**现行处理**：文件名**不改**（历史不动）；**禁止**再新造 `F` 前缀编号，新编号一律 `J<d>`。规范 §5.4 的版本历史表里也把 `0.1.2`–`0.1.6` 标为「⬜ 未单独发版」，避免读者以为漏推了 4 个 tag。

## 三、流程执行

### Q10 · ★ 我在 `dev` 上顺手改了文件（还没提交），怎么办？

**不要"先提交再补分支"**——那样就已经违反 R1 了。

正确做法是**先开分支**：`git switch -c` 会**把未提交的改动一起带过去**。

```bash
git switch dev
node scripts/release.mjs start J3.2 versioning-spec
#   ↑ 会提示「工作区不干净，建议先提交或 stash」——这是**提醒型**检查，不阻塞
git add docs/VERSIONING.md
git commit -F .cache/commit-msg.txt
```

此时改动已经在正确的分支上了，历史是干净的。

> 这正是规范 §3.3 把 `task:start` 的三条检查标为「**提醒型**（不阻塞）」的原因——它允许"带着工作区改动开分支"这个**合法且常用**的操作。

---

### Q11 · 已经在 `dev` 上误提交了怎么办？

**未推送**：把提交"接"到新分支上，让 `dev` 回到干净状态。

```bash
git branch task/J4.1-player-module     # 用当前 dev 的位置建分支（提交跟着走）
git switch dev
git reset --hard HEAD~1                # dev 回退一格（未推送，安全）
git switch task/J4.1-player-module     # 在分支上继续
```

**已推送**：**禁止**改写历史（R11）。改用 `git revert` 生成反向提交，并在记录里留痕说明。

---

### Q12 · 任务做了一半不想做了，怎么清理？

| 阶段 | 做法 |
|---|---|
| **还没合并** | `git switch dev && git branch -D task/…`（强删未合并分支，提交变不可达；`git reflog` 可救 90 天） |
| **已经合并** | `git revert -m 1 <merge commit>` —— 正规做法，历史留痕 |

---

### Q13 · 为什么推送必须由人工执行？工具为什么不自动 push？

因为**工具不该做它无法可靠完成的事**。实测：受限沙箱里 `git push` 会因 SSH 无法创建命名管道而失败：

```
ssh.exe: *** fatal error - couldn't create signal pipe, Win32 error 5
```

让工具"有时能推、有时静默失败"，比"只生成命令交给人执行"危险得多——**静默失败正是判例 P5 的成因**。

所以 §4⑦ 的分工是：**工具生成命令 + 记录，人工在普通终端执行，工具事后用 git 状态核对**。

---

### Q14 · 推送之后为什么一定要跑 `git:status`？

因为它是把待执行命令的 `[ ]` 翻成 `[x]` 的**唯一时机**（§9.1 铁律 3「标记不猜」：只有 git 状态能证明执行了才翻）。

**真实证据**：本项目里曾经有 5 条 `# [ ] git push origin dev` 长期未翻，而 `origin/dev` 其实早就同步了——只是因为推送后没人跑 `git:status`。

好消息是它有**自愈能力**：`start` / `verify` / `done` / `ship` / `status` 每次运行都会顺带做完成标记。所以下次跑任意工具命令，滞留的 `[ ]` 会自动翻正。

---

### Q15 · `task:done` 跑的门禁够吗？

**不够。** 这是 0.x 版规范里最容易误读的一处，SPEC-1.0.0 已在 §6 明确澄清：

| | 内容 | 谁跑 |
|---|---|---|
| **静态三件套** | `typecheck` + `verify` + `build` | `task:verify` / `task:done` 自动跑 |
| **完整门禁（六项，DoD）** | 静态三件套 + `test:visual` + `test:smoke` + `test:perf` | 后三项**人工必须跑** |

原因是技术性的：`test:visual` / `test:smoke` / `test:perf` 需要先 `build` 再 `serve` 托管 `dist/`，脚本内不好托管服务器。

**结论**：`task:done` 通过 ≠ DoD 达成。后三项的结论**必须**写进实施结果文档。

## 四、事故判例（规则的来源 · 禁止删改）

> 规范里的每条硬规则都能追溯到下面某一次真实翻车。**判例是事实依据，改了判例等于推翻规则**（规范 §12.5）。

### P1 · `J3` 直接提交到 `dev` —— 无法整体撤销

- **发生了什么**：`J3` 的 6 个提交**直接落在 `dev` 上**，没有任务分支、没有合并节点。
- **后果**：**无法用一条 `revert` 整体撤销 `J3`**，只能逐个挑提交。而 `J3` 的改动面是 **6217 行 / 35 个新模块**——这个代价随阶段规模放大。
- **正例**：`J2` 的 10 个任务、`J2.5`、`J3.1` 都走了完整流程。
- **由此产生的规则**：R1（禁止 dev 直提）、R4（`--no-ff` 是硬规则）、§3.2 唯一判据、§4①/⑥ 不可跳步。

### P2 · `J3.1` 漏传 `--base` —— 打成错 tag

- **发生了什么**：`node scripts/release.mjs done J3.1` 按任务号推断出 `v0.3.1-dev.1`；而 `J3.1` 是 `J3` 阶段内的任务，应与 `J3` 共用 `0.3.0-dev.N`。
- **正确命令**：`done J3.1 --base=0.3.0` ⇒ 产出 `v0.3.0-dev.2`。
- **由此产生的规则**：§2.4 序列规则、R6/R8、`--base` 硬规定。

### P3 · tag 更正的**正确示范**

- **发生了什么**：发现 `v0.3.1-dev.1` 打错后，判断该 tag **从未推送**（删除安全）⇒ `git tag -d` ⇒ 改打 `v0.3.0-dev.2`。
- **关键动作**：在 `GitPushHistory.md` 写了一条**更正记录**，说明"按任务号推断错了、我漏传了 `--base`、该 tag 从未推送所以删除安全"。
- **意义**：这是 §13 处置的**标准形态**——**留一条记录，说明发生了什么、为什么、怎么补救**，而不是"悄悄改回去"。

### P4 · 阶段状态有**四处副本**，必然漏同步

- **四个位置**：规范 §5.4 版本历史表 / `README.md` 顶部 / 路线图**阶段总表** / 路线图**阶段章节标题**。
- **实证**：`J3` 已完成并打出 `v0.3.0-dev.1`、`dev.2`，但路线图章节标题仍是 `### J3 · 物件模块化 ⬜`，而规范表里 `0.3.0` 也仍标着「⬜ 计划」。
- **由此产生的规则**：§5.3 阶段收尾清单（四处一起改）+ §5.4 状态只允许三种取值（⬜ 计划 / 🟡 开发中 / ✅ 稳定版）。

### P5 · 2026-09-14 推送事故 —— 记录上"看不出少了什么"

- **发生了什么**：`J2` 阶段收尾后，`main` 的 **37 个提交**与 **11 个 tag** 静静躺在本地，而 `GitPushHistory.md` 上"看不出少做了什么"。
- **两个根因**：
  1. 那时任务级 `done` 只生成 dev 的推送命令，**不生成 tag 的**（`git push origin dev` 不带 tag）；
  2. 阶段收尾**漏跑了 `pnpm ship`**，于是 main 与正式 tag 根本没被列进待执行命令。
- **由此产生的规则**：
  - §4⑦ / §5.2：阶段收尾必须跑 `ship`，三件套（dev + main + 所有未推送 tag）缺一不可；
  - §9.2：「无法确认 ≠ 未推送」——远端不可达时**仍必须列出**这些 tag 的推送命令，**漏列才是危险的**；
  - `pendingPushCommands()` 里那段注释就是这个事故的墓志铭。

### P6 · `J2.5` 撞号 —— 一种形式承载两种含义

- **由此产生的规则**：§2 标识符命名空间账本、C1（跳过序号 5）、R7。

## 五、风险与边界

### Q16 · 本地仓库坏了 / 换机器了怎么办？

| 项 | 是否持久 | 说明 |
|---|---|---|
| 已推送到 `origin` 的提交与 tag | ✅ | 这是**唯一真正的备份** |
| 只在本地、未推送的提交 / tag / 分支 | ❌ | 硬盘坏了就没了（判例 P5 的隐患） |
| `.git/hooks/` 里的钩子 | ❌ | 不受版本控制——换机器后**必须**跑一次 `node scripts/install-hooks.mjs` |
| `GitPushHistory.md` | ❌ | 在 `.gitignore` 里，**只留本地**（它是交接凭据，但不是备份） |
| `node_modules/`、`.astro/` | ❌ | 重新 `install` / `sync` 即可 |

**判据**：`node scripts/release.mjs status` 里 `dev` 与 `main` 都显示 **0 ahead**、所有 tag 都带 **✓**——这才算真的安全。

### Q17 · 规范本身能改吗？怎么改？

**能改，但不能"顺手改"。** 判据必须稳定——一条规则在执行期内被悄悄改掉，会让**正在执行的任务**失去判据，并极易引入自相矛盾的条款。

规范 §12 规定的门槛：

1. 修订**必须**走完整七步流程（立项 → 影响面清单 → 一致性核对 → **人类确认** → 版本递增 → 记录 → 独立提交）；
2. **禁止**在功能任务的同一分支/提交里改规范（R14）；
3. **禁止**模型单方面冻结新版本——**必须**经人类确认；
4. 发现规范有缺陷时：**先按现行规范做完**，另开 `spec:` 任务修。

版本递增规则：措辞澄清 `1.0.0→1.0.1`；新增规则 `→1.1.0`；改变既有规则含义 `→2.0.0`（且必须写明迁移方案）。

> **为什么这么严**：规范是**判据**。判据若可随意变动，`git log` 里的历史就无法被统一解释——同一个操作在昨天合规、今天违规，追溯就失去了意义。

> 📌 **首个执行先例（`J3.3`，2026-09-16）**：`SPEC-1.0.0 → 1.0.1` 就是第一个走完这套流程的修订——
> 独立编号 + 独立分支 + 影响面清单 + **人类确认** + 补丁位递增 + §12.4 追加记录。
> 它也顺带实证了上面第 4 条：**先按现行规范把 `J3.2` 做完，再另开任务修规范**。

### Q18 · 为什么沙箱里 `pnpm` 命令会失败？会毁掉 `node_modules` 吗？

**不会毁掉。** 这个问题在 `J3.3` 被实测查清，根因记录在规范 **§11.1.1**。

**三条实测事实**：

1. **PATH 上可能有两个 pnpm**：宿主注入的 shim（实测 `11.8.0`）**优先**于你自己装的版本（实测 `12.3.4`——才是 `ci.yml` 固定的那个）。所以「我明明装了 12」和「报错说版本不对」可以同时为真。
2. **`node_modules/.modules.yaml` 缺失是直接原因**。pnpm 靠它记录「这个 `node_modules` 是哪个 pnpm、用什么参数装的」；文件不在 ⇒ pnpm 无法确认它完好 ⇒ **任何** `pnpm` 命令（哪怕只是 `git:status`）都会先跑 `runDepsStatusCheck()` 并尝试重装。
3. **重装会在原生依赖的 postinstall 失败**（`esbuild` → `spawnSync … EPERM`，受限环境不允许创建子进程），于是**写不出** `.modules.yaml` ⇒ **每次重复触发，永不收敛**。

**所以：受限环境一律用 `node scripts/release.mjs <子命令>`**——完全等价，且不碰依赖检查。

**⚠️ 千万别按 pnpm 的建议去"修复"**：它会提示设置 `CI=true` 或 `confirmModulesPurge=false`。照做的话 pnpm 会**真的删除 `node_modules` 并重装**——在无网络环境里这等于毁掉工作区。**那个 TTY 中止是保护，不是故障。**

**想彻底修好**：在**普通终端**跑一次 `pnpm install`，补写 `.modules.yaml`。它只补状态文件、不改依赖图 ⇒ **不会改动 `pnpm-lock.yaml`**（lockfile 是判据的一部分）。

**实测：即使重装中途失败，环境也不会坏。** `J3.3` 期间误触发过一次（`+193` 包后失败），事后验证 `astro v7.3.2` 正常、`tsc 5.6.3` 正常、`verify` 7 脚本全过、符号链接完好——`.pnpm` 与 `.bin` 反而被补全了。
