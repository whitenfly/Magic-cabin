## 1. 做了什么

把「8 个硬编码 uniform 槽位」改成「N 个注册式光源」：

| 新增 | 内容 |
|---|---|
| `core/lighting/PointLightSource.js` | 一盏灯的完整描述：`position` / `color` / `radius` / `strength` / `yMin` / `yMax` |
| `core/lighting/LightField.js` | 光照场：注册、槽位分配、每帧填充、超编裁剪 |

**monolith 里被替换掉的**：

```js
// 搬迁前：tickOnce() 里 8 行硬编码（新增一盏灯要改 shader 数组长度、循环上界、uPtCount、这里的赋值）
const PP = FILL.uniforms.uPtPos.value, PC = …, PG = …;
PP[0].set(MTX, 2.52, MTZ); PC[0].set(0xffb066); PG[0].set(4.6, ptLantern, 0.0, 3.04);
… PP[7] …

// 现在：初始化时注册 8 盏，每帧一行
lightField.update(time, dt);
```

## 2. ★ 槽位顺序 = 注册顺序（像素零差异的关键）

shader 的闪烁相位里含 `float(i)`：

```glsl
float flickPt = 0.90 + 0.06 * sin(uTime * (5.3 + float(i) * 1.7) + dPt * 1.1 + float(i) * 2.4) + …
```

**槽位索引参与亮度计算** —— 顺序一换，同一盏灯的闪烁相位就变了。
因此 `LightField` 保证：注册数不超过槽位上限时**严格按注册顺序填入 0…n-1**，
而 monolith 里 8 个 `register()` 的次序与原 `PP[0]…PP[7]` 逐条对齐
（位置、颜色、半径、`yMin/yMax` 也逐字照搬）。

| 槽位 | 光源 | 位置 | 颜色 | 半径 | 强度 | 高度区间 |
|---|---|---|---|---|---|---|
| 0 | 吊挂木灯 | `MTX, 2.52, MTZ` | `0xffb066` | 4.6 | `ptLantern` | 0 – 3.04 |
| 1 | 坩埚魔火 | `CCX, 1.14, CCZ` | `0x6fa8ff` | 5.6 | `0.92`（常量） | 0 – 3.04 |
| 2 | 魔法阵 | `MC_X, 0.36, MC_Z` | `0x9b6fe8` | 5.2 | `ptMc` | 0 – 3.04 |
| 3 | 暖桌 | `KOT_X, 0.48, KOT_Z` | `0xffa858` | 4.2 | `ptKot × 呼吸` | 0 – 3.04 |
| 4 | 水晶球 | `CBX, 0.88, CBZ` | `0xb5a0f2` | 3.6 | `ptCb` | 0 – 3.04 |
| 5 | 蜡烛 | `NSX, FY+1.00, NSZ` | `0xffc06a` | 3.6 | `candleP` | 3.02 – 6.9 |
| 6 | 魔法书桌 | `1.75, TBL_TOP+0.52, -2.72` | `0xffe08a` | 4.6 | `magicP` | 3.02 – 6.9 |
| 7 | 月光盆栽 | `PLX, 0.48, PLZ` | `0x9bc0e8` | 3.8 | `ptPlant` | 0 – 3.04 |

> 位置全部来自 `cabin/world/layout.js`（不变量 `N9`）；强度用**闭包**读状态量
> （`() => ptLantern`），于是 `core/` 里不出现任何具体物件的名字（不变量 `N1`）。
> 暖桌那盏灯的呼吸带 `Math.sin(time * 4.2)`，所以强度函数接收 `(time, dt)` 参数
> —— 注册点在 `tickOnce()` 之外，闭包捕获不到那里的 `time`（这一步踩过，见 §6）。

## 3. ★ DoD 证明：「新增一盏灯的改动文件数 = 1」

路线图的 `J2` DoD 要求「新增一盏灯 / 一个交互的"改动文件数" = 1（写测试用例证明）」。
`tests/unit/lighting.test.mjs` 里那条 ★ 测试就是证明：

```js
// 先铺满 8 盏（模拟现有场景）→ 然后第 9 盏**只做一次 register**
const extra = lamp('new-lamp', { position: [42, 1, 42], color: 0x123456, strength: 2 })
lf.register(extra)
lf.update(0, 0)
assert.ok(fill.uniforms.uPtPos.value.map(v => v.x).includes(42), '新增的灯进入了渲染槽位')
```

**没有第二处改动**：shader 不动、槽位代码不动、`uPtCount` 自动维护、
`monolith` 一行不改 —— 这就是「改动文件数 = 1」的含义。

## 4. 超编与空槽位

| 情形 | 行为 |
|---|---|
| 注册数 ≤ 8 | 按注册顺序填 0…n-1；`uPtCount = n`（零差异路径） |
| 注册数 > 8 | 按 `强度 × priority` 降序取前 8（强度为 0 的最先让位），同强度时**稳定**保持注册顺序；只警告一次 |
| 未使用的槽位 | 写成 `y = 0`（强度 0）—— shader 里 `if (ptS < 0.003) continue` 会跳过；不清理会留下上一帧的残留值 |
| 强度返回 `NaN`/`Infinity` | 按 0 处理（不把 NaN 送进 shader） |

> 超编裁剪会改变槽位分配与闪烁相位 —— 但它只在**真的超过上限**时发生，
> 而且此时必然有画面变化（多了一盏灯），属预期。要全量显示就提升 `POINT_LIGHT_SLOTS`
> 并同步 shader 声明（`tests/unit/materials.test.mjs` 会守住两侧不脱节）。

## 6. 实现中踩到的一个坑（记录）

第一版把暖桌光源写成 `strength: () => ptKot * (0.82 + 0.18 * (0.5 + 0.5 * Math.sin(time * 4.2)))`
—— `time` 是 `tickOnce()` 的**参数**，而注册点在 `tickOnce()` **之外**，
闭包捕获不到它（严格模式下会 `ReferenceError`）。改为 `strength: (time) => …`，
由 `lightField.update(time, dt)` 把时间传进去。

**这也是"强度必须是函数"的原因**：常量强度与时间无关，函数强度才能带上呼吸/闪烁。

## 8. 遗留与交接

| 项 | 留给谁 | 说明 |
|---|---|---|
| 炉火与吊灯的**两段独立光照** | `J8` | 它们不走 `uPt*` 槽位，而是 `uFire*` / `uLamp*` 两组专属 uniform；`J2.2` 已说明"三段合一"属 `J8` 的调优范畴 |
| `POINT_LIGHT_SLOTS` 提升 | 按需 | 要超过 8 盏灯时：改 `FillMaterial.js` 的常量 + `fill.frag.glsl.js` 的三处数组声明与循环上界（`materials.test.mjs` 会验证一致） |
| 光源的 `priority` | `J7` | 现在都取默认 1；将来某个模块的灯更重要时可以调 |
| 按 tier / 距离裁剪光源 | `J8` | `J2` 期间不做（画面零差异的前提） |

## 9. 一句话总结

**"新增一盏灯要改 4 处"变成"注册一次"** —— 8 个槽位、位序、参数逐字照搬所以画面未变，
而 `LightField` 把"槽位顺序即相位"这条隐式规则写成了显式契约（并有测试锁死），
这是 `J3` 搬 67 件物件时"每件物件自己声明 `lights()`"的前提。
