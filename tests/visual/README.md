# tests/visual — 截图回归（J0.4 ✅ 已落地）

> **判据**：同一机位 + 同一种子 + 定格到第 120 帧 ⇒ **PNG 逐字节相同**。
> `baseline/*.png` 是证据，`baseline/manifest.json` 里的 `sha256` 是判据本身。**两者都必须提交。**

没有它，`J3` 的 67 件物件搬迁全是盲改 —— 这是 [`improve/05`](../../../docs/improve/05-阻断级发现与整合评审.md) U3 判定"不可选"的原因。

---

## 1. 目录内容

| 文件 | 内容 |
|---|---|
| `baseline/*.png` | 基线截图（3 个机位 × 1440×900） |
| `baseline/manifest.json` | 观测条件 + 每张基线的 `{ 机位, 相机, 小屋形态, 视口, 种子, 帧数, sha256, 画面统计 }` |
| `poses.js` | **机位表**（相机坐标 + 小屋形态）—— 判据的一部分，与基线同住 |
| `capture.mjs` | 抓图（固定种子 + 定格时钟 + 固定机位 + 逐机位重新加载） |
| `compare.mjs` | 与基线比对（sha256 主判据 + 逐像素差异定位） |
| `png.mjs` | 零依赖 PNG 解码 / 像素比对 / 画面统计 |
| `view.mjs` | **字符图查看器**（终端里"看"构图与差异；模型无法读图时的必备工具） |

零依赖 CDP 客户端住在 `tests/e2e/cdp.mjs`（按 [`03`](../../docs/BuildPlaning/03-渲染通道与构建选型.md) §7 的移植表），由本目录复用。

---

## 2. 怎么用

```bash
pnpm serve                      # 另开一个终端：零构建兜底服务，必须先用它
pnpm verify:visual              # ★ DoD：连续抓 3 轮，轮间必须零差异
pnpm test:visual                # 与基线比对（搬迁/改动后跑这个）
pnpm test:visual:additive       # 新增式改动：允许恰好 1 个机位有差异（仍需人工审查）
pnpm baseline:visual            # 重建基线 —— ⚠️ 先人工审查画面，不要盲目接受差异

# 单看某张图 / 比对某两张图（终端里的"文字化视觉"）
node tests/visual/view.mjs tests/visual/baseline/floor2-desk.png --cols=100
node tests/visual/view.mjs _shots/visual/floor2-desk.png --diff tests/visual/baseline/floor2-desk.png
```

`capture.mjs` 的常用参数：`--rounds=N`、`--poses=a,b`、`--viewport=1440x900`、`--frames=120`、`--out=<dir>`、`--update`。

> ⚠️ **需要真实浏览器**：CDP 客户端会启动 headless Chrome/Edge。
> 受限沙箱（禁止命名管道）下 Chrome 会以 `FATAL: platform_channel.cc ... 拒绝访问` 退出 —— 这是环境限制，不是脚本问题。

## 3. 判据

| 情形 | 判据 |
|---|---|
| **搬迁式改动**（把 `legacy/` 里的物件模块化） | 全部机位 **sha256 相同**；任何差异都是 bug（`compare.mjs` 严格模式直接失败） |
| **新增式改动**（场景里原本没有的东西） | **只允许 1 个机位有差异**，人工审查后更新基线（`--mode=additive`） |

这条区别来自 [`02-架构与目录调整.md`](../../docs/BuildPlaning/02-架构与目录调整.md) 与 [`docs/MIGRATION.md`](../../docs/MIGRATION.md) §7：
搬迁期"零优化、零画面变化"是硬规矩，新增物品则必然改变画面。

`compare.mjs` 除了哈希，还会给出**差异像素比例与区域包围盒** —— "哪一块变了"比"变了"有用得多。

## 4. 三个机位与两种小屋形态

| 机位 | 相机 | 小屋形态 | 看什么 |
|---|---|---|---|
| `default-fixed` | **不覆盖**（默认固定视角） | `full` | 完整小屋外观 + 森林前景，与"打开页面的第一眼"一致 |
| `floor1-indoor` | `[0, 1.6, 3.0] → [-1.6, 1.1, -1.2]` | `full` | 一楼室内：砖砌壁炉、大坩埚、置物架、天花板梁、承重柱、餐桌 |
| `floor2-desk` | `[0.2, 4.55, 2.95] → [0.2, 3.85, -2.6]` | `full` | 二楼：大床与书桌（含浑天仪/沙漏/魔方等）**同时入画** |

- **小屋形态**是场景自带的「小屋」按钮开关：默认**剖切**（省略的墙/屋顶用虚线示意），
  `full` = 完整外观（实墙 + 屋顶）。机位表显式声明要哪一种（`?house=full|cutaway`）。
- 二楼机位的坐标是**按视场角算出来的**（相机 `fov=50°`、16:10 ⇒ 水平半角 ≈ 36.7°，深度 d 处覆盖半宽 ≈ `0.746·d`），
  改动前请先读 `poses.js` 里那段注释。

## 5. 注意（踩过的坑，别再踩）

1. **"sha256 相同"在画面全黑时同样成立**（F0.3 §6.1 的教训）。
   所以每张图都带内容统计，`capture.mjs` 会把"主色占比 > 98% / 边缘 < 1%"判为无效截图并拒绝写入基线。
2. **边缘统计必须同时看水平与垂直差分**。线稿场景里叠木墙的木纹、地板线、横梁都是**横向**的；
   只算水平差分会把"有木纹的白墙"统计成"空白"——J0.4 期间因此误判过一次"右墙没渲染"。
   实测证据：正对右墙（`full`）边缘 5.96% / 深色描边像素 0.763%，正对左墙 5.45% / 0.780%，**两面墙一致**；
   画面最深像素值 13–16（即描边材质 `0x111111`）⇒ 墙一直在正常渲染。
   `poses.js` 底部也记了这条结论。
3. **每个机位都重新加载页面**。机位不是"移动相机"，而是"从初始状态重新观察"：
   复用页面会让后一个机位落在前一个推进过的状态上（120 帧 → 240 帧），画面不可比。
4. **定格后必须持续重绘**（`preserveDrawingBuffer = false`），静止重绘只 `render()`、不推进任何状态。
5. 基线比对若不稳定，**先查时间源与随机源**（`F0.2`/`F0.3` 已把两者都确定化），
   不要退化成"允许微小差异"的人工比对。
6. 产物目录 `_shots/` 已在 `.gitignore` 里；**`tests/visual/baseline/*.png` 必须提交**（它是判据本身）。
